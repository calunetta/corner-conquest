## 6.7. UI/UX and Other Interactions

#### **UI Dialogs and Player Scope**
- **Local Dialogs:** Most dialogs for actions (`Sabotage`, `Wealthy`, `Position`, `My Cards`, `Abilities Shop`, `ProductiveCardDialog`, `SpecialIslandRollDialog`) are rendered **only for the current player**. Their open/closed state is managed locally in the `GameBoard` component and is not part of the shared `GameState`.
- **Global Dialogs:** The `CombatDialog` and `MonsterCombatDialog` are exceptions. Their state (`combatState`, `monsterCombatState`) is stored in `GameState` because all players need to see the outcome or have the potential to be involved.

#### **Army and Tile Selection**
- **Manual Selection:** Clicking a tile containing one of your armies selects it. This is a local UI action.
- **Multi-Army Selection:** Clicking a tile with multiple friendly armies opens a local `ArmySelectionDialog` to choose a specific unit.
- **Deselection:** An army can be deselected locally by:
    1.  Clicking the "Deselect Army" button. This is a "hard reset" that clears the selected army and any pending card action.
    2.  Clicking on any tile that is not a valid move for the currently selected army.

#### **Home Islands Login & Lobby Background (`LobbyBackground`, `src/modules/lobby/components/LobbyBackground/`)**
- **Single Mount:** `src/app/page.tsx` renders one `<LobbyBackground />` for the Login screen and the Lobby. It is shown only while `activeGameId` is null, so a game board never mounts it; the board's optional sky backdrop is a flat CSS gradient (see "In-Game Sky Background Toggle" below). `Login.tsx` and `Lobby.tsx` do not render it.
- **Layers (bottom to top):** a dusk sky gradient, a sea strip covering the bottom 30% of the screen (`bg-water-pattern`), the clouds, then the three islands. The whole layer is `fixed`, `aria-hidden`, and pointer-transparent.
- **Islands:** base (castle from `PLAYER_DATA`, blue, with a static knight in front of it drawn from `PLAYER_DATA[blue].sprite.idle`, sized by `KNIGHT_SIZE_PERCENT` and placed by `KNIGHT_POSITION`), resource (Food, Wood and Gold nodes from `RESOURCE_SPRITES`), and monster (level 4, Minotaur). All three are `ISLAND_WIDTH_PERCENT` (26%) of the container width and square, placed at `top: 40%` with lefts 4%, 37% and 70%. Below the `md` breakpoint the islands are hidden (`hidden md:block`).
- **Monster (lobby-owned, `LobbyBackground.monster.hook.ts`):** the monster is not rendered by the real `AnimatedMonster` component or hook; the lobby has its own `useLobbyMonster` hook. It wanders by a horizontal offset of −15% to +15% of its sprite width (`MONSTER_WANDER_OFFSET_RANGE`), stepping every 3000–5500 ms (`MONSTER_WANDER_INTERVAL_MS`, one interval drawn on mount), and each step has a 25% chance (`MONSTER_ATTACK_CHANCE`) to show the attack pose instead of wandering. Facing flips when it steps left. Sprite paths still come from `MONSTER_DATA`. Its size (`MONSTER_SIZE_PERCENT`, 45% of the island box) and top-left position (`MONSTER_POSITION`, 27.5%, centred) are in `LobbyBackground.layout.ts`. The monster island clips its contents (`overflow-hidden`), so the wander stays inside its tile.
- **Clouds (`useLobbyBackground`, `LobbyBackground.hook.ts`):** one cloud spawns every 2500 ms, with at most 5 alive at once. Each cloud picks one of `cloud_small.png`, `cloud_medium.png` or `cloud_big.png` at random, lives 18–28 s, then is removed. Its drift and fade come from the `cloud-drift` keyframe in `tailwind.config.ts`.
- **Literal Isolation:** every position, size and timing value for this background lives in `LobbyBackground.layout.ts`. No `LobbyBackground` source file imports `island-tile-slots.types.ts`, and `LobbyBackground.map.test.ts` fails if one does. The same test, and `LobbyBackground.monster.hook.test.ts`, also fail if any `LobbyBackground` source file imports `AnimatedMonster` or `useAnimatedMonster`. The real board's locked slot values are not shared with this background.

#### **In-Game Sky Background Toggle (`useBoardBackground`, `src/modules/shared/`)**
- **Background:** `GameBoardContent` (`src/features/game/components/GameBoard.tsx`) applies `SKY_GRADIENT_CLASS` (`src/modules/shared/sky-gradient.ts`, the same class `LobbyBackground.styles.ts` uses for its sky layer) when the preference is on. When it is off, the board uses its base gradient `bg-gradient-to-b from-background via-background/95 to-black/90`. The board shows only this flat gradient: no clouds, sea strip or islands.
- **Default and storage:** The preference is on by default. It is stored in `localStorage` under `board-background-enabled` as `'true'` or `'false'`, per browser rather than per player or match. `board-background-store.ts` keeps the in-memory value and its subscribers. Storage is read in the hook's mount effect (`hydrateBoardBackgroundFromStorage`), not at module load, so server and client markup match; only a stored `'false'` changes the default.
- **Control:** `GameBoardHeader` (`src/modules/hud/components/GameBoardHeader/`) renders a "Background" label with an image icon and a ShadCN `Switch` (`aria-label="Toggle sky background"`) at the start of its right-hand group, before the turn timer. The header is hidden only when `status === 'finished'`.
- **Sharing:** `useBoardBackground()` (`use-board-background.ts`) returns `{ isBackgroundOn, setBackgroundOn }`. The board and the header both call it and subscribe to the same store, so a toggle takes effect on the board immediately.

## 6.8. Fog of War & Debug Mode

-   **Fog of War (Enabled):** This is the default, tactical experience.
    -   Each player has their own, independent visibility of the map stored in `player.revealedTiles`.
    -   Tiles (and any armies on them) are only revealed to a player when they move one of their armies to an adjacent tile.
    -   Opponent armies are only visible on their starting Base or on personally explored islands.
-   **Fog of War (Disabled):** This mode provides a more open, chess-like experience.
    -   Map visibility is shared. When any player reveals a tile, it becomes visible to *all* players for the rest of the game.
-   **Debug Mode:** This is a special mode intended for testing, which is automatically enabled for "Player vs. Bot" games started from the lobby.
    -   **Complete Map Visibility:** It overrides any Fog of War setting, making the entire map and all armies visible from the start of the match.
    -   **All Special Cards & 20 Starting Resources:** The human player begins the game with one of every available Special Card and **20 Food, 20 Wood, and 20 Gold**, allowing for immediate testing of all strategic and army mechanics.

## 6.9. Bot Logic
The AI behavior is defined in `src/modules/game-rules/bot-turn.reducer.ts` and `services/bot-turn.service.ts`. `decideBotTurn` deep-clones the incoming state (lodash `cloneDeep` — pure, never mutates the caller's object) and runs the three steps below, in that fixed order, before dispatching `EndTurn`:

> [!IMPORTANT]
> **Balance Simulator:** `scripts/balance-simulator/` plays many complete bot-vs-bot matches through this real logic (Firestore stubbed, zero writes) and reports win rates, match length, resource and card economy, combat accuracy, and bot-health signals (does a seat ever leave its own Base, get stuck on Productive, etc.). See `docs/balance-simulator-guide.md` for how to run it and read its report, including its known limitations and the bot quirks it already confirmed.

1.  **Strategic Pre-computation** (`bot-card-strategy.reducer.ts` → `bot-purchases.reducer.ts`):
    - Activates `Reinforce`, `Efficient`, and `MasterBuilder` **unconditionally** whenever held and no card has been used yet this turn — with no check that the bot will actually go on to deploy or upgrade that turn. If it doesn't, the flag simply lapses at the next turn-start reset (§6.1) and the card stays in hand, having used up the turn's one card-action for nothing.
    - `Wealthy`, when held, targets whichever resource the bot is short of, in a fixed priority order: Food (if it can't afford its next deploy and has room for more armies) → else Wood (if it can't afford its upgrade and isn't attack-capped) → else Gold (default).
    - `Sabotage`, when held, **always targets a human opponent, never another bot** — in a multi-bot match, bots never sabotage each other.
    - `Productive`, when the bot's own seat has a pending `productiveDialogState` (§6.6), resolves it immediately by dispatching `UseProductiveCard`. It doubles the first of Food → Wood → Gold on which the bot has a positioned collector. If none is positioned, it clears the dialog with no selection, so the card stays in hand and nothing is doubled. Either way, the turn's collection completes and the bot is never stalled by an open dialog.
    - Purchases run in a fixed order — Ability → Upgrade → Deploy → Buy Card — each re-checking affordability against the state left by the previous purchase in the same turn, so an earlier buy can block a later one.
2.  **Army Action Evaluation & Execution** (`bot-army-actions.reducer.ts`): across all unacted armies on the board, every possible action is scored and the single highest-scoring one executed, repeated until no unacted army has a move left:
    - **Positioning on a resource:** flat priority **6** (tied with moving onto an unrevealed fog tile). Because a collected position clears (§5.3), a bot's farming army is re-positioned each turn it is eligible, and attacks (priority `8 + …`, or 7 vs. a monster) still outrank it.
    - **Attacking a player:** priority **`8 + (bot's attackPower − target's attackPower)`** — relative, not fixed, and has no floor: a bot will pick a fight it's likely to lose if nothing else scores higher that loop.
    - **Attacking a monster:** flat priority **7**, regardless of the monster's level.
    - **Moving onto an unrevealed fog-of-war tile:** priority **6**. **Moving onto an unoccupied resource/Base tile:** priority **4**. **Moving onto a Special island:** priority **3**. Any other move: priority **2**.
    - Any resulting combat (player or monster) is auto-resolved within the same loop — dice rolled with no card options (`useWarChief`/`useOvercome`/`useDecideCard` all `false`), then immediately closed.
3.  **Guaranteed Turn Transition:** the bot calls `handleEndTurn` and the service writes the resulting state to Firestore in a single `setDoc` — **this is a plain write, not a Firestore transaction**: there is no optimistic-concurrency check against the document's current version. If a human action and a bot turn race on the same match document, the later write silently wins and the earlier one is lost; this differs from `handlePlayerExit`, which does use `runTransaction`.

Bots are created at match setup only for a solo-vs-bot lobby game (`maxPlayers === 1`, `game-setup.reducer.ts`). A human seat can also become a bot mid-match when that player leaves a playing match: `handlePlayerExit` sets `isBot: true` and `isVacant: true` on the seat (see §6.12 Match Dismantling Rules), and the session driver's bot-turn effect (`game-board.engine.hook.ts`, see the session driver in §6.14) drives it from then on like any other bot seat.

## 6.10. UI Components and Mobile Responsiveness
- **Map Rendering & Colonist.io Mobile Strategy:**
  - **Desktop Starting Zoom:** Initial zoom on desktop defaults to **85% (`0.85`)**, giving players an optimal tactical overview of the archipelago, centered with margin for the sidebars and HUD.
  - **Zoom Controls:** Zoom in/out operates in 15% intervals with a quick-reset button that returns to the 85% default zoom.
  - **Mobile Auto-Fitting Layout (Colonist.io Paradigm):** On mobile devices, the entire archipelago grid (`MAP_COLS` × `MAP_ROWS`, 5 × 6, from `src/lib/types/actions.ts`) is scaled to fit within the viewport width (`clamp(46px, 13.5vw, 68px)` tile size with `clamp(4px, 1.2vw, 8px)` gaps and reduced frame padding). This ensures all 4 corner bases (Blue, Red, Yellow, Purple) are visible at a glance on initial load without clipping or requiring panning.
  - **Touch Interactions:** Supports smooth single-finger panning and two-finger pinch-to-zoom (up to `2.0x`) for close inspection of individual islands and armies.
- **Mobile Actions Bar:** On mobile, `ActionsPanel` (`src/modules/hud/components/ActionsPanel`) renders a fixed bottom `MobileActionsBar` instead of the desktop `Card` — Row 1 holds context actions (Cancel/Deselect/extra-move banner) plus a "More Actions" trigger, Row 2 holds the primary turn actions (Position/Attack/Deploy/End Turn) sized to a 44px+ touch-target floor. Secondary actions (Upgrade/Buy Card/Cards/Abilities) open in a `MobileActionsSheet` bottom sheet. Disabled-action reasons render as a static caption on mobile (no hover tooltip, since touch has no hover) instead of the desktop `Tooltip`. Desktop rendering (`ActionsPanelView`) is unchanged.
- **Player Stats Display:** The `PlayerInfo` panel renders `armies.length` accurately and displays the base `attackPower` stat with an informative tooltip detailing the `Attack Power + 1` combat dice formula, while prioritizing sprite image loading.
- **Combat & Monster Dialog Flow:**
  - Real-time combat actions (`MonsterCombatRoll`, `CloseMonsterCombat`, `CombatRoll`, `CloseCombat`) update both local client state and Firestore synchronously, ensuring instantaneous UI transitions between preparation, rolling, and results screens.
  - `MonsterCombatDialog` includes a dedicated spectator view during `phase === 'rolling'` that displays a waiting status without interactive buttons, preventing spectator interference or accidental cancellation.
- **Standardized Dialogs:** All game dialogs (`CombatDialog`, `MonsterCombatDialog`, `ArmySelectionDialog`, `AttackSelectionDialog`, `StealResourceDialog`, `SabotageDialog`, `WealthyDialog`, `AbilitiesDialog`, `SpecialIslandRollDialog`, `PositionDialog`) follow standardized ShadCN styling with outline action cancellations and synchronized dice/card payloads.
- **Turn Progression Safety:** `handleEndTurn` utilizes bounded iterative turn advancement to process multiple simultaneous sabotaged players safely without recursion stack risks, and safely validates tile data before passive ability execution.
- **Automatic Turn Completion:** When the active player has exhausted all possible army moves, attacks, positions, and cannot afford any remaining strategic actions (`Deploy`, `Upgrade`, `BuyCard`, `UseCard`, `BuyAbility`), the game automatically completes and transitions the turn.
- **Resource Collection Toasts:** `useResourceCollectionFeedback` (`src/modules/game-board/resource-collection-feedback.hook.ts`) shows the local player a "Resources collected" toast for each new collection log entry addressed to them (automatic or Productive). At the start of their own turn it also shows "Army idle" / "Armies idle" when one or more of their armies sits on an eligible resource or Base spot without a position. Log entries seen before the first render are not replayed, so a reload does not repeat old toasts.
- **Hook Architecture & Firestore Economics:**
  - Custom hooks in `src/modules/` (`useIsMobile` in `shared/`, `useGameEngine` in `game-board/`, `usePlayer` in `session/`) provide consolidated viewport detection, resilient session validation, and real-time Firestore synchronization.
  - **In-Memory Turn Buffering:** Only while `gameState.status === 'playing'` and it is the local human player's turn (`isMyTurn` in `src/modules/game-board/game-board.engine.hook.ts`, which is `false` during `'waiting'`), all human player actions within the turn (`Move`, `Deploy`, `Upgrade`, `BuyCard`, `UseCard`, `SelectResourcePosition`, `CancelAction`) execute entirely in local client memory (`localGameState`, cloned from `serverGameState` in `src/modules/game-board/game-board.state.hook.ts`), generating **zero Firestore writes** until turn completion. The one exception to the local copy is seat management on other seats: `withSyncedSeatManagement` (`src/modules/game-board/game-board.state.map.ts`) copies `isBot`, `isVacant` and `reclaimRequested` from each new `serverGameState` into the buffer for every seat except the local player's own, so a seat that another client converts or reclaims mid-turn shows its current state on the turn-holder's screen. `GameState.heartbeats` is synced the same way but separately (`syncedHeartbeats`), since it lives at the top level of `GameState`, not per seat: every entry is taken from `serverGameState` except the local player's own seat, which is kept from the buffer so the turn-holder's own in-flight heartbeat is never clobbered. This is a read-side sync and adds no write. In the pre-game lobby (`'waiting'`) the displayed game state always tracks the live `serverGameState`, so joining players appear on the host's screen immediately.
  - **Atomic Turn Writes:** A single `setDoc` write is dispatched when ending a turn (`handleEndTurn`), keeping total writes per player to ~1 write per round.
  - **Atomic Bot Loops:** AI bot turns execute completely in memory and commit only once per round via a single atomic `setDoc`.
  - **Zero Redundant Reads:** Host cleanup routines for animations and events use in-memory state references (`gameStateRef`) instead of performing `getDoc` calls before updating documents.
  - **Firestore Free Tier Sustainability:** A standard 20-turn match requires only ~20–30 document writes and ~40–60 document reads across all connected clients combined, allowing hundreds of complete multiplayer games per day on Firebase's free quota.

## 6.11. Tutorial System
- **Overview**: The game includes both a skippable tutorial overlay (`TutorialOverlay.tsx`) and contextual help beacons (`TutorialBeacon` / `TutorialBeacon.tsx`) that explain the UI area they sit next to. Together they cover the core loop: Goals, Deploying, Moving & Positioning, Resources & Shop, Combat, and Special Cards.
- **Interactive Info Beacons**: Contextual helper beacons throughout the HUD render high-contrast pixel icons (`/sprites/icon_info.png`) and open informative popovers on click. Current beacons include `map-info`, `player-info`, and `actions-info`.
- **State Management**: The tutorial overlay remembers whether a player has seen it via `localStorage` (`'corner-conquest-tutorial'`), while each beacon stores a separate `beacon-seen-<id>` flag so input stays calm after first open. Players can reopen either flow from the 'Help' button or by clicking a beacon.
- **Maintenance Rule**: Whenever core mechanics, UI layouts, or game rules are added or modified, update the matching tutorial copy or beacon description (or add a new beacon) so the new-player guidance stays accurate.

## 6.12. End-to-End (E2E) Testing & Match Cleanup Lifecycle
- **Firestore and Auth Emulators**: E2E runs never touch the real project. `playwright.config.ts` starts the Firestore and Auth emulators together (`npx firebase emulators:start --only firestore,auth`, both declared in `firebase.json`, project `demo-corner-conquest`). It builds the app with `NEXT_PUBLIC_FIRESTORE_EMULATOR_HOST` and `NEXT_PUBLIC_FIREBASE_AUTH_EMULATOR_HOST` (`AUTH_EMULATOR_HOST` = `127.0.0.1:9099`), which makes `src/lib/firebase.ts` connect both SDKs to their emulators. Each run starts with an empty database and no Auth users.
- **Mandatory Teardown Hook (`safeCleanupGame`)**:
  - Every Playwright test suite (`e2e/*.spec.ts`) **MUST** register `safeCleanupGame` inside `test.afterEach(async ({ page }) => { await safeCleanupGame(page); });`.
  - **Guaranteed Cleanup Regardless of Test Outcome:** Even if an assertion throws an error or times out midway through test execution, `test.afterEach` is guaranteed to execute, dismissing any open modals and clicking the GameBoard exit button to dismantle the match.
- **Match Dismantling Rules (`handlePlayerExit` in `src/modules/game-rules/services/player-exit.service.ts`)**:
  - **Leaving a Match In Progress (`status === 'playing'`):** Triggered by an explicit exit, or by the staleness check in §6.14. The leaving player's seat is never removed. It is converted in place to a bot (`isBot: true`, `isVacant: true`), keeping its index, armies, resources and board state. A log entry records the takeover. If it was that seat's turn, the seat keeps the turn as a bot: the session driver's bot-turn effect (§6.14) plays it out and calls `handleEndTurn` when it finishes, so the turn is not skipped. Player indices, `baseTiles`, `map` references and `combatState`/`monsterCombatState` are not renumbered.
  - **Already-Bot Seat:** Calling `handlePlayerExit` for a seat that is already a bot is a no-op, so a repeated exit cannot convert the same seat twice.
  - **No Human Players Remaining:** If no real (non-bot) players remain in a match in progress, the game room is deleted immediately (`transaction.delete(gameDocRef)`), so no all-bot match is left behind.
  - **Leaving a Finished Match (`status === 'finished'`):** The victory screen (`VictoryDialog`, §5.1) stays up on the remaining clients, so nothing is spliced, renumbered or handed to `handleEndTurn`. The room is deleted only if no real (non-bot) players remain; otherwise the transaction writes nothing.
  - **Leaving a Pre-Game Lobby (`status === 'waiting'`):** The room is deleted if no real players remain, or if the host leaves while they are the only player. Otherwise the player is removed: the seat is spliced out, the remaining `players` ids are renumbered 0..n-1, and `baseTiles`, map occupants/`positionedBy`, `combatState` and `monsterCombatState` references are shifted to match. If the leaving player was the current player, the turn ends.
  - **Writes:** Every path runs in one `runTransaction` on the match document.
- **Lobby Hygiene:** Adhering to these rules prevents test runs and player abandonments from cluttering Firestore and ensures the game lobby only ever lists active, joinable rooms.

## 6.13. Island Tile Visual Layout & Animated Sprite Architecture
- **Shared Slot Table (`src/modules/map/island-tile-slots.types.ts`)**:
  - Every resource-node and corner coordinate on an island tile lives in this one file: resource node slots (`SINGLE_RESOURCE_SLOT`, `DUAL_RESOURCE_SLOTS`, `TRIPLE_RESOURCE_SLOTS`, `BASE_RESOURCE_SLOTS`), and the corner anchors: boats (`BOAT_CORNER_POSITIONS`, `CORNER_TRANSFORMS`) and knights (`OCCUPANT_CORNER_SLOTS`, same corner order as the boats). Decorative sprites are not in this file; they are data in the decoration layouts config (below).
  - `TileResources.map.ts`, `TileBoats.map.ts` and `TileOccupants.hook.ts` read these tables and define no slot or corner literals of their own. Each component keeps only its selection logic (for example `getSlot` in `TileResources.map.ts`).
  - All percentages are of the tile's own side length, including `SlotDef.size`: the reference size of a resource node's box (39 for a single node, 32 for dual, 27 for triple, 22 for base). Sprite boxes therefore scale with the tile instead of staying at a fixed px size. A non-corner slot must clear the 0–22% and 78–100% bands on at least one axis for every corner it is near: 22% is the boat's 21% half-box plus a 1-point gap.
  - A resource slot's `top`/`left` is always the node's **center** point, not a corner: `TileResourcesView` (`TileResources.tsx`) centers every node on it with `transform: translate(-50%, -50%)`. This is load-bearing, not cosmetic — the Food sprite's box is inflated 1.45x (`FOOD_SCALE`) to compensate its transparent canvas padding, and a corner-anchored box only grows away from its anchor, so an edge-anchored slot could push an inflated Food node's visible center most of the way off the tile. Centering keeps growth symmetric in every direction around the same point, for every resource type.
- **Decoration Layouts (`TileDecorations.tsx`, `src/modules/map/components/TileDecorations/`)**:
  - Decorative sprites on an island tile (trees today) are data. `src/modules/map/decoration-layouts.config.json` holds, for each of the 10 scenario keys in `DECORATION_SCENARIO_KEYS` (`src/modules/map/decoration-layouts.types.ts`), an array of named layouts. A layout is a list of instances, each with `image` (public path under `/sprites/decorations/`), `top`/`left` (the sprite's center, % of the tile side), `size` (box width and height, % of the tile side) and `z`.
  - `toScenarioKey` (`TileDecorations.map.ts`) picks the key: Base → `base`; Special → `special`; Monster → `monster-alive` while `monsters` is non-empty, else `monster-cleared`; Resource → `resource-N`, where N is the summed resource amount clamped to 1–4; Empty or Cleared → `empty-2` or `empty-3` by seed parity.
  - `toDecorationLayout` picks one layout from the key's array with `seed % layouts.length`, where `seed = Math.abs(island.x * 7 + island.y * 13 + (isBase ? 3 : 0))`. The result is a pure function of the island, so every client shows the same layout.
  - Shipped data: Base, Special, Empty (2- and 3-tree), and cleared Monster islands carry trees. `resource-1` to `resource-4` and `monster-alive` each ship one `Default` layout with zero instances, so those islands render no decorations until a layout gets instances.
  - Rendering: each instance is absolutely positioned with `translate(-50%, -50%)` inside a `pointer-events-none` container at `z-[12]`, below `TileBoats` and `TileResources`. Resource and living-Monster islands are not special-cased; they render whatever their layout contains.
- **Animated Resource Representations (`TileResources.tsx`)**:
  - Replaces vector icons with rich animated pixel art sprites positioned at elevated layer `z-35`:
    - **Wheat / Food:** Grazing livestock pasture (`/sprites/sheep.gif`, dialog/HUD icons: `/sprites/icon_meat.png` / `/sprites/meat.png`).
    - **Iron / Wood:** Timber forest (`/sprites/tree.gif`, dialog/HUD icons: `/sprites/icon_wood.png` / `/sprites/wood.png`).
    - **Gems / Gold:** Gold mine (`/sprites/mine.png` idle, `/sprites/mine_active.png` when farmed, dialog/HUD icons: `/sprites/icon_gold.png` / `/sprites/gold.gif`).
  - **Deterministic Node Placement (`TileResources.map.ts`):** Resource nodes sit at fixed center points, clear of the terrain sprite's painted shoreline border on every edge (`public/sprites/terrain.png` bakes a grass/water fringe into the tile, thickest at the bottom): a single node is centered in the tile; two nodes sit at distinct upper-left and lower-right centers; three nodes sit at three centers spread across the tile. The layout is a pure function of the node index, so it is identical on every client.
  - **Individual Multi-Sprite Rendering (No x2 Badges):** Islands with multiple resources of the same type render distinct individual animated sprites side-by-side (e.g. 2 sheep, 2 trees, 2 mines) instead of number badges.
- **Active Collector Farming:** A collector (`/sprites/farm_${player.color}.gif`) assigned to a resource node is drawn as a badge beside that node, not on top of it. The badge is 65% of the node's own rendered box (44.8% for Food, whose box is inflated by `FOOD_SCALE`), with no px floor. It is always centred on the node's left edge, whatever the node's anchor inside the tile (`BADGE_SIZE_RATIO` and `toBadgeSize` in `TileResources.map.ts`; the left-edge placement in `toCollectorBadgeStyle`, `TileResources.tsx`). The badge is not rendered on mobile (`useIsMobile()` in `TileResources()`, `TileResources.tsx`). The soldier remains stationed on the island.
- **Resource Gain Animations:** Whenever a player's resource total increases, a looping GIF from `RESOURCE_GAIN_SPRITES` (`src/modules/shared/resource-display.ts`) plays once for `RESOURCE_GAIN_ANIMATION_MS` (820 ms), then unmounts. The trigger is `StructuredLogEntry.resourceGain`, set by the reducers on every entry that increases a player's resources: automatic and Collector collection, Productive cards, Wealthy, and a successful Steal (for the gainer only). `useResourceGainEvents` (`src/modules/game-board/resource-gain-events.hook.ts`) returns only the entries added since it last saw the log, so a reload does not replay past gains. The existing "Resources collected" toasts are unchanged.
  - **HUD:** only the local player's own `PlayerInfo` card animates. A gain overlay plays under the matching resource chip (`PlayerInfoStats.tsx`), and the chip gets a ring (`PlayerInfo.hook.ts`).
  - **Island tile:** a gain pulses the resource node(s) of each tile listed in `resourceGain[].tileIds`, whichever player made it (`TileResources.hook.ts`). Both nodes of a dual-slot type pulse together. Wealthy and Steal carry no `tileIds`, so they animate the HUD only. The overlay sits above the node sprite and below the collector badge (`TileResources.styles.ts`).
  - **Reduced motion:** the GIF is hidden under `motion-reduce:` and a ring is drawn on the chip or node instead (`PlayerInfo.styles.ts`, `TileResources.styles.ts`).
- **Persistent Soldier / Knight Visibility (`TileOccupants.tsx`)**:
  - Army soldiers / knights remain **persistently visible** on island tiles at all times, ensuring commanders and opponents always have complete situational awareness of garrisoned forces.
  - **Placement:** Knight `N` uses the same corner id as boat `N` (index mod 4), but its box is 27% of the tile side, inset 24% from the tile's two edges at that corner (`OCCUPANT_CORNER_SLOTS`, `TileOccupants.hook.ts`; box size in `styles.slot`, `TileOccupants.styles.ts`). The knight therefore stands on land beside its boat and never shares the boat's center point, so it does not overlap the boat's 42% hull box.
- **Extra Move Card Mechanics & Balance (Nerfed to 1 Bonus Action)**:
  - Using the `Extra Move` card activates `hasExtraMove = true` on the player, allowing any 1 selected army on the board to perform a bonus action (`Move`, `Position`, or `Attack`).
  - As soon as that army completes its action, `hasExtraMove` is consumed (`false`) and all other armies that had previously acted remain disabled (`hasActed = true`), preventing whole-fleet multi-move exploits.
- **Automatic Turn Completion (`hasPlayerRemainingActions` & `GameBoardContext.tsx`)**:
  - Automatically transitions the turn when a player has exhausted all valid moves/attacks/positions and cannot afford any strategic actions (`Deploy`, `Upgrade`, `Buy Card`, `Use Card`, `Buy Ability`). Works from Turn 1 throughout the entire game.
- **Unified Sprite Dialogs & UI Presentation**:
  - All interactive dialogs (`ProductiveCardDialog`, `WealthyDialog`, `StealResourceDialog`, `PositionDialog`, `AbilitiesDialog`) feature rich animated preview sprites (`sheep.gif`, `tree.gif`, `gold.gif`), custom icons (`FightIcon`, `ResourceIcon`), and consistent presentation of resources as **Food**, **Wood**, and **Gold**.
- **Shoreline Boat Docking System (`TileBoats.tsx`)**:
  - Each island features 4 discrete shore corner anchors:
    - Corner 0: Bottom-Right
    - Corner 1: Top-Right
    - Corner 2: Top-Left
    - Corner 3: Bottom-Left
  - Every player's expedition boat (`/sprites/boat.gif`) begins anchored to their home Base shoreline.
  - When an army is occupying an island without being positioned on a resource, an idle faction collector (`/sprites/collector_${player.color}_idle.gif`) waits docked at the shoreline boat, inside the hull's painted silhouette: its box is 36% × 32% of the boat box, centered at 50% / 54% (`collectorOverlay`, `TileBoats.styles.ts`). Player Base tiles start with the owner's boat anchored in the water canal and idle collector. The base boat is not a permanent fixture: it is drawn only while one of the owner's armies is physically on the Base tile (`toTileBoatsViewModel` in `TileBoats.map.ts`), so it disappears once the owner's last army leaves.
  - When an army is landed on an island, their boat docks at the first available corner on that tile. Multiple players or armies occupying the same island receive separate corners without visual collision.
- **Perimeter Map Clouds & Atmosphere (`MapDecorations.tsx`)**:
  - Outer ocean margins surrounding the playable board are decorated with fixed atmospheric cloud formations (`/sprites/cloud_small.png`, `/sprites/cloud_medium.png`, `/sprites/cloud_big.png`) along margins and outer corners, framing uncharted waters.
- **Rebalanced Base Tile Layout (`IslandTile.tsx`)**:
  - Base castles (`/sprites/castle_{color}.png`) are sized to 44% of the base content box, floored at 18px (`IslandTile.tsx`), creating a balanced landscape that cleanly accommodates the castle, tree forest, base resource nodes, idle collectors, and, while an army of the owner is stationed there, the anchored shoreline boat.

- **Special Island Art & Card-Reveal Animation (`IslandTile.tsx`, `IslandTile.hook.ts`, `CardRevealEffect/`)**:
  - An `IslandType.Special` tile shows `special_island_idle.png` (`fill`, `object-contain`) in its center content. While `cardRevealAnimationOnTile` is set and reduced motion is not preferred, `IslandTile.tsx` renders `<CardRevealEffect>` (`special_island_reveal.gif`) in its place.
  - `cardRevealAnimationOnTile` is the first `gameState.cardRevealAnimations` entry on the tile whose `createdAt` is within `REVEAL_ANIMATION_DURATION` (1400 ms) and whose `id` is not in the tile's locally-hidden set. When `CardRevealEffect`'s own timer ends, it calls `onHidden`, and the tile falls back to the idle art at once instead of waiting for the Firestore entry to be removed.
  - `prefersReducedMotion` is read once per tile from `(prefers-reduced-motion: reduce)` in `IslandTile.hook.ts`. When it is true, the GIF is never mounted and the idle art shows for the whole window.
  - Fog (`HelpCircle`) is checked first and wins over both the idle art and the reveal.
  - Clearing: the session driver's `useAnimationCleanup` (`src/modules/game-board/game-board.animation-cleanup.hook.ts`) schedules `clearCardRevealAnimations` for each entry 1400 ms after its `createdAt` (minimum 100 ms). `handleEndTurn` also drops entries older than 1400 ms (`REVEAL_ANIMATION_DURATION_MS` in `player-turn.reducer.ts`).

## 6.14. Disconnect Detection & Seat Takeover
- **Heartbeat (`useHeartbeat`, `game-board.heartbeat.hook.ts`)**: While a match is `playing`, each client whose local player is a human (not a bot) writes `GameState.heartbeats[seat] = Date.now()` immediately on start and then every **15 s** (`HEARTBEAT_INTERVAL_MS`). The write is `writeHeartbeat` in `services/game-board.engine.service.ts`: a single-field-path `updateDoc(ref, { 'heartbeats.<seat>': Date.now() })`, not a transaction, so it is never version-checked against the rest of the document and cannot collide with a concurrent whole-document `setDoc` (`saveGameState`, bot-turn completion). A failed heartbeat is logged to the console and retried on the next tick; it shows no toast.
- **Staleness Check (`useStalenessCheck`, `game-board.staleness.hook.ts`)**: While a match is `playing`, **every** connected client runs the check every **20 s** (`STALENESS_CHECK_INTERVAL_MS`) on the latest snapshot. Any seat that is not a bot, is not the client's own player, and has a `heartbeats[seat.id]` entry older than **45 s** (`STALE_THRESHOLD_MS`) is converted with `handlePlayerExit` (§6.12). A seat with no `heartbeats` entry yet (no heartbeat sent) is never converted by this check.
- **Detection Window:** A client that drops silently (closed tab, lost network, no `beforeunload`) is therefore converted to a bot between 45 s and 65 s after its last heartbeat, whichever check tick first sees it stale.
- **Connection Warning (`ConnectionWarningDialog`, `src/modules/game-board/components/ConnectionWarningDialog/`)**: A client-local, informational stage that runs before the takeover. It is rendered unconditionally by `GameDialogManager` and reads the local player's own `heartbeats` entry (`serverGameState.heartbeats[livePlayer.id] ?? null`) and `isBot`, looked up by `playerId` in the live, unbuffered `serverGameState` exposed on the game board context, and the match `status` from the display `gameState`. The local seat's heartbeat entry is never synced into the turn buffer (the In-Memory Turn Buffering bullet in §6.10), so reading it or `isBot` from the buffered `localPlayer` during the player's own turn would freeze the warning. It opens when the match is `playing`, the local seat is not a bot, the heartbeat entry is present and more than **25 s** old (`WARNING_THRESHOLD_MS`, `useConnectionWarning`, `ConnectionWarningDialog.hook.ts`). While open it shows an alert ("Connection lost") with a live "Taking over in m:ss" countdown to the **45 s** `STALE_THRESHOLD_MS` point, which turns destructive and pulses under 10 s remaining. The countdown ticks once per second. The dialog has one action, an "I'm back" button (`onDismiss` in `useConnectionWarning`). Pressing it calls `writeHeartbeat` directly, not `sendHeartbeat` (which swallows errors), and the button reads "Checking…" and is disabled while that write is in flight. The dialog never closes locally: it closes on the next render after the forced write lands and the `heartbeats` entry updates through the normal subscription. If the write fails, the button re-enables and a destructive "Still can't reach you" toast is shown, unless the dialog has already closed through another path (automatic recovery or takeover), in which case nothing is shown. Escape and overlay clicks still do not close it. The dialog closes on the next render after a fresh heartbeat lands (from the button or the automatic heartbeat) or the seat is no longer a playing human seat. A short synthesized tone (Web Audio oscillator, `playConnectionWarningTone`) plays once per hidden→open transition. It is never repeated while open, and it re-arms if the dialog closes and reopens. The warning adds no Firestore field and does not change when or how a seat converts; the takeover still happens only in the staleness check above. The countdown can read `0:00` while the seat is still human for up to one `STALENESS_CHECK_INTERVAL_MS` tick, because conversion is driven by whichever client's check runs first.
- **No Elected Driver for Conversion:** The staleness check does not depend on a single host or driver, because the driver can be the seat that went dark. Two clients converting the same seat is harmless: each conversion is a transaction, and an already-bot seat is a no-op (§6.12).
- **Converted Seats:** The takeover sets `isBot: true` and `isVacant: true` on the seat and deletes its `heartbeats` entry (`convertSeatToBot` in `src/modules/game-rules/services/player-exit.service.ts`), so a converted seat stops being checked and stops heartbeating.
- **Seat Reclaim (`handleSeatReclaim`, `src/modules/game-rules/services/player-reclaim.service.ts`)**: A player whose seat was converted can take it back. The call is one `runTransaction` that finds the caller's seat by `playerId` with `isVacant: true`. If there is none, it resolves `false` and writes nothing. If the seat is not the current player (`currentPlayerIndex`), it sets `isBot: false` and `isVacant: false` immediately. If it is that seat's turn, it sets `reclaimRequested: true` and the bot keeps the turn. Reclaim does not touch `heartbeats`, which stays absent for that seat until the reclaimed client's heartbeat starts when the board mounts.
- **Deferred Reclaim (`applyDeferredReclaim`, `src/modules/game-rules/player-turn.reducer.ts`)**: `handleEndTurn` applies a pending `reclaimRequested` to the outgoing player just before turn rotation, so the seat flips exactly when its bot turn ends, never mid-turn. It logs `<name> has reclaimed their seat.` Until then the seat stays vacant and bot-controlled.
- **Lobby Restriction (`subscribeToVacantSeat`, `src/modules/lobby/services/lobby.service.ts`; `RejoinMatchPanel`)**: While the signed-in player holds a vacant seat in a `playing` match, the lobby (`Lobby.tsx`) renders `RejoinMatchPanel` in place of the create/join UI. The open-rooms list is not rendered, and `CreateGameDialog` is forced closed (`open={isCreateDialogOpen && !vacantMatch}`). The panel's Resume button calls `handleSeatReclaim`: on `true` the lobby opens that match, on `false` or error it shows a "Could Not Rejoin" toast. A deferred reclaim also returns `true`, so the player enters the match while the bot still holds the current turn. The restriction lifts once the seat is no longer vacant.
- **Session Driver (`isSessionDriver`, `game-board.engine.hook.ts`)**: The single client that performs the bot-turn trigger and death-animation clearing is the one holding the lowest seat id among non-bot players. The returned `isHost` value (seat `0`) is unchanged for other consumers. The driver is not `isHost` because seat 0 can be a bot mid-match, and a host-gated effect would never fire once the host is the one who disconnected. These effects use a single driver because their Firestore writes are not transactional.
- **Scope:** Heartbeats and staleness checks run only while `status === 'playing'`. The pre-game lobby has no heartbeats and no takeover.
