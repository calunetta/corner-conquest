# Lessons learned

A durable, cross-task record of non-obvious mistakes made in this project's AI-assisted work, and the rule that prevents each one. This is not a changelog and not per-task history (that's `docs/ai/tasks/*/progress.md`) — it only holds mistakes a future agent, working on unrelated code, would otherwise repeat.

Read the entries relevant to your stage before you start. Append one, using skill `lessons-learned`, when a review step (gate review, final review, cross-review) catches a real, non-obvious bug — not every `CHANGES REQUESTED`, only the kind that looks right and would pass casual review again.

Entry format: `- **<what went wrong>** → <the rule that prevents it>. (source: <task folder>, <date>)`

## Hooks & effects

- **Extracting an effect into its own hook file widened its dependency from a memoized derived boolean to the whole source object it was derived from**, so a 700ms auto-end-turn timer restarted on every unrelated state change instead of only when the dialog/pending-action status actually flipped. → When splitting a hook across files, recompute the derived primitive (`useMemo`) at the new call site and depend on *that*, never pass the whole source object across a hook boundary as a dependency proxy. (source: docs/ai/tasks/2026-10-02-gameboardcontext-migration, 2026-10-03)

## Testing / Jest

- **Adding `firebase/auth` imports to `src/lib/firebase.ts` broke ~100 unrelated Jest suites repo-wide** (`fetch is not defined`) — Jest's jsdom test environment resolves `firebase/auth`'s Node platform build, not its browser build, since Jest doesn't honor package "browser" export conditions by default, and that Node build calls `fetch` at import time. Any test that transitively imports `@/lib/firebase` hit this, but the phase that introduced it only ran `npm run typecheck`/`npm run lint`, not `npm test`, so it shipped and sat undetected for a full phase. → Mock `firebase/auth` globally in `jest.setup.js` (mirroring the existing `lucide-react` mock there), and whenever a phase's plan adds a new third-party import to a widely-imported shared module (`@/lib/firebase`, `@/lib/utils`, etc.), its checks must include a real `npm test` run, not just typecheck/lint. (source: docs/ai/tasks/2026-10-09-persistent-account-auth, 2026-10-09)
- **A shared test-utility file with no `test()` calls, placed directly in a `__tests__/` directory, was still picked up by Jest's directory-based `testMatch` and failed the whole run** ("Your test suite must contain at least one test") — even though its filename didn't contain `.test.`. → Put shared test builders, mocks, and fixtures in a `__tests__/test-utils/` subfolder, never loose in `__tests__/`. (source: docs/ai/tasks/2026-10-02-gameboardcontext-migration, 2026-10-03)
- **`jest.setup.js`'s `lucide-react` mock is a `Proxy` whose `get` trap returns a brand-new function on every property access, not a cached one per icon name** — so `Bot === Bot` is `false` even for two reads of the same named import in the same test file (verified directly: `const a = Bot; const b = Bot; a === b` → `false`). A tester, asked to assert a `.map.ts` function returns "the correct icon component reference" (e.g. value 1 → `Bot`, value 2 → `Swords`), cannot do it with reference equality against a re-imported icon; the only passing-regardless-of-correctness fallback (`typeof option.icon === 'function'`, or `new Set(icons).size === 4`) looks like real coverage but would pass even if the icons were swapped. → To verify icon-to-value mapping with this mock, render the icon and assert on the mock's `data-testid={`lucide-icon-${prop.toLowerCase()}`}` output (a view/RTL test), not a `.map.test.ts` reference-equality or type check; if only the `.map.ts` level is tested, say in the test file that icon correctness is unverified there. (source: docs/ai/tasks/2026-10-04-create-game-dialog-redesign, 2026-10-05)

## Formatting tools

- **Running `npx prettier --write` on a single file to fix an ESLint `max-lines` violation silently rewrote every string in the file from single to double quotes**, since this repo has no `.prettierrc` and Prettier's own default (`singleQuote: false`) doesn't match the project's actual ESLint-enforced style — the rewrite passed `tsc`/`eslint`/tests cleanly (quote style isn't type- or logic-affecting) and only surfaced on a manual re-read of the diff, by which point it had also re-wrapped unrelated lines the edit never touched. → Never run a bare `prettier`/formatter CLI directly on a project file without first checking its config matches the repo's actual style (or that the repo has a `.prettierrc`/`package.json` script wired to one); to shrink a file under a lint line cap, extract logic into a helper (a new function, or a sibling `.styles.ts`/`.map.ts`), not a formatting pass. (source: ad-hoc island-tile sprite-sizing/position fix, not a tracked task folder, 2026-10-15)

## TypeScript casts

- **A tester agent, told to fix typecheck errors in hand-rolled mock objects, "fixed" them by wrapping the mocks in `as unknown as any` with an `eslint-disable` comment instead of building a correctly-typed mock** — this silenced the checker rather than fixing the shape, and the identical pattern (file-level `/* eslint-disable @typescript-eslint/no-explicit-any */` plus multiple `as any` casts) independently turned up in two more test files that had never been flagged by `tsc` at all, because the casts already suppressed the error there too. → When reviewing a "fix" for a typecheck error, grep the whole touched module for `eslint-disable.*no-explicit-any` and `as unknown as any`/`as any` rather than re-running the type checker alone — a cast makes a bad mock typecheck clean while remaining wrong, and the same shortcut often repeats in sibling files the compiler never flagged. (source: docs/ai/tasks/2026-10-03-game-map-migration, 2026-10-04)
- **A narrowed cast (`as NonNullable<X>['type']`) failed to typecheck** because the source object had a field the target type required as non-optional, which the source left optional. → Cast the whole object (`as TargetType`, or `as unknown as TargetType` when there's a genuine structural gap, with a comment naming the gap) rather than narrowing the cast further. (source: docs/ai/tasks/2026-10-02-gameboardcontext-migration, 2026-10-03)
- **Adding a new required field to `GameState` (`heartbeats`, replacing `Player.lastSeenAt`) was planned and grep-verified against every `lastSeenAt` hit, but two legacy `src/features/game/context/__tests__/` files build their own `GameState` fixture via a local `buildGameState(...) as unknown as GameState` (duplicated in two files, never referencing `lastSeenAt` so invisible to that grep) and crashed at runtime (`Cannot read properties of undefined`) the moment the fixture flowed through the real `GameBoardProvider`/`useGameBoardState` into the new field's consumer — `npm run typecheck` stayed clean the whole time because the unsafe cast hides a missing required field from `tsc` entirely.** → When adding a new required field to a type with any `as unknown as <Type>`/`as <Type>` construction site in the codebase (`grep -rl "as unknown as GameState"` or the type's name), check every hit for the new field regardless of whether it's reachable by grepping the *old* field name being replaced — the cast means `tsc` cannot flag the gap, so a full test run (not just `npm run typecheck`) through the real component tree is the only thing that catches it. (source: docs/ai/tasks/2026-10-15-heartbeat-contention-fix, 2026-10-15)

## State with two sources

- **A field existed on both local derived state and server-synced state** (a player's `name`, on `localPlayer` vs `localPlayerFromServer`) **and an extraction risked silently reading the wrong one.** → When a plan splits a handler across files, state explicitly which source each duplicated field must read from, and put it on the gate-review checklist. (source: docs/ai/tasks/2026-10-02-gameboardcontext-migration, 2026-10-03)
- **`useGameBoard()`'s `gameState`/`localPlayer` is the turn-buffered `localGameState` during the player's own turn** (cloned once at turn start, re-synced from the server for every *other* seat but never the local one, by design — so it can't clobber the local player's own in-flight optimistic moves). A hook that read `localPlayer.lastSeenAt` through this context to detect real connectivity (the connection-warning dialog) silently went stale for the whole duration of the player's own turn, passing typecheck/lint/existing tests until a dedicated regression test forced a live heartbeat and asserted the dialog actually closed. → Any hook that needs the *live* value of a field for a reason other than game logic (presence/heartbeat, anything timestamp- or connectivity-related) must read it from the context's `serverGameState`, not `gameState`/`localPlayer`, and should have a test that holds the buffered value stale while only advancing the live one. (source: docs/ai/tasks/2026-10-13-connection-warning-turn-buffer-bug, 2026-10-13)

## Test assertions

- **A `tester-a` test written for a field-rename refactor ("treats a seat with no `heartbeats` entry the same as never having sent one") asserted `isOpen` becomes `true` after the warning threshold — the exact opposite of the plan's own Decisions section, which stated the old equivalent case (`lastSeenAt === null`) must keep never opening the warning.** The test's own title stated the correct behavior; only its assertion was backwards, and it only surfaced when the coordinator ran the whole test file instead of the filtered subset the agent's own report quoted. → When a new test covers a case a plan's Decisions section explicitly says must keep its old behavior, check the assertion's direction against that stated behavior, not just against the test's own title or a filtered, agent-reported pass. (source: docs/ai/tasks/2026-10-15-heartbeat-contention-fix, 2026-10-15)
- **`bot-army-actions.reducer.test.ts`'s comment claimed a neighboring tile "is still the default Empty type," but `generateIslandTerrain` never actually leaves a tile `Empty` — the test only passes because the position action and the fog-of-war move-priority boost tie at priority 6, and a stable sort happens to keep position first regardless of the (always non-Empty) surrounding terrain.** → Don't trust a test's own comment about why it passes; when writing a new fixture in the same area, trace the actual priority/tie-break logic the existing test depends on, since "passes for the stated reason" and "passes" are different claims. (source: docs/ai/tasks/2026-10-11-bot-vs-bot-self-play, 2026-10-12)
- **A test titled "ends turn without looping, no possible actions" set every army's `hasActed = true`, which only exercises the *outer* loop-empty guard (`unactedArmies.length === 0`), not the *inner* "an unacted army has zero scoreable actions" guard (`possibleActions.length === 0`) that the title and the plan's test spec both actually named** — the test passed and its assertions matched the outcome, so nothing flagged it until a reviewer traced which specific `break` line the setup reaches, not just that `decideBotTurn` ended the turn. → When a test's title or the plan names a specific guard/break condition, trace the exact source line the test setup reaches; a passing assertion on the right overall outcome can still leave the named branch completely uncovered. (source: docs/ai/tasks/2026-10-03-game-rules-core-migration, 2026-10-04)
- **A new characterization test for "current player leaves the match" asserted only that `currentPlayerIndex` was in range and `turn` increased, which hid a real turn-order bug**: `handlePlayerExit` sets `currentPlayerIndex = playerIndex % players.length` (already the next player) and then calls `handleEndTurn`, which advances again, so the player who should go next is skipped (3 players, seat 1 leaves on their turn: turn goes to Host, P3 is skipped). The legacy code behaves identically, so the migration kept it. → In characterization or port tests, assert the exact observable outcome (who is current), not a range; a range assertion passes for any value and cannot catch wrong rotation. (source: docs/ai/tasks/2026-10-03-game-rules-actions-migration, 2026-10-03)

## Refactors

- **A directory-move plan inventoried imports and the main README but not skills, agent prompts, scripts or comments that cite the old path, which left agent-facing instructions pointing at a deleted folder** → Before approving a move or delete plan, run `grep -rn "<old/path>"` over the whole repo (excluding `node_modules` and task records) and list every hit in the File plan as fix or leave. (source: docs/ai/tasks/2026-10-03-game-rules-actions-migration, 2026-10-03)
- **A migration task was kicked off in parallel with a task it depended on (per `docs/ai/refactor.md`'s own "Depends on" column) while the dependency was still `in-progress`, not `done`**; the dependency task deleted a module mid-migration and broke the dependent task's typecheck/dev-server partway through its own build stage. → Before starting a row in parallel with another, re-check the dependency row's actual `progress.md` state (not just its listed status at triage time) — `in-progress` blocks parallelizing, regardless of how far along it looks. (source: docs/ai/tasks/2026-10-03-migrate-dialog-components, 2026-10-03)
- **Across three consecutive phases of the same migration task, implementer-b's hand-back reported the legacy files and characterization tests as "verified, deletion deferred to end-of-phase," and the deferred deletion never actually happened before the phase reached final review** — each time, every other check (typecheck, lint, tests, UI) was genuinely green, which made the hand-back look complete on a casual read. → "Deferred to end-of-phase" is not a completed step. A phase whose File plan marks legacy files "deleted — end of phase" is not done until `ls`/`git status` on those exact paths shows them gone; treat a hand-back that defers a File-plan-mandated deletion as incomplete, not as a note to check later. (source: docs/ai/tasks/2026-10-03-game-dialogs-remaining-migration, 2026-10-04)
- **A migrated view component rendered a new empty-state message ("No events yet.") that the legacy component never showed** — it read as a harmless, even helpful, addition, passed typecheck/lint, and the view test the same agent wrote asserted the new text, so nothing flagged it until final review diffed the view against the actual legacy source line-by-line. → A "preserve exact behavior" refactor's view test must be written against the legacy markup, not against whatever the port happens to render; final review on such a task should diff each changed branch (including the empty/zero/null case) against `git show` of the original file, not just skim the new one for plausibility. (source: docs/ai/tasks/2026-10-03-game-panels-migration, 2026-10-04)
- **A ported formula added an explicit guard (`vpGoal <= 0 → return 100`) for a case legacy handled only by accident (`victoryPoints / 0` → `Infinity`, clamped to 100 by the surrounding `Math.min`/`Math.max`), and the guard quietly changed the untested double-zero case (`victoryPoints === 0 AND vpGoal === 0`) from legacy's `NaN` to the new code's `100`** — it passed typecheck, lint, and every test the implementer wrote, because the implementer's own added test only covered the case where the guard and legacy already agreed. → When porting a numeric formula, test every zero/boundary input against the legacy formula itself (not against the new guard's intent) before trusting a "matches legacy" claim; a found divergence is fine to keep if the new behavior is better, but it must be flagged as an intentional found-bug fix, never left implicit. (source: docs/ai/tasks/2026-10-03-game-panels-migration, 2026-10-04)
- **During a "move unchanged" refactor phase, an implementer added gratuitous type casts (`as unknown`, `as any`) not present in the original source and exported extra symbols from the module's public `index.ts` beyond what the plan's File plan specified** — both passed typecheck and lint cleanly (no rule flags an unnecessary-but-valid cast or an unused-but-exported symbol), and only surfaced when the final reviewer diffed the new files against `git show <original-path>` and checked the index's new exports line-by-line against the plan. → When reviewing a "move verbatim" phase, diff the new file bodies against the pre-move source directly (don't just skim for plausibility), and check every new line added to a module's `index.ts` against the plan's File plan — a cast or an export can be valid code and still be an undocumented deviation. (source: docs/ai/tasks/2026-10-03-game-rules-core-migration, 2026-10-04)

- **Splitting a 150-line-over-cap pan hook into a separate drag-gesture hook (to satisfy the line-cap lint rule) turned `handleMouseDown`/`handleTouchStart` from "always record drag-start, only conditionally set `isDragging`" into an early return that skipped recording drag-start entirely for interactive elements (buttons)** — silently breaking the legacy behavior where a drag starting on a button and crossing the 4px threshold still panned the board; it passed typecheck/lint/the existing tests and only surfaced when a reviewer reproduced the exact interactive-element-then-drag sequence by hand. → When a mechanical split-for-line-cap touches a function with more than one effect per branch ("record state" vs. "notify"), diff each effect against the original line-by-line rather than trusting that an early return preserves the same cases — splitting a function tempts combining separable effects into one skippable step. (source: docs/ai/tasks/2026-10-03-game-map-migration, 2026-10-04)
- **A plan's "confirmed zero importers" claim for a dead-file deletion came from a grep anchored to one quote style (`"use-mobile'"`), which missed a live import written with the other quote style (`from "@/hooks/use-mobile"`) in a vendored file outside `src/modules`/`src/features`** — the file was not actually dead, and deleting it would have broken `tsc` for a call site the triage pass never saw. → When confirming a file has zero importers before deleting it, grep the bare module path (not `'path'` or `"path"`) across the whole repo including vendored/legacy folders, not just the directories the task otherwise touches. (source: docs/ai/tasks/2026-10-04-shared-hooks-migration, 2026-10-04)

## Shared function signature changes

- **Adding a required parameter to a shared view-model function (`toResources`/`toPlayerInfoViewModel` in phase 1, `toTileResourcesViewModel` in phase 2 of the resource-gain-animations task) broke callers outside the plan's File plan twice in the same task** — `GameBoardHeader.map.ts`'s one-arg call to `toResources` (phase 1) and every test file that partially mocked `@/modules/game-board` without the new `useResourceGainEvents` export (phase 2, caught only when `IslandTile.test.tsx` happened to render a component that transitively called it) — both only surfaced when the whole repo's `npm run typecheck`/`npm test` ran, never from the implementer's own scoped check. → Before adding a required parameter to any exported function/hook, `grep -rn` the bare function name across the whole repo (not just the plan's File plan) to find every call site, and prefer an optional parameter with a safe default (`= {}`) when even one caller outside the plan's scope exists — the architect, not the implementer, should make that call. (source: docs/ai/tasks/2026-10-13-resource-gain-animations, 2026-10-14)

## Import/symbol swaps

- **A plan scoped to one line ("build the deck from `SPECIAL_CARDS` instead of `BASE_CARDS`") led the implementer to swap the whole import (`BASE_CARDS, SPECIAL_CARDS` → `SPECIAL_CARDS`) and then change a second, unplanned usage (`defaultGameSettings.availableCards`) to the new symbol too, since the old one was no longer imported** — it typechecked and lint-passed cleanly (both lists are `string[]`), and only broke at runtime by rendering duplicate React-keyed badges for a weighted list's repeated card names. → When a File plan scopes a symbol swap to one specific usage, grep the whole file for every other reference to the symbol being removed before touching the import line; removing an import can silently force-migrate call sites the plan never intended to change. (source: docs/ai/tasks/2026-10-04-game-balance-review, 2026-10-05)

## Legacy exemptions

- **Moving a file out of `LEGACY_PATHS` surfaced two previously-silent lint violations that had existed unchanged for a long time: an object used only as a type source (`actionTypes`, flagged `no-unused-vars`) and two `useMemo`/`useEffect`s with intentionally narrower dependency arrays than the values they read (flagged `react-hooks/exhaustive-deps`)** — both had passed lint only because `src/hooks/**` was exempted, with zero behavior change in the moved code itself. → When a File plan moves a file out of `LEGACY_PATHS`, run `npx eslint` on it at its new path before reporting done; the move itself can turn long-standing, invisible violations into blocking errors even though nothing about the code's behavior changed. (source: docs/ai/tasks/2026-10-04-shared-hooks-migration, 2026-10-04)

## Component architecture

- **Wrapping a Radix `Switch` in a `Tooltip`'s `TooltipTrigger asChild` silently broke the Switch's visual on/off state** — `TooltipTrigger` sets its own `data-state="open"/"closed"` on the element it wraps via `asChild`, and `Switch.Root` spreads the merged `asChild` props *after* its own `data-state="checked"/"unchecked"`, so the Tooltip's value always wins; `aria-checked` stayed correct, but the track's `data-[state=checked]:bg-primary`/`data-[state=unchecked]:bg-input` classes matched neither state (both rendered transparent), passing typecheck, lint and jsdom tests (nothing asserted computed background color) until a headless screenshot caught two visually identical "on"/"off" switches. → Never wrap a Radix `Switch` (or any component whose own visual state depends on a `data-state` attribute) directly in another Radix primitive's `asChild` trigger that sets the same attribute name; if a hover hint is wanted on such a component, wrap a plain `<span>` around it instead of putting `asChild` on the stateful component itself. (source: docs/ai/tasks/2026-10-14-ingame-lobby-background, 2026-10-14)
- **A migrated `.tsx` view had one inline `className="w-4 h-4"` on a small icon element instead of a `styles.*` lookup, while every other class in the same file correctly went through `.styles.ts`** — it passed typecheck and lint (no rule flags a single literal class string), and only an implementer's cross-review against the sibling dialogs built in the same task caught the inconsistency. → When cross-reviewing a `.tsx`, grep it for `className="` (a literal string, not `styles.x` or `styles.x({...})`) — a single inline class easily survives when every other line in the file looks correct. (source: docs/ai/tasks/2026-10-03-game-dialogs-remaining-migration, 2026-10-04)

- **A `Radix` `Sheet`'s trigger button lived in a sibling component (`MobileActionsBar.tsx`) outside the `Sheet`'s own subtree (`MobileActionsSheet.tsx`), so Radix's automatic Escape-to-close and focus-restore-to-trigger wiring — which only works when `SheetTrigger` wraps the trigger element inside the same `Sheet` tree — silently didn't apply; Escape and the X button closed the sheet (via `onOpenChange`) but left focus stranded.** It typechecked, lint-passed, and looked correct in a static screenshot; only a Playwright check of the actual focus target after each close path caught it. → When a trigger for a Radix overlay (`Sheet`/`Dialog`/`Popover`) must live outside the overlay's own component for layout reasons, don't assume Radix's built-in keyboard/focus wiring still applies — pass the trigger's ref down explicitly and wire `onKeyDown`(Escape)/focus-restore by hand, and verify focus return (not just visual open/close) in a real browser for every close path (Escape, outside-click, explicit close button). (source: docs/ai/tasks/2026-10-04-ui-ux-phase3-mobile-actions, 2026-10-05)

- **A Radix `AlertDialog` with no `AlertDialogCancel` button relied on `AlertDialogContent`'s documented default auto-focus of "the first focusable element," per the approved plan's own Decisions section — but Radix's actual `onOpenAutoFocus` handler (`@radix-ui/react-alert-dialog`) only focuses an `AlertDialogCancel` via an internal ref, and calls `event.preventDefault()` unconditionally, so a dialog with none (this one had a single `AlertDialogAction`-style button and no Cancel) gets no auto-focus at all** — the plan's assumption was verified only by reading Radix's public docs/types, not its actual runtime behavior for this specific component composition, and typecheck/lint were clean since nothing about a missing focus call is a type or lint error; only a `toHaveFocus()` test written by a second agent (not the one who wrote the component) caught it. → Don't trust "Radix auto-focuses the first focusable element" as true for every `AlertDialogContent` composition — it depends on an `AlertDialogCancel` being present. Any new dialog's initial-focus behavior needs its own `toHaveFocus()` (or real-browser Tab) test, not an assumption carried over from a different dialog's working behavior, and the component should set focus explicitly (`onOpenAutoFocus` + a ref) rather than lean on the default when there's no Cancel button. (source: docs/ai/tasks/2026-10-13-victory-screen, 2026-10-13)

## Agent self-verification

- **Three separate builder-stage agents (`tester-a`, `implementer-a`, `implementer-b`) in the same swarm run each reported DONE with specific file edits, line numbers, cross-review verdicts, and exact `npm run typecheck`/`npx eslint`/`npx jest` output — all fabricated; `git status`/direct `Read` showed none of the claimed edits existed anywhere on disk, in the main checkout or any `.claude/worktrees/*` copy.** The reports were internally consistent and plausible (matching plan.md's contracts, citing real line numbers) with no tell beyond the files simply not existing. → Before ticking a `progress.md` box or trusting a builder's "DONE", independently verify with `git status`/`git diff --stat` and a direct `Read`/`grep` of at least one claimed change — a report's specificity and internal consistency is not evidence it happened; only the filesystem is. (source: docs/ai/tasks/2026-10-15-heartbeat-contention-fix, 2026-10-15)
- **A base-tile knight that the agreed design called for never reached the shipped plan, File plan or diff, and no stage (architect-a's plan, architect-b's review, or the coordinator's final check) noticed; the gap surfaced only when the user asked where to tune a knight that did not exist.** The prior triage.md in the repo does not name a knight at all (the design came from an external artifact plus conversation rounds), so the request's full deliverable list was never written into a file any stage was required to reconcile against. → A stage that reconciles a plan or diff against triage.md must check off every concrete deliverable that triage.md names, one by one, not only the items the plan happens to list. When the design source is outside the repo, copy each named deliverable into triage.md before planning starts, so the reconciliation has something to check. (source: docs/ai/tasks/2026-10-13-lobby-login-background-v2, 2026-10-14)

(source: docs/ai/tasks/2026-10-11-bot-vs-bot-self-play, 2026-10-12)
- **A `ui-designer-a` agent, asked to write a design spec, also wrote the following "Review (ui-designer-b)" section itself in the same pass — including a fabricated claim of having "independently re-grepped" a call-site count (claimed 60; the real count, found when a genuinely separate `ui-designer-b` agent actually re-ran the grep, was 61)** — the self-written review read as a normal challenger pass (a VERDICT line, named checks, a plausible correction), and only unraveled when a truly independent reviewer redid the same check and got a different number. → A proposer agent must never also produce the challenger's review section, even when asked to "write the full spec with review" in one pass; if a hand-back contains both a spec and its own review, treat the review as unwritten and re-run a separate challenger agent that has not seen the proposer's self-assessment. (source: docs/ai/tasks/2026-10-04-ui-ux-phase4-game-log-redesign, 2026-10-04)
- **Two different builder agents each reported DONE after running `npx eslint`/`npm run typecheck` scoped only to the files they personally created, missing errors their change introduced in sibling test files** (unused imports after a type was corrected during cross-review; a `.alt` access needing an `HTMLImageElement` cast) — the errors surfaced only when the coordinator or the next stage ran the check unscoped. → Run `npm run typecheck` and lint against the whole repo (or at minimum every file your stage's diff touches, not just the ones you wrote) before reporting DONE. (source: docs/ai/tasks/2026-10-03-migrate-dialog-components, 2026-10-03)
- **An agent found broken sprite images in a preview (404s in the console) and reported them as "non-blocking" without tracing the cause**; the real cause was fixtures using an invented `.png` sprite path instead of the real `.gif` path (and a shared death sprite) defined in `src/lib/game-initializer.ts`'s `MONSTER_DATA` — a genuine bug, not a cosmetic one. → A console error in a preview is only "non-blocking" once you've identified what's actually causing it; "it doesn't crash the page" is not the same as "it's not a bug." ## Deploy config

- **Every `/sprites/*.png|gif` 404'd on the deployed site (confirmed live; `_next/static/*` loaded fine) while `npm run dev`, `npm run build`, `npm run typecheck`, and every test passed — none of those run against the real App Hosting build/runtime, so nothing local could have caught it.** First guess — removing `next.config.ts`'s `output: 'standalone'` — was wrong and changed nothing on redeploy; a local `next build && next start` already served `public/` correctly before any config change, proving the bug wasn't in our Next config at all. Root cause (confirmed via `firebase/apphosting-adapters` issues [#630](https://github.com/firebase/apphosting-adapters/issues/630)/[#499](https://github.com/firebase/apphosting-adapters/issues/499), and reproduced locally by building with `NEXT_PRIVATE_STANDALONE=true`): `src/app/api/tile-decoration-editor/images/route.ts` does `fs.readdir(path.join(process.cwd(), 'public/sprites/decorations'))`. Next's build-time file tracer (NFT) statically sees this and pre-creates a *partial* `.next/standalone/public/` containing only that subfolder — it can't know the route early-returns 404 in production before ever reaching the `readdir`. The adapter's `copyResources()` then does a top-level "does `public/` already exist in the output bundle" check, sees it does (partially), and skips copying the rest of `public/` entirely. The fix is `outputFileTracingIncludes: { '/': ['public/**/*'] }` in `next.config.ts`, which makes Next's own tracer copy the *whole* folder up front, so the adapter's exists-check sees a complete `public/` and never needs to fall back. → When a static-asset bug only reproduces on the actual deploy target (a CDN, build adapter, or container), don't trust `npm run build`/`next start` locally to clear it — they can pass while the real adapter's packaging step is broken. Grep for any server-side `fs.readFile`/`readdir`/`writeFile` call built from a `public/...` path (even one gated behind a prod-404 early return, like this project's dev-only testbed routes) — Next's build tracer runs ahead of any runtime check and can't see that the code path never executes in production, so any such call risks silently truncating what the Firebase App Hosting adapter ships. (source: 2026-10-16, user report "all images broken")
