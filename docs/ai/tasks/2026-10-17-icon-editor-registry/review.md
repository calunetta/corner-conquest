## Adjudicating the four flagged deviations

1a. **New file `IconEditorField.tsx`, not in plan's File plan.** Accept as-is. `IconEditor.tsx` (90 lines), `IconEditorRow.tsx` (122 lines) and `IconEditorField.tsx` (75 lines) are each under the 150-line lint limit; the split is by responsibility (row chrome vs. the slider+input field pairing), not arbitrary, and doesn't cross an import boundary. A reasonable, correctly-scoped addition; not worth a plan amendment.

1b. **Raw `@radix-ui/react-slider` instead of the vendored `src/components/ui/slider.tsx`.** Accept as-is for this phase, with a cleanup recommendation. Verified the claim: `slider.tsx:11-24` spreads `{...props}` only onto `SliderPrimitive.Root`, never onto `Thumb` (the element with `role="slider"`), so `<Slider aria-label="...">` would silently mislabel the wrong node — confirmed by reading the file. Bypassing it was the only way to label the `Thumb` directly, and `IconEditorField.tsx:20-36`'s `IconSlider` does so correctly (verified via `IconEditor.test.tsx:111-112,132`'s `aria-valuenow` assertions passing). Cost: `Track`/`Range`/`Thumb` markup and classes are now duplicated between two files and will silently drift if `slider.tsx`'s design changes. Better fix, not required for this phase: extend the vendored `Slider` to forward an optional label prop to `Thumb` (e.g. `thumbLabel?: string`) instead of duplicating it — this benefits every future accessible-slider use, not just this one. Recommend a follow-up cleanup task; not blocking since the current code works and is tested.

1c. **Number inputs apply on every keystroke instead of on blur — BLOCKING, not just a spec deviation.** Reproduced the failure mode directly (not just "doesn't crash"): `IconEditorField.tsx`'s `Input onChange` calls `onValueChange(Number(event.target.value))` on every keystroke, and the hook's `onSizeChange`/`onRotationChange` clamp immediately (`IconEditor.hook.ts:41-46`, `clampSize` min 25). I rendered `IconField` standalone and simulated a developer clearing the Size field to type a new value: clearing sets the input to `''` → `Number('') === 0` → `clampSize(0) === 25` → the controlled value snaps back to `25` before the next keystroke lands. Typing further digits then appends to the committed `"25"` rather than replacing it (e.g. typing `1` after clearing produces `251`, clamped to `200`), and every subsequent keystroke re-clamps to `200` — the developer is now stuck at the maximum and cannot type `150` at all by clearing and retyping. This is exactly the bug `ui-design.md`'s "clamps on blur" line exists to prevent, and it breaks the single most ordinary way to edit a number input (select/clear, then type). Owner: implementer-b, `IconEditorField.tsx`. Fix: keep a local, uncommitted string/number state for the `Input` while focused, and only call `onValueChange` (which clamps) `onBlur`; the paired `Slider` can keep committing immediately as it already does, since dragging never produces an out-of-range intermediate value. Not required: reproducing the exact "live preview while typing" nuance from the Interactions section — committing on blur without breaking the slider's live link satisfies the plan's acceptance criteria.

   Also flagged in point 1: unknown lucide names render nothing (`IconEditorRow.tsx:29-31`, `IconGlyph` returns `null` when the name isn't found). Accept as-is: defensive-but-harmless, and Phase 1's review independently re-verified all 56 registry names exist in the installed `lucide-react` version, so this path can't currently be hit by real data.

2. **Preview renders pure `IconEditorView` with local `useState`, not the connected `IconEditor`.** Accept as-is; this is the more correct choice, not a deviation to overrule. `component-architecture`'s own "Pure view, connected component" rule states previews use `NameView` with fixtures precisely because a connected component's hook reads app state — here `useIconEditor` statically imports the real `iconRegistry`/`iconOverridesConfig` singletons and calls the real service on mount, none of which `jest.mock`-style swapping reaches in an actual rendered testbed page (that technique only works inside Jest). The plan's own fallback text ("mocks the service instead") assumed a swap that isn't achievable here without dependency injection the hook doesn't have; preview-a's actual approach (local state wired through the real, shared pure functions `toModuleGroups`/`clampRotation`/`clampSize` from `IconEditor.map.ts`, not reimplemented) is the right adaptation and is documented in the preview file's own comment as the plan required. No fix needed.

3. **Reset/Overridden badge both visible after a pre-save Reset click; only "Editor" state visually checked.** Accept as-is, both parts. The coexistence is the direct, correct consequence of `plan.md`'s own Decisions ("`hasSavedOverride(id) = id in savedOverrides`"): clicking Reset only clears `draftOverrides[id]`, so `hasSavedOverride` (derived from `savedOverrides`) correctly stays true until Save actually persists the removal, while `isDirty` correctly turns true because the draft now differs from the saved state. Confirmed visually in `icon-editor-interact-after-reset.png`: the "Info" row shows "Overridden" + "Unsaved changes" + a Reset button together, which accurately tells the developer "still saved on disk, and you have a pending change." Not a bug; the plan's own architecture produces this intentionally, and it's not confusing information. The single-"Editor"-state preview is exactly what `plan.md`'s Preview states section specifies (`plan.md:360-361`); no additional state was ever required.

4. **`docs/README.md`'s index doesn't list §6.15.** Defer to a future task, as flagged by docs-sync. Verified: `docs/README.md:31`'s systems-and-visuals.md index entry stops at "§6.14" and never mentions §6.15 at all, confirming this predates this task (§6.15 was added by the earlier TileVariantEditor work, per docs-sync's own note).
