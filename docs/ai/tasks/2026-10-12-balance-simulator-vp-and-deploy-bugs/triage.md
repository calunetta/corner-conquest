## Why this tier
- Root cause for both bugs already verified in this session (not just hypothesized) — handing architect-a the pointers below so it doesn't re-derive them:

**Bug 1 — M5 VP-integrity breach fires in every config (3 to 31 mismatches per config on a 30-game-per-config run).**
Confirmed root cause: `scripts/balance-simulator/engine.ts:103,117` attributes every `LogEvent` produced during a turn to `turn.seat = actingSeat` (`state.currentPlayerIndex`, the player whose turn it is). `scripts/balance-simulator/metrics/victory-point-sources.ts:50-52` then credits `pvpVictoryPoints` events to that same `turn.seat` unconditionally. But in PvP combat, the VP winner is not always the acting seat: `src/modules/game-rules/combat-player-resolve.reducer.ts:16-20,32,72` resolves `winner`/`loser` from dice, and the **defender** can win and receive the 5 VP (`winner.victoryPoints += COMBAT_WIN_VICTORY_POINTS`) even though the **attacker** is the one whose turn it is and who dispatched `InitiateCombat`. The log line itself already carries the right attribution (`playerId: winner.playerId` at `combat-player-resolve.reducer.ts:36,76`) — the simulator's metrics layer just never reads it, crediting the acting seat instead. When the defender wins, the attacker's `perMatchVP` gets +5 they never actually received → sum exceeds their real final VP (the flagged overcount); the defender's real +5 is never added to their own sum (an undercount, which `computeM5`'s check at `victory-point-sources.ts:64` doesn't flag, by design — only overcounts are breaches).
Verified NOT the cause: monster combat (`combat-monster-resolve.reducer.ts:19,23,25` — `attacker` is always `state.players[attackerId]`, same seat that initiated it, so `monsterWin` attribution is correct) and island discovery (`island-discovery.reducer.ts:7,19` — VP always goes to `state.players[state.currentPlayerIndex]`, i.e. the acting seat, so `discoveryVP` attribution is correct too). The bug is isolated to `pvpVictoryPoints`.
This is a bug in the balance-simulator's own metrics/log-parsing layer (`scripts/balance-simulator/`), not in `src/modules/game-rules`'s actual VP-awarding code, which is correct. A fix needs the winner's seat threaded through, e.g. `LogEvent`'s `pvpVictoryPoints` case carrying the winner's player name (parseable from the exact log string `combat-player-resolve.reducer.ts:35,75` already pushes: `` `${winner.name} receives 5 VP for defeating ${loser.name}!` ``) and `victory-point-sources.ts` resolving that name to a seat index via the match's `finalState`/player list, instead of assuming `turn.seat`. Left to architect-a to design the exact mechanism (name→seat lookup already exists as a pattern elsewhere in `log-parsers.ts`/`engine.ts` — check before inventing a new one).

**Bug 2 — bot attempts an unaffordable Deploy ("Not enough food. Cost: 12"), confirmed reproducible, current paths (the guide's own paths are stale — see Bug 3).**
`src/modules/game-rules/player-actions.reducer.ts:21,23,26` (`handleDeployAction`) only applies the Reinforce (free) or Efficient (half-cost) discount when `canUseCard = !player.actionsThisTurn.includes(GameAction.UseCard)` is still true — i.e. the player hasn't already spent their one card-use action this turn. `src/modules/game-rules/bot-purchases.reducer.ts:30-33` computes the bot's own affordability pre-check from `activeBot.efficientActive`/`activeBot.reinforceActive` directly, with no `canUseCard` gate, so once a bot has used a card earlier in the same turn, it still believes the discount applies, proposes a Deploy it can't actually afford, and the reducer correctly rejects it (caught by phase 1's anomaly capture, not a crash). Fix: `bot-purchases.reducer.ts`'s deploy-cost pre-check needs the same `canUseCard` gate `handleDeployAction` uses.
