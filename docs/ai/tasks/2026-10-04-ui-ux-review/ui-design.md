## Current state audit

### 1. Login/Lobby animated background never renders (bug, file-referenced)
- **Evidence:** `test-results/ui-verify/home--desktop.png` (live `/` route, logged out) shows a flat navy card on a flat navy background — none of `LobbyBackground`'s gradient glows, floating islands or boats are visible, even though `Login.tsx:31` renders `<LobbyBackground />` and `docs/README.md` §2 calls out Login/Lobby visual parity as a hard rule.
- **Root cause:** `LobbyBackground.styles.ts:1` sets `root: 'fixed inset-0 -z-10 ...'`. A `position:fixed` element with negative `z-index` paints **below** any sibling that is itself positioned (even with `z-index:auto`), per CSS stacking rules. Every consumer wraps it in a sibling that is itself positioned and carries its own opaque background:
  - `Login.styles.ts` root (verified `Login.tsx:30` renders `<div className={styles.root}><LobbyBackground/>...`) — need to confirm `root`'s position value, but the rendered screenshot proves the paint order problem regardless of the exact class.
  - `src/app/page.tsx:20`: `<div className="relative flex h-screen w-screen ... bg-gradient-to-br from-background via-indigo-950/20 to-background ...">` — `position:relative` (positioned) with an opaque gradient background, sibling-order after `LobbyBackground` is irrelevant once it's positioned and opaque; it paints over the `-z-10` fixed layer.
  - Testbed confirms the same effect in isolation: `test-results/ui-verify/testbed-lobby-background-state-Default--desktop.png` renders a totally empty dashed preview frame for the `Default` state of the `LobbyBackground` preview itself.
- **Why it matters:** The dark-navy-only look is not the intended theme — `docs/README.md` explicitly mandates the animated diorama for both Login and Lobby, and the whole "island conquest" visual identity (floating islands, boats, bioluminescent glows) is completely invisible to every player, every session. This is the single biggest gap between the intended visual language and what ships.
- **Proposed fix direction:** Change `LobbyBackground.styles.ts:1` root to a non-negative stacking approach: drop `-z-10` and instead give it `z-0` while giving the sibling content wrapper (e.g. `Login.styles.ts` root, `page.tsx`'s wrapper div) `z-10` and a transparent (not gradient-opaque) background, or render `LobbyBackground` as the first child of a `position:relative` parent with `z-index:0` and put content in a `z-10` child — the pattern the map/HUD layering already uses (`z-20`/`z-30` per `ui-design` skill). Needs re-verification in both Login and Lobby after the fix.
- **Size:** Medium — one shared root-cause fix, but must be re-verified on both Login (`src/modules/session/components/Login`) and the in-game Lobby (`src/modules/lobby/components/Lobby`), plus the `lobby-background` testbed preview.
- **Screens touched:** Login, Lobby.

### 2. Island border sprite causes a hydration mismatch on every map render (bug)
- **Evidence:** `node .claude/skills/ui-verify/scripts/snapshot.mjs "http://localhost:9002/testbed/map-grid?state=Populated%20board"` FAILs with a React hydration-mismatch console error; the diffed DOM shows server rendered `src="/sprites/island_edge_1.gif"` vs. client `src="/sprites/island_edge_2.gif"` for the same tile. The testbed itself surfaces this as a red "1 Issue" badge in `test-results/ui-verify/testbed-map-grid-state-Populated-20board--mobile.png`.
- **Root cause:** `src/modules/map/components/IslandTile/IslandTile.hook.ts:28-31`:
  ```ts
  const borderImageSequence = useMemo((): [string, string, string] => {
    const middleImage = BORDER_IMAGES[Math.floor(Math.random() * BORDER_IMAGES.length)];
    return [BORDER_IMAGES[0], middleImage, BORDER_IMAGES[1]];
  }, []);
  ```
  `Math.random()` runs once during SSR and again during client hydration; `useMemo` does not persist a value across the server/client boundary, so the two renders disagree and React logs a hydration-mismatch error for every tile in a populated map, on every full page load.
- **Why it matters:** This is a genuine, reproducible console error (not cosmetic) on the single most-used screen (the main game board), on every match load. React explicitly states "this won't be patched up" — the visible flicker/wrong sprite is possible, and it signals a real SSR/CSR divergence that could mask or compound other hydration bugs later.
- **Proposed fix direction:** Derive the "random" middle border image deterministically from `island.id`/`island.x,y` (e.g. a cheap hash into `BORDER_IMAGES`) instead of `Math.random()`, so server and client agree. Alternatively, pick the image in a client-only effect (`useEffect` + state, defaulting to a fixed image for SSR) — the hash approach is simpler and avoids a flash of the wrong sprite.
- **Size:** Small — one function, one file (`src/modules/map/components/IslandTile/IslandTile.hook.ts`), existing test at `IslandTile.hook.test.ts:204-232` already exercises `borderImageSequence` and should be updated.
- **Screens touched:** Main game board / map.

### 3. Mobile: Actions panel sits below the map and player bar, requiring a scroll every turn (UX)
- **Evidence:** `src/features/game/components/GameBoard.tsx:24-65` — the layout is `flex flex-col lg:flex-row`: on mobile the DOM/visual order is header → `PlayerInfoBar` → map (`main`, `min-h-[420px]`) → `aside` (`ActionsPanel` + `GameLog`). `ActionsPanel`'s own mobile screenshot (`test-results/ui-verify/testbed-hud-actions-panel-state-Army-20selected-2C-20can-20attack--mobile.png`) shows a tall, non-collapsible block (header, Deselect/End Turn row, 6 action buttons) that, combined with the header and a ≥420px-tall map above it, pushes the actual turn controls (Attack, Deploy, End Turn) off the first 844px-tall mobile viewport.
- **Why it matters:** Corner Conquest is turn-based and the primary mobile loop (select army → act → End Turn) requires reaching these controls every turn; `PlayerInfoBar` already collapses by default on mobile (`src/features/game/components/PlayerInfoBar.tsx:12-16`, `isPlayerInfoOpen` defaults to `!isMobile`) showing the team already recognizes the problem for the player list, but `ActionsPanel` got no equivalent mobile treatment. This does not violate the "map grid stays visible" rule literally (the grid itself isn't clipped), but it adds a scroll-to-act step to every single mobile turn, which is real friction a new player will hit immediately.
- **Proposed fix direction:** Either (a) make the actions bar sticky/anchored at the bottom of the viewport on mobile (a persistent bottom action bar, common mobile game pattern), or (b) collapse `ActionsPanel` to a compact summary row by default on mobile (mirroring `PlayerInfoBar`'s collapsible pattern) that expands on army selection. Needs its own design spec — this is a layout/interaction change, not a token tweak.
- **Size:** Large — touches `GameBoard.tsx` layout, `ActionsPanel` (`src/modules/hud/components/ActionsPanel/`), likely needs a new sticky/collapsed state and mobile-specific interaction design.
- **Screens touched:** Main game board (mobile only).

### 4. Icon-only zoom controls have no accessible name (accessibility)
- **Evidence:** `src/modules/map/components/MapZoomControls/MapZoomControls.tsx:21-34` — the zoom-out button renders only a `<ZoomOut>` icon inside a `Button`, with no `aria-label`; its only text is a Radix `Tooltip` (`<TooltipContent><p>Zoom Out</p></TooltipContent>`), which sets `aria-describedby`, not an accessible name. Same pattern for zoom-in (not shown above but same file, same construction). The reset button is fine because it has visible text (`{percentage}%`).
- **Why it matters:** This is exactly the "known gap" flagged in the `ui-design` skill ("legacy icon buttons rely on tooltips only"). Screen reader users get an unlabeled button for Zoom Out/Zoom In.
- **Proposed fix direction:** Add `aria-label="Zoom out"` / `aria-label="Zoom in"` to the two icon-only buttons in `MapZoomControls.tsx`. Trivial, no visual change.
- **Size:** Small — one file, two attributes, plus a sweep for the same pattern elsewhere (not exhaustively audited beyond this component in this pass; worth a dedicated grep for `size="icon"` buttons without `aria-label` across `src/modules`).
- **Screens touched:** Main game board (map zoom controls); likely other icon-only buttons project-wide, unverified beyond `MapZoomControls`.

### 5. "Deck: N" label in the Actions panel is ambiguous (copy)
- **Evidence:** `src/modules/hud/components/ActionsPanel/ActionsPanel.tsx:44`: `<div className={styles.deckCount}>Deck: {deckCount}</div>`, shown top-right of the Actions card (see `test-results/ui-verify/testbed-hud-actions-panel-state-Army-20selected-2C-20can-20attack--desktop.png`).
- **Why it matters:** "Deck" is never introduced anywhere else in the visible HUD; a new player has no way to tell this is the shared special-card draw pile size (per `docs/README.md` §5.3, special cards come from a shared deck) versus, say, their own hand size (which is shown separately a row below as "Cards (2/7)"). Two numeric "card" labels sitting in the same small panel with no distinguishing copy is confusing mid-turn.
- **Proposed fix direction:** Rename to something explicit, e.g. "Cards left in deck: 18" or add a tooltip/beacon explaining it. Smallest fix: change the string in `ActionsPanel.tsx:44` (and update `ActionsPanel.test.tsx:34`'s regex accordingly).
- **Size:** Small — copy-only change, one component, one test assertion to update.
- **Screens touched:** Main game board (Actions panel).

### 6. Resource/army stat chips in Player info are icon+number only, no text label (minor accessibility/clarity)
- **Evidence:** `test-results/ui-verify/testbed-hud-player-info-state-Current-20player-20with-20buffs--desktop.png` — the three chips under the VP bar read `[sword icon] 2/5 ⚓1`, `[lightning icon] +2 AP`, `[card icon] 2/3` with no text labels, relying entirely on icon shape + sprite art to convey "armies deployed / army cap", "attack power buff", "cards in hand". The three resource rows below (`🍖 15`, `🪵 8`, `🪙 10`) have the same pattern.
- **Why it matters:** Icons differ in shape (not just color), so this is not a pure "color alone" violation, but a new player has no textual anchor for what `2/5` or `+2 AP` means without hovering/tapping (unverified whether these have tooltips — not confirmed in this pass). This is the densest, most ambiguous part of the HUD for a first-time player.
- **Proposed fix direction:** Confirm whether tooltips already exist (check `PlayerInfo` sub-components); if not, add them, or add a one-time tutorial beacon (the project already uses `TutorialBeacon` for exactly this purpose elsewhere, e.g. `GameBoard.tsx:36-44`'s "map-info" beacon and `PlayerInfoBar.tsx`'s "player-info" beacon — `PlayerInfo` itself doesn't appear to have one).
- **Size:** Small/Medium depending on whether tooltips already exist — needs a quick source check of `src/modules/hud/components/PlayerInfo/` before sizing further.
- **Screens touched:** Player info bar (desktop and mobile).

### 7. Game log entries are undifferentiated gray text (minor polish)
- **Evidence:** `test-results/ui-verify/testbed-hud-game-log-state-With-20entries--desktop.png` — every log line ("Player Red upgraded...", "Player Blue deployed...") renders in the same muted gray, same weight, no per-player color accent even though the game has a defined `PlayerColor` palette (blue/red/purple/yellow, per the `ui-design` skill) used everywhere else (player badges, combat dialog names in `test-results/ui-verify/testbed-combat-combat-dialog-state-Results-20-E2-80-94-20attacker-20wins--desktop.png`, where "Alice"/"Bob" are colored blue/red).
- **Why it matters:** Scanning the event log to find "what did my opponent just do" is slower without the same color coding the rest of the UI uses. Minor relative to the other findings, but cheap to fix and consistent with the existing pattern (Combat Dialog already colors player names).
- **Proposed fix direction:** Color the player-name token at the start of each log line with that player's `PlayerColor` token, same approach as Combat Dialog.
- **Size:** Small — `GameLog` component and whatever already extracts player color from name/id.
- **Screens touched:** Game log panel (desktop and mobile).

### Verification method
Read every cited file. For findings 1 and 2 (the two bug claims) I also ran the app locally (`npm run dev`, port 9002), re-captured `node .claude/skills/ui-verify/scripts/snapshot.mjs "http://localhost:9002/"`, and wrote two throwaway Playwright probe scripts to read computed styles and sample rendered pixel colors directly — not just compare screenshots by eye.

### Finding 1 — Login/Lobby background not rendering: confirmed, root cause is more precise than stated
- The screenshot claim is correct and reproducible. I re-ran the snapshot and additionally sampled 12 pixels across `home--desktop.png` (corners, edges, center) with Pillow: every single sample returned exactly `(9, 11, 21)` — the raw `--background` token color, with zero variation anywhere, including the corners where `LobbyBackground`'s cyan glow (`-top-32 -left-32`, 550px, blur-140px) and the `blue-citadel` island (`top-[6%] left-[3%]`) should visibly tint the pixels even at low opacity. This rules out "just too subtle to see" — it is not painting at all.
- I then probed computed styles via Playwright `page.evaluate`: `LobbyBackground`'s root div is present, `position: fixed`, `z-index: -10`, `opacity: 1`, correctly sized to the full 1280×720 viewport, with 16 children. Every child (gradient, four glow blobs, water pattern, 7 islands, 2 boats, fog overlay) has a correctly computed `background-color`/`background-image` (e.g. the cyan glow computes to `rgba(6, 182, 212, 0.15)`, the radial gradient computes to a real `radial-gradient(...)`). Nothing is `display:none`, `visibility:hidden`, or `opacity:0`. So this is not a missing-asset or broken-Tailwind-class problem — the DOM and CSS are correct in isolation, and the element still fails to paint.
- **Correction to the stated root cause:** the "Why it matters"/root-cause section cites `src/app/page.tsx:20`'s opaque gradient wrapper as part of what covers `LobbyBackground`. That does not apply to the Login path: `src/app/page.tsx:12-14` early-returns `<Login />` before that wrapper div ever renders when the player is logged out (confirmed by reading `page.tsx`). `page.tsx`'s wrapper is real and may contribute to the same bug on the in-game Lobby path (post-login), but citing it as the cause for the Login screenshot specifically is wrong — the Login screenshot proves the bug exists with `page.tsx`'s div entirely absent from the tree, which means `-z-10` + `position: fixed` inside a non-stacking-context ancestor (`Login.styles.ts:2`'s `root: 'relative ... overflow-hidden'` — `position: relative` with `z-index: auto` does **not** establish a new stacking context) is sufficient on its own to cause this, in both Login and Lobby.
- The proposed fix direction (drop `-z-10`, use `z-0` on the background and give the content wrapper an explicit `z-10` positioned ancestor, mirroring the map/HUD `z-20`/`z-30` layering pattern) is correct and is exactly the standard fix for this exact gotcha — negative z-index on a fixed/absolute full-bleed background is a known foot-gun precisely because it depends on an ancestor establishing a stacking context, which callers of `LobbyBackground` do not reliably do.
- Size: Medium is right — same root cause, two call sites to re-verify (Login, Lobby) plus the testbed preview.
- Net: finding stands, severity and size unchanged. Fix the root-cause text to drop the `page.tsx:20` citation for the Login case (or scope it explicitly to "Lobby path only") before this goes to an architect, so the architect doesn't waste a phase chasing an irrelevant file for the Login fix.

### Finding 7 — game log color-coding: confirmed as a real gap, but the size is understated
- `src/modules/hud/components/GameLog/GameLog.tsx:19-23` renders `entries.map((entry, index) => <p>{entry}</p>)` — confirmed uniform styling, no per-entry structure.
- Checked the data path the finding didn't: `GameLog.types.ts:1-3` — `GameLogViewModel.entries: string[]`; `GameLog.map.ts:1-3` — `toGameLogEntries(logs: string[]): string[]` just reverses the array. **The log entries arrive as plain, already-formatted strings** (e.g. "Player Red upgraded..."), not structured `{ playerId, message }` objects. There is no player-color metadata anywhere in this pipeline to key off.

Both are reasonable, but (b) is the only robust option and it crosses a module boundary this review didn't audit.
- Size correction: **Small → Medium.** Flag for the architect: this needs a `game-rules` change, not just a `hud` component change, so it is not a pure view-layer polish item the way finding 5's copy change is.

### Design inspiration
Added per explicit user request: concrete UI patterns from comparable games, each mapped to a specific Corner Conquest screen/component and labeled as a token-level tweak (small change inside existing primitives) or a structural change (new layout/interaction, its own spec). These are directions for a future design pass, not part of the prioritized backlog above — do not fold them into findings 1–7's sizing.

- **Colonist.io (Catan, mobile-first 2026 direction).** Clean bottom navigation, vibrant board as the hero element, minimal home-screen chrome, fewer taps to get into a game. Applies to: (a) the Lobby's room list / "Create Game" flow (`src/modules/lobby/components/Lobby`) — audit whether creating or joining a game takes more taps than Colonist's flow; **structural**, needs its own flow audit, not scoped here. (b) Reinforces finding 3: a persistent bottom action bar on mobile is exactly Colonist's pattern for keeping primary actions reachable without scrolling — this is a concrete precedent for the "sticky bottom bar" option already listed as a fix direction for finding 3, not a new idea on top of it.
- **Age of Empires (Definitive Editions).** Resource bar fixed at the top of the screen; a minimap anchored bottom-right; HUD elements that show or hide based on what's currently selected (unit/building stats consolidated into one panel instead of scattered). Applies to: (a) `PlayerInfoBar`'s resource rows (`🍖`/`🪵`/`🪙`) — already top-of-layout on desktop, so this is largely **validation that the existing placement is right**, not a change. (b) The "stat-block panel instead of scattered" idea is a stronger version of finding 6: instead of just labeling the existing icon+number chips, a future pass could consolidate `PlayerInfo`'s army/buff/card chips into one explicit labeled block the way AoE consolidates unit stats — **structural**, worth a follow-up spec if finding 6's tooltip fix turns out insufficient in practice. (c) AoE's "HUD shows/hides based on selection" maps to `ActionsPanel`: it already conditionally shows action buttons based on `hasSelectedArmy`/`isMyTurn` (`ActionsPanel.tsx`), so Corner Conquest is already following this pattern — no new work implied, cited as confirmation the existing approach is sound.
- **Diluvium.** Digital reimagining of a tabletop wargame; its defining UI idea is that the board animates to *show* what changed turn-to-turn (unit moves, resource deltas) instead of making the player re-read numbers after each turn resolves. Applies to: the map's turn-resolution moment generally (`src/modules/map`, `GameBoard.tsx`'s turn-advance path) — e.g. animating army movement/combat results on the board rather than only updating `GameLog` text and static sprites. **Structural** — this is a new interaction pattern (animation choreography tied to state diffs), not a token tweak, and is a plausible explanation for why finding 7 (game log color-coding) only partially solves "what changed" — color-coding the log is a readability patch; Diluvium's pattern is the more ambitious fix for the same underlying need (scanning for "what did my opponent just do"). Flag as a candidate follow-up research spike, not something to size into this backlog.
- **Polytopia.** Turn-based territory/army game with a deliberately minimal HUD: a single collapsed resource/tech counter in a corner that expands on tap, and large, unambiguous unit-selection highlighting directly on the hex/tile grid rather than in a side panel. Applies to: `PlayerInfoBar`'s existing collapse-on-mobile behavior (`PlayerInfoBar.tsx:13-14`) is already directionally aligned with Polytopia's "collapsed by default, expand on demand" HUD philosophy — **token-level validation**, not a new ask. Also relevant to finding 3: Polytopia keeps its primary action (end turn / confirm move) as a single, always-visible button rather than a scrollable list, which is a simpler alternative worth listing alongside "sticky bottom bar" when finding 3 gets its own spec — **structural**, input for that future spec only.
