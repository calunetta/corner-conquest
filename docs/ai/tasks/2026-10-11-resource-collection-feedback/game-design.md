# Game design: Resource collection feedback + farmer-boat reset

## Proposal (game-designer-a)

### Problem or opportunity
Two linked problems, both already confirmed in `triage.md`:

1. **Feedback and juice lens.** `applyAutomaticCollection` (`src/modules/game-rules/player-turn.reducer.ts:8-31`) collects resources every turn for every positioned army and writes a log entry, but that entry has `isPassive: true`, so `filterVisibleEntries` (`src/modules/hud/components/GameLog/GameLog.map.ts:41`) hides it from the log by default. There is no toast. A player who positions an army and never opens "Show routine activity" has no way to see the collection happening — hence "doesn't seem to have happened."
2. **Readable-at-a-glance lens.** `player.positions` (`src/lib/types/map.ts:18-23`) persists until the army moves, loses a fight, or dies — there is no code path that clears it on collection. `docs/architecture/game-mechanics.md:85` documents this as intentional: "the army ... keeps collecting it every turn after that without re-clicking Position." The farmer sprite (`TileBoats.map.ts:74,80`, `showIdleCollector: !isPositionedOnResource`) is driven purely off that same persistent state, so it never reverts to idle-at-boat even when the player has mentally "moved on." This is a genuine rule change, not a bug fix — confirmed with the user (triage.md:16, Open questions).

**Correction to triage's bot-impact claim.** Triage states (triage.md:17) "Bots were checked and do not call the resource-positioning reducer at all ... grep for `resource-position`/`handleSelectResourceForPosition` across `src` found no bot module," and scopes "Any change to bot behavior" as Out. This is factually wrong. `src/modules/game-rules/bot-army-actions.reducer.ts:54-65` does dispatch `GameAction.SelectResourcePosition` for bots, at **flat priority 9** — the single highest priority of any bot action, above attacking a player (`8 + attackPower diff`, line 35), attacking a monster (flat 7, line 48), and all movement (6/4/3/2, lines 70-81). `docs/architecture/systems-and-visuals.md:42` independently documents this as "the bot's primary way to build its economy." Today, once a bot's army is positioned, `isAlreadyPositioned` (line 54) is permanently true, so on every later turn that army falls through to the attack/move checks instead — it still earns passive income while being free to fight. If positions auto-clear after every collection with no other change, that same army becomes "not positioned" again every turn, and because position-scoring (9) outranks every combat action, the bot will re-lock it into farming forever instead of ever fighting with it. That silently makes bots far more passive and less aggressive than they are today — the opposite of what the "Out of scope: bot behavior" line assumes. This proposal's recommended option includes a one-constant bot fix to prevent that regression; it cannot stay out of scope.

### Options considered
| Option | Player-facing summary | Fun lens | Complexity cost |
|---|---|---|---|
| A (minimal, recommended) | Position collects once, then clears; re-positioning that spot next turn costs the army's one action, exactly like the first time. Toast added; log entry stays hidden-by-default. | Agency + risk/reward (farm vs. fight becomes a real per-turn choice) | Lowest: reuses the existing `SelectResourcePosition` action and `PositionDialog` untouched; only removes a `player.positions` entry (and its `tile.positionedBy` mirror) in both collection code paths after crediting resources. Needs one bot-priority constant change (below). |
| B | Position clears visually/in state, but re-positioning the same army on the same spot it just collected from is a free "renew" that does not set `hasActed`. | Feedback and juice only | Medium: needs a new "is this a renewal of my own last spot" branch in `resource-position.reducer.ts`, distinct from the existing Extra Move exception — a second kind of free positioning, which is the complexity budget's "earns its place" bar, and it doesn't: the click becomes pure busywork with zero strategic content, since nothing is ever actually at stake. |
| C | Position persists for a fixed number of turns (e.g. 3) after being set, then clears automatically. | Tension and pacing (a visible countdown) | Highest: new per-position counter field (`Position` type, `src/lib/types/map.ts`), new save/serialize surface, new UI (countdown badge), new tooltip rule on top of the existing Position rule instead of replacing it. Over budget for an M-tier task framed around a feedback fix. |

### Recommended rule spec
- On collection (`applyAutomaticCollection`, `player-turn.reducer.ts:8-31`, **and** the Productive-card collection path, `handleProductiveCollection` in `src/modules/game-rules/card-effects.reducer.ts:54-91` — both currently credit resources without ever touching `player.positions`), after crediting a positioned army's resource, remove that entry from `player.positions` and the matching entry from `tile.positionedBy`.
- The army's visual and game state immediately fall back to "idle at boat" (`TileBoats.map.ts:74,80` already derives this purely from `positionedBy`, so no new view logic is needed — confirm in preview per triage scope).
- To keep collecting from that spot, the player must click Position again on their next turn, using the same `PositionDialog` → `SelectResourcePosition` flow that exists today. Because `hasActed` resets to `false` for every army at the start of each turn (`player-turn.reducer.ts:84`), re-positioning competes for the army's one action exactly like Move or Attack would — no special-case exception.
- Tooltip-sized rule: "A positioned army collects its resource once, then must be re-positioned to keep collecting."
- **Bot companion fix (mandatory, not optional):** lower the flat positioning priority in `bot-army-actions.reducer.ts:60` from `9` to `5`. This sits below monster-attack (7) and fog exploration (6), but above moving onto an unoccupied resource/Base tile (4), Special island (3), and other moves (2). It is a single constant, not new state: it treats first-time and renewal positioning identically (a priority distinction between the two would need new per-army history state, which the minimal option deliberately avoids). Net effect: bots will still build economy when nothing better is available, but will choose to fight before automatically re-committing an army to a spot it already farmed.
- Toast: fire for the local client's own player only, at the moment of `handleEndTurn` processing for that player (mirrors the existing `use-toast.ts` pattern from `AbilitiesDialog.hook.ts`), listing resource type + amount, e.g. "Collected 2 Food, 1 Gold." No toast for the Productive-doubled case needs special wording beyond including the doubled total — the player already sees the doubled number in the amount.
- Log visibility: keep `isPassive: true` (hidden by default). The toast is the real-time signal; the log stays available for history via "Show routine activity." Promoting it to non-passive would add a recurring line to the default log every single turn for every player at the table, hurting "readable at a glance" (pillar 2) for a signal the toast already covers. If playtesting after this ships shows players still miss it, promoting log visibility is a one-line follow-up — call this out to the UI-designer pair as the one open call they should confirm once the toast exists.

### Balance math
Scenario: a single-resource island always has 2 collection spots (`docs/architecture/game-mechanics.md:26`), `baseResourceAmount` default 1. Match length target ~20 turns (pillar 2). Computed with:
```
node -e '
const matchLength = 20;
const spots = 2;
const amountPerSpot = 1;
for (const positionTurn of [3, 6, 10, 15]) {
  const remainingTurns = Math.max(0, matchLength - positionTurn);
  const totalYield = spots * amountPerSpot * remainingTurns;
  const currentActionCost = spots;
  const optionAActionCost = spots * remainingTurns;
  console.log(`positioned turn ${positionTurn}: yield=${totalYield} food, current cost=${currentActionCost} actions, option-A cost=${optionAActionCost} actions (${(optionAActionCost/currentActionCost).toFixed(1)}x)`);
}
'
```
Result:
```
positioned turn 3: yield=34 food, current cost=2 actions, option-A cost=34 actions (17.0x)
positioned turn 6: yield=28 food, current cost=2 actions, option-A cost=28 actions (14.0x)
positioned turn 10: yield=20 food, current cost=2 actions, option-A cost=20 actions (10.0x)
positioned turn 15: yield=10 food, current cost=2 actions, option-A cost=10 actions (5.0x)
```
Reading: under today's rule, positioning costs 2 actions total for the whole match regardless of when you do it. Under Option A, maintaining the same yield costs one action per spot per remaining turn — a 5x to 17x increase in action cost for the identical resource total, front-loaded worse the earlier you commit. This is the intended tradeoff: resources (food/wood/gold) never grant VP directly — VP comes only from discovery (1), beating a player (+5) or a monster (2/5/7/10), and the two passive abilities (`game-mechanics.md:36-44`) — so resources only matter as fuel for deploys/upgrades/cards. Taxing passive income with the army's own action makes "park this army forever as a farm" compete honestly against "use this army to fight or explore," instead of being a strictly dominant, zero-upkeep background task. It does not change any player's economy asymmetrically (same rule for all seats), so it does not create or remove a runaway-leader effect; if anything it reduces a leader's ability to coast on accumulated, action-free farms (pillar 4).

### Interactions and exploits checked
- **Two collection code paths, both need the clear.** `applyAutomaticCollection` (`player-turn.reducer.ts:8-31`) and `handleProductiveCollection` (`card-effects.reducer.ts:54-91`, triggered via `state.productiveDialogState`) independently duplicate the "read `player.positions`, credit resources" loop. Both must remove the position entry; missing one would let Productive-doubled spots keep farming forever, while normal ones clear — an inconsistency the implementer must avoid and the tester must cover with one test per path.
- **Extra Move bonus positioning** (`resource-position.reducer.ts:38-44`) is untouched — it's a one-time placement exception already in the code (`hasExtraMove` skips `hasActed`), unrelated to the renewal cost added here.
- **Multiple spots per tile.** `alreadyPositioned` in `resource-position.reducer.ts:29-32` is checked per-resource, not per-tile, so two different armies can independently farm two different spots on the same island; each clears and must be renewed independently — no change needed there.
- **War Chief / Overcome / Decide Dice Roll** are combat-only cards (`card-data.ts:47,52-53`); no interaction with positioning.
- **Defensive wins keep the position** (`game-mechanics.md:86`, "Winning a fight from its tile keeps the position") — unaffected; the position still clears on its own collection cycle regardless of combat outcome, since collection and combat are independent events.
- **Hand limit / card draw** — unaffected; no new card, no new hand interaction.
- **Fog of war** — unaffected; positioning already requires a revealed, un-monstered Resource or Base tile.
- **Bot priority regression — covered above** and addressed by the single-constant fix (priority 9 → 5). This should be re-verified with `scripts/balance-simulator/` (per `docs/balance-simulator-guide.md`, already referenced from `systems-and-visuals.md`) before/after the change, watching match length and bot combat frequency, since this is the one lever in this proposal that changes bot behavior beyond "do the same thing every turn instead of once."

### Bot impact
`bot-army-actions.reducer.ts` requires no new logic: its priority loop already re-evaluates every unacted army every turn from scratch, so a cleared position is picked up automatically by the existing `isAlreadyPositioned` check (line 54) with zero new state. The only required change is the one-line priority constant at line 60 (`9` → `5`), justified above, so position-renewal no longer outranks every combat option by default.

### UI needs
- Toast on the local player's own turn start when `collectedResources` is non-empty, matching amounts already computed in `applyAutomaticCollection`/`handleProductiveCollection` (no new calculation, just surfacing the existing values) — wire into the existing toast store (`src/modules/shared/toast-store.ts`, `use-toast.ts`), following the `AbilitiesDialog.hook.ts` usage pattern.
- No change to `PositionDialog` — same dialog, same flow, just invoked again next turn.
- `TutorialBeacon.preview.tsx:12` currently reads "Move onto Resource Islands and click Position to gather resources automatically every turn." — this is now wrong (it implies the first click is enough forever) and must change to reflect the renewal requirement, e.g. "...click Position to gather resources — re-position each turn to keep collecting." UI-designer pair to finalize exact copy.
- Farmer sprite reverting to idle-at-boat is expected to fall out of existing `TileBoats.map.ts` logic once `positionedBy` is actually cleared — confirm visually in `npm run dev` → testbed/live board per `triage.md` scope, no new sprite states needed.

### How we will know it works
- Unit test: after `handleEndTurn` collects for a positioned player, `player.positions` is empty and the matching `tile.positionedBy` entry is gone (cover both the normal path and the Productive-dialog path).
- Unit test: a player who does not re-click Position next turn collects nothing further from that spot; a player who does re-clicks and it consumes `hasActed` same as any other action.
- Unit test (bot): `bot-army-actions.reducer.test.ts` — a bot with an attackable player/monster present and an already-farmed-and-cleared position prefers the attack (priority 7/8+) over re-positioning (priority 5) when both are legal.
- Playtest/balance-simulator signal: match length and bot win rate stay within the simulator's existing baseline range (`docs/balance-simulator-guide.md`) after the priority change — a large shift (e.g., bots winning or losing dramatically more, or matches running much longer) means the priority constant needs tuning, not reverting the whole feature.
- Qualitative: players report seeing the toast and the boat returning; no report of "my farm silently stopped" (since now it's an intentional, visible choice, not a silent code gap).

## Review (game-designer-b)
VERDICT: CHANGES REQUESTED

Citations re-verified: `player-turn.reducer.ts:8-31,143-151`, `resource-position.reducer.ts:5-55`, `bot-army-actions.reducer.ts:54-65`, `movement.reducer.ts:6,9-42,82-96`, `card-effects.reducer.ts:48-92`, `TileBoats.map.ts:74,80`, `GameLog.map.ts:41`, `player-factory.ts:45`, `game-setup.reducer.test.ts:23`, `TutorialBeacon.preview.tsx:12`. All check out except one name (below). Math in the proposal's `node -e` table reproduces correctly (positionTurn 3 → yield 34 / cost 34 / 17.0x, etc. — re-ran the same formula by hand, matches).

### Findings

**1. Bot priority 5 sits below fog-exploration (6) — this doesn't just under-farm, it causes bots to permanently abandon established farms, the opposite of the stated goal. BLOCKING.**
`handleMoveAction` (`movement.reducer.ts:82-96`) clears `player.positions`/`tile.positionedBy` the instant an army *moves off* its spot — not just skips a turn, destroys the position. A farmer army never moves (`handleSelectResourceForPosition` marks the position in place; `resource-position.reducer.ts:17` uses `selectedArmy.position` unchanged). Fog reveal only happens when an army physically visits a tile (`revealIsland`, called from `handleMoveAction`). So a stationary farmer's neighboring tiles (within `MOVE_RADIUS = 2`, `movement.reducer.ts:6`) never get revealed unless that same army walks there — meaning if even one tile within radius 2 of a farm spot stays unrevealed (plausible for a long stretch of a ~20-turn match on a 30-tile 5×6 grid, since reveal is per-player and MOVE_RADIUS 2 covers most of a small board), that farm scores a fog-move at priority 6 every single turn versus priority 5 to re-farm. The bot will walk the army away and permanently lose the position — this is worse than today's complaint (bots are "more passive"); it's bots repeatedly founding, then abandoning, farms, which the proposal's own stated mitigation goal ("bots will still build economy when nothing better is available") does not hold since "nothing better" is not a transient state for a parked army.
Fix: set the renewal priority to **6**, tied with fog-exploration, not 5. `Array.prototype.sort` has been stable since ES2019/Node 11; within the per-army loop (`bot-army-actions.reducer.ts:25-85`) the position action is pushed before that army's move options, so a same-army tie resolves in favor of re-positioning, while a genuine monster (7) or player attack (8+) for *another* army still outranks it. A tie against *another* army's fog-move is arbitrary but harmless (both options are deliberately valued equally). This keeps the single-constant-change simplicity budget (still one line, just `6` not `5`).

**2. The "meaningful choice" framing overstates the common case; re-positioning a parked generator army is undifferentiated busywork, and the toast only fires when something was collected — so forgetting to re-position produces exactly the same silent "nothing happened" signal this task exists to fix, for a new reason.**
The dominant strategy under the current (pre-change) rule is: park 1–2 armies permanently as generators (including the starting army at Base, which is itself positionable — `player-factory.ts:45` confirms armies start with `positions: []`, and `creatorBase?.resources.length` is 3 per `game-setup.reducer.test.ts:23`, so Base income is gated by the same Position mechanic), and use the rest to fight/explore. For a generator army with no enemy/monster on its tile, "re-position" is its only legal major action every turn — there is no alternative to weigh, so it is not the "farm vs. fight" choice the proposal claims (game-design.md:16); it is a mandatory click to stand still, structurally identical to the busywork the proposal itself rejects in Option B ("the click becomes pure busywork with zero strategic content, since nothing is ever actually at stake," game-design.md:17) — Option A has that exact failure mode for every army with no local threat, which by mid-game is most farmers. The only place genuine choice exists is when a farmer's tile *also* has something else worth doing that turn (rare, since positioning already requires no monster on the tile, `resource-position.reducer.ts` — a monster-free tile never has an attack option, so the "choice" is really farm-vs-go-explore-elsewhere, a real but infrequent decision since the player already chose to stay there originally).
Worse: `applyAutomaticCollection` (`player-turn.reducer.ts:20-28`) and the toast (per proposal's UI needs) both only fire `if (collectedStrings.length > 0)` — a player who forgets to re-position gets *zero* signal, not a "you missed it" warning. That reproduces this task's own root complaint ("doesn't seem to have happened") for a new root cause: silently-expired positions instead of silently-hidden log entries.
Fix: not a blocker to the overall direction (the user already confirmed real position-clearing, not cosmetic, in triage.md:34), but the spec must add a lightweight "you have N idle, unpositioned armies sitting on resource/Base tiles" signal — reuse the existing idle-boat visual (once finding 3 below is fixed) plus one `isPassive: false` log line or toast per turn when a previously-farmed tile collected nothing because no army is positioned there now. This is a one-branch addition to the same collection loop, not a new system, and keeps the complexity budget.

**3. `TileBoats.map.ts:74` keys the idle/farming sprite by `playerId`, not by army — the "boat reverts to idle" acceptance criterion silently fails whenever a player has two armies on the same island.**
`isPositionedOnResource = (island.positionedBy || []).some((pos) => pos.playerId === player.id)` (confirmed, `TileBoats.map.ts:74`) is computed once per occupant and does not check which specific army/resource pairing it belongs to. A single island can have two collection spots (`docs/architecture/game-mechanics.md:26`), each needing its own army, so two of the same player's armies on one island is a normal, not edge, case. If Army A's position clears (per this feature) while Army B's position on the same island is still active, Army A's boat will still render as "collecting," not idle — because the check only asks "does this player have *any* positioned entry on this island," not "does *this* army's own position entry still exist." The proposal's claim "no new view logic is needed" (game-design.md:9,22) is wrong for this case; this must change to match on `armyId`, not just `playerId`. This is a map-module file (owned by UI-designer/implementer for the map domain, not mine to fix), but it must be called out now since it directly contradicts one of the feature's two "How we will know it works" criteria (game-design.md:78, "the boat returning").

**4. Minor: wrong function name.** The proposal calls out `handleProductiveCollection` (game-design.md:9,21,55) as the Productive-card collection path. The actual function is `handleUseProductiveCard` (`src/modules/game-rules/card-effects.reducer.ts:48`). Same file/line range is otherwise correct (`:54-91` → actually `:48-92`, off by one at the start); the fix target is right, just the name is wrong. Carry the corrected name into the plan so the implementer doesn't grep for a function that doesn't exist.

### Pillars and constraints check
- Pillar 1 (meaningful choice every turn): not fully met for the common "parked generator" case — see finding 2. Mitigated, not solved, by the final spec below.
- Pillar 2 (~20 turns, readable at a glance): the added per-turn click for every active farmer is a real, if small, tax on turn length; no evidence it breaks the 20-turn target, but it works against "readable at a glance" per finding 2 until the idle-army signal is added.
- Pillar 3 (interaction): unaffected, no new interaction surface.
- Pillar 4 (trailing players keep a path back): correctly argued in the proposal's balance section — the rule is symmetric across seats, so it does not asymmetrically help or hurt a leader.
- Pillar 5 (luck vs. skill): unaffected, no dice involved.
- Complexity budget (one tooltip sentence): met — "A positioned army collects its resource once, then must be re-positioned to keep collecting" fits.
- Firestore cost: confirmed no extra write — the position-clear is folded into the same `handleEndTurn`/`handleUseProductiveCard` state mutation already written once per action; the toast is client-local (`toast-store.ts`), not persisted.
- Bots: finding 1 is a correctness bug in the proposed fix, not just a tuning nit — must be priority 6, not 5.
- Tutorial: proposal's replacement copy direction is right; exact wording left to UI-designer pair per triage.

## Final spec
Approved pending the three required changes below folded in (findings 1, 2, 4); finding 3 is routed to the UI-designer/architect pair as an implementation-ownership note, not a reason to hold this spec.

1. **Collection and position-clear**, in both `applyAutomaticCollection` (`player-turn.reducer.ts:8-31`) and `handleUseProductiveCard` (`card-effects.reducer.ts:48-92`, not `handleProductiveCollection` — corrects proposal's naming error): after crediting a positioned army's resource for the turn, remove that entry from `player.positions` and the matching entry from `tile.positionedBy`. Applies identically to Base tiles (Base is a positionable tile with 3 resource spots, same as any Resource island).
2. **Re-positioning**: unchanged flow — same `PositionDialog` → `GameAction.SelectResourcePosition` → `handleSelectResourceForPosition` (`resource-position.reducer.ts`), consumes the army's one action per turn (`hasActed`) exactly like Move or Attack, no new exception. Extra Move interaction unchanged.
3. **Bot priority fix (mandatory)**: in `bot-army-actions.reducer.ts:60`, change the flat positioning priority from `9` to **`6`** (not `5` — see finding 1), tying it with fog-exploration (line 72's `priority = 6`) rather than sitting below it. Monster-attack (flat 7, line 48) and player-attack (`8 + attackPower diff`, line 35) still outrank it unconditionally. No other bot logic changes; `isAlreadyPositioned` (line 54) already re-evaluates every unacted army from scratch each turn.
4. **Idle-farm signal (new, required — finding 2)**: when `handleEndTurn` processes a player whose `positions` array is empty but who has at least one army sitting on a Resource or Base tile with an available, un-positioned spot (same eligibility `resource-position.reducer.ts` already checks, minus the per-turn action cost), surface that as a non-silent signal for the local player only — reuse the toast store; one line, e.g. "N army(s) sitting idle on resources — re-position to collect." This does not require new state: derive it at render time from existing `army.position` + `tile.resources` + `tile.positionedBy`, same data the collection loop already reads. No log-entry schema change, no extra Firestore write (client-side derivation only, like the main collection toast).
5. **Toast (collection)**: fire for the local client's own player only, when `collectedResources` is non-empty, listing resource type + amount (e.g. "Collected 2 Food, 1 Gold"), following the `use-toast.ts` / `AbilitiesDialog.hook.ts` pattern (`AbilitiesDialog.hook.ts` confirmed as an existing toast call site).
6. **Log visibility**: keep `isPassive: true` for the routine per-turn collection entry (hidden by default, same as today) — the two toasts (collection + idle-farm signal) are the real-time surface; "Show routine activity" remains the history view. Revisit only if post-ship playtesting shows players still miss it.
7. **Tutorial**: update `TutorialBeacon.preview.tsx:12` off "...click Position to gather resources automatically every turn" to reflect the renewal requirement (exact copy owned by UI-designer pair), e.g. "...click Position to gather resources — re-position each turn to keep collecting."
8. **Docs**: `docs/architecture/game-mechanics.md` §5.3 and §6.3 (currently states positions persist "without re-clicking Position" and are "removed only when the army moves... loses a fight... or is defeated") must be updated to the new rule: a position also clears automatically after each collection, requiring renewal — `docs-sync`, mandatory per the skill, same phase.
9. **Tests required** (unchanged from proposal, plus finding 1's corrected priority and finding 2's new behavior):
   - `player.positions`/`tile.positionedBy` cleared after collection, both paths (`applyAutomaticCollection` and `handleUseProductiveCard`).
   - A player who doesn't re-click Position next turn collects nothing further from that spot; re-clicking consumes `hasActed` like any other action.
   - Bot test: with an attackable player/monster present and an already-farmed-and-cleared position, the bot prefers attack (7/8+) over re-positioning (6) when both are legal; separately, a bot with *only* a cleared position and *no* unrevealed tile in range re-positions (confirms the priority-6 tie resolves correctly for a stationary army, per finding 1's stable-sort argument).
   - New: the idle-farm toast fires exactly when a player has an eligible-but-unpositioned army and does not fire when all farmable spots are either collecting or genuinely unavailable (no open spot).
   - `TileBoats.map.ts` (route to its owner, not blocking this spec): a regression test for two same-player armies on one island where only one position clears — document as a known gap for that stage to close, per finding 3.
10. **Balance-simulator gate (mandatory, not optional)**: run `BALANCE_SIMULATOR_ARGS="--players 2,3,4 --fog on,off --games 200 --seed 1" npm run balance:simulate` before and after, specifically watching M2 (match length) and the bot-economy-adjacent metrics (deploy/upgrade frequency if reported) in addition to win-rate — finding 1's bug (farms being permanently abandoned) would show up as bots never accumulating resources; a priority-6 fix that still shows this pattern means the priority needs to go higher still (never lower than monster-attack's 7), not that the whole feature should revert.

DONE
