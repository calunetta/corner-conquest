# Plan: bot-vs-bot-ui.spec.ts stalls on the Position action button

Status: APPROVED
Inputs: triage.md

## Goal and acceptance criteria
- [ ] `e2e/bot-vs-bot-ui.spec.ts` no longer stalls; a full `npm run test:e2e -- e2e/bot-vs-bot-ui.spec.ts` run passes.
- [ ] No behavior change to legitimate human-disconnect handling (a peer that is genuinely gone still gets converted to a bot within a reasonable bound).
- [ ] The possibleMoves fix already shipped (see below) is retained; it fixed a real race, just not the one still stalling the suite.
- [ ] `GameState.heartbeats` can never contain an explicit JS `undefined` value for any key (only genuinely absent keys), so `saveGameState`'s `setDoc` can never again throw `FirebaseError: Function setDoc() called with invalid data. Unsupported field value: undefined`.

## Revise-mode update (second pass — the real root cause)
Phase 1 below (120s threshold, e2e un-skip, widened issue-buffer draining) was implemented, checked clean, and re-run for real. The suite still stalled at ~10 minutes, but this time the widened issue-buffer draining (exactly the diagnostic Phase 1 added for this reason) caught the actual mechanism directly: turn 1, seat 0's console errors contain `Error handling game action: FirebaseError: Function setDoc() called with invalid data. Unsupported field value: undefined (found in field heartbeats.\`0\` in document games/1Hj86ZqodE2BZXAcFmlv)`, and that same turn's `landingIssues` show `never landed: army 0 position on food at (0,0)` — the turn's Firestore write (End Turn, `saveGameState`'s `setDoc`) threw synchronously and never landed, because `state.heartbeats[0]` was an explicit `undefined` in the object passed to `setDoc`. Firestore's client SDK rejects an explicit `undefined` anywhere in the write (an absent key is fine; `undefined` is not).
This is the real, confirmed root cause of the whole stall. The staleness/45s-threshold mechanism investigated in Phase 1 was very likely a downstream symptom, not the cause: once a game-state write like this one silently (from the player's point of view) throws and never reaches Firestore, the match genuinely stops advancing server-side, which is consistent with the "document deleted mid-match" failures the two earlier live runs also hit (a match stuck mid-write for long enough starts looking "stale" to peers for real reasons, not a timing fluke). Phase 2 below is the real fix. Phase 1's two changes are kept — the e2e observability widening is what caught this, and the 120s threshold still has independent production merit (see its own Decision) — but neither one was the primary fix; this plan's framing is corrected to say so.
Root cause and decisions below replace the prior (correct-as-far-as-it-went, but not load-bearing) ones from the first revision; File plan, Contracts and Phases gain a new Phase 2 for the real fix. Old rows kept in Verified context are still accurate and still relevant (they explain why Phase 1's changes are correct and the investigation that led here); new rows below are from this pass.

**Note for whoever resumes `docs/ai/tasks/2026-10-15-heartbeat-contention-fix`:** that task's Phase 2 moved mid-pop during this session (its `git stash` was popped by the coordinator partway through my investigation), so the "Verified context" rows below cite the current, post-Phase-2 shape of `game-board.staleness.hook.ts` and `game-board.state.map.ts` (reading/syncing `GameState.heartbeats[seatId]`, not `Player.lastSeenAt`). This plan does not touch those files' ownership or design; Phase 1 below only changes `STALE_THRESHOLD_MS`'s value and the e2e harness, both of which are compatible with either shape of the heartbeat storage. If that task's Phase 2 is not yet committed when this plan executes, re-verify `game-board.staleness.hook.ts`'s exact current field names before implementer-a edits it.

## Root cause (bugs only)
- **Confirmed mechanism, not yet confirmed trigger.** The match document (`games/{gameId}`) is deleted mid-match. The only in-progress delete path in the repo is `player-exit.service.ts:57-60` (`remainingRealPlayers.length === 0`), reached only via `useStalenessCheck`'s `convertStalePeer` (no "Leave Game" button is ever clicked by the spec). For a 2-seat match this requires *both* seats to have been wrongly converted to a bot at some point (the branch only fires once excluding the seat being processed leaves zero humans) — i.e. each seat's own `heartbeats[seat.id]` entry must have gone unwritten in Firestore for more than `STALE_THRESHOLD_MS` (45s) at least once during the match, while that seat was not actually disconnected (both browser contexts stay open for the test's whole 10-minute run).
- **Ruled out, with evidence (this pass), as the mechanism:**
  - *Chrome background-tab timer throttling.* Disproven twice over: (1) the three flags the original hypothesis proposed adding (`--disable-background-timer-throttling`, `--disable-backgrounding-occluded-windows`, `--disable-renderer-backgrounding`) are already unconditionally present in Playwright's own default Chromium launch switches (`node_modules/playwright-core/lib/coreBundle.js`'s `chromiumSwitches`), independent of `playwright.config.ts` (which only sets `executablePath`). (2) An isolated experiment this session — two `chromium.launch()` contexts, a page in each with a bare 15000ms `setInterval`, one page CPU-busy-looping for 70s while the other sits fully idle, using this repo's exact default launch options — showed `document.visibilityState: "visible"` on *both* pages throughout and the idle page's interval firing at ~15000ms, zero drift, the whole 70s. Separate `browser.newContext()` pages are not treated as backgrounded tabs here, with or without the proposed flags.
  - *Turn-buffer clobbering the peer's heartbeat.* `withSyncedSeatManagement`/`syncedHeartbeats` (`game-board.state.map.ts:15-66`) re-syncs every *other* seat's latest `heartbeats` entry into the turn-holder's local buffer on every `serverGameState` change, before any `setGameState`/`setDoc`. A full-document overwrite from that buffer cannot carry an older `heartbeats` value for a peer than the last snapshot the turn-holder's client has seen — ruled out.
  - *Write contention on the heartbeat write itself.* `writeHeartbeat` (`game-board.engine.service.ts:44-50`) is a single-field-path `updateDoc`, not a transaction — it cannot be blocked or retried-into-failure by a concurrent whole-document `setDoc` the way the separately-tracked write-contention bug (`docs/ai/tasks/2026-10-15-heartbeat-contention-fix`) described; that bug's Phase 1 already landed this exact change.
  - *The spec's own per-turn wait budget (up to ~60s: 3 `BOT_STEPS` + End Turn, each bounded at `SYNC_TIMEOUT_MS = 15000`) directly causing a gap.* The Node-side Playwright driver waiting on `waitForStepEffects`/`waitForGameState` does not block the browser page's own JS event loop — confirmed by the same experiment above (the busy page's *own* interval also landed on schedule). A slow turn, by itself, does not stall that page's heartbeat.
- **Most likely remaining, unconfirmed lead:** the e2e spec itself has a real, independently-confirmable gap that would hide exactly this failure mode. `attachIssueListeners`/`drainIssueBuffer` (`e2e/bot-vs-bot-ui.spec.ts:264,290,312`) only ever drains and checks `issueBuffers[actingSeat]` — the *idle* seat's console errors, page errors and failed requests accumulate but are explicitly discarded, unread, the moment that seat becomes active again (the `drainIssueBuffer(issueBuffers[actingSeat])` call at the top of the loop, commented "discard noise from the previous seat's turn", is discarding exactly the window the idle seat was NOT acting — the one window we need visibility into). A JS error, an unhandled rejection, or a React crash on the idle page — which would plausibly stop its `setInterval`-driven heartbeat outright, unlike any of the ruled-out mechanisms above — would currently produce **zero** signal anywhere in this spec's output.
- This has not been confirmed with a live run (per the coordinator's own instruction, that specific sub-question needs one, not a guess). Phase 1 below closes the known, real gap (idle-seat issues going unobserved) and applies a defensive threshold increase justified independently by the triage's own production concern (a human alt-tabbing under a minute should not get bot-converted), rather than landing a fix keyed to an unconfirmed mechanism.

### Root cause, confirmed (second pass — Phase 2)
- **The actual bug: `syncedHeartbeats` (`src/modules/game-board/game-board.state.map.ts:55-66`) can write an explicit JS `undefined` into `GameState.heartbeats`, which Firestore's client SDK refuses to persist.** Line 61 is `if (localSeatId !== undefined) merged[localSeatId] = local[localSeatId];` — unconditional. On (at least) the match's first turn, the turn-holder's local buffer (`localGameState`, seeded by `cloneDeep(serverGameState)` in `game-board.state.hook.ts:31-32` the instant `isMyTurn` first becomes true) can be cloned from a `serverGameState` snapshot taken *before* this seat's own first `writeHeartbeat` call has round-tripped back through `onSnapshot` — a real race, since `useHeartbeat`'s "send immediately" write is an async network round trip, not synchronous with the clone. When that happens, `local.heartbeats` has no key at all for the local seat; `local[localSeatId]` reads as `undefined`; and the line above **assigns** that `undefined` onto `merged[localSeatId]` — unlike an absent key, a JS `obj[key] = undefined` assignment creates a real, enumerable own-property with value `undefined` (confirmed: `Object.keys`/`in`/`hasOwnProperty` all see it). Once any *other* seat's heartbeat differs between `local` and `server` (which happens on its own 15s cadence, continuously), `isSame` (line 64) is `false` for an unrelated key, so the whole `merged` object — including the poisoned `heartbeats.<localSeatId>: undefined` — is returned and becomes the new `localGameState`. It then rides along through every reducer call for the rest of that turn (most reducers shallow-copy `GameState`, preserving the `heartbeats` reference/value) until `EndTurn`'s `setGameState`/`saveGameState` calls `setDoc` with it, which throws synchronously (`game-board.engine.hook.ts:23-29`'s try/catch logs it as `console.error('Error handling game action:', error)` — the exact text captured). The write never lands, so nothing from that turn (including the position action) reaches Firestore — exactly the captured `landingIssues` entry.
- **Why this explains the earlier "document deleted mid-match" failures too, not just this run's symptom:** once a turn's write silently fails this way, the match stops advancing in Firestore even though both players are still actively playing through the UI — the document looks abandoned from the staleness check's point of view for a real, if indirect, reason. Phase 1's threshold raise and observability widening were reasonable, independently-justified defensive moves (kept, see Decisions), but they were not the primary fix — they could not have been, since nothing in Phase 1 touches `syncedHeartbeats`.
- Confirmed NOT present on every turn, only when the race lands against the local seat's own still-unsynced heartbeat — consistent with this being turn 1, seat 0 specifically (the host's very first turn, heartbeats barely a few hundred ms old anywhere in the system) rather than every turn.

## Decisions
- **Widen the e2e harness to observe the idle seat, not just the acting one.** Instead of discarding `issueBuffers[actingSeat]`'s stale content when a seat's turn starts, drain it and flag it (attributed to "idle before this turn") before clearing it. This is a real, confirmed gap independent of which exact mechanism turns out to be at fault — a crash or hang on the page that isn't currently acting should never be invisible to this suite. Rejected: leaving it as-is and relying solely on the threshold increase below — that would mask a real crash instead of surfacing it, and "fix the test's blind spot" is itself in scope per the triage ("fix the root cause... whichever is actually wrong").
- **Raise `STALE_THRESHOLD_MS` from 45s to 120s** (`game-board.staleness.hook.ts:6`). Both browser contexts in this spec stay open and connected for the test's whole duration — there is no legitimate disconnect to detect here, so any value comfortably above real-world transient gaps (CI CPU contention, a brief Firestore SDK reconnect/backoff, or whatever the widened issue-buffer draining surfaces) closes the observed failure without depending on pinning the exact mechanism. 120s is also a direct answer to the triage's second, independent question: a real human alt-tabbing during an opponent's turn for under a minute should not be silently converted to a bot; 45s already fails that bar, 120s comfortably clears it. Rejected: leaving `STALE_THRESHOLD_MS` unchanged and fixing only the observability gap — if the real cause turns out to be generic transient CI/SDK flakiness rather than a reproducible crash, a 45s threshold would still misfire occasionally with no code bug to fix. Rejected: a much larger value (e.g. 5+ minutes) — this is a production disconnect-detection feature, not just a test knob; 120s is the smallest increase that is comfortably safe against both the test's own worst-case per-turn wait budget (~60s) and casual real-world alt-tabbing, without materially degrading how quickly a genuinely dropped player's seat gets handed to a bot.
- `WARNING_THRESHOLD_MS` (`ConnectionWarningDialog.hook.ts:12`, 25,000) is unchanged — it still opens the "Connection lost" warning at the same absolute delay; only the countdown to takeover gets longer (now ~95s instead of ~20s), which is the intended effect of the increase. Its stale comment ("leaves a 20s countdown window") needs updating to match.
- Not fixing a specific code bug yet, because none is confirmed. If the widened issue-buffer draining (once it runs for real, Phase 1 step 5) shows a genuine idle-page crash or error, that is a new, separate root cause requiring its own fix — report it to architect-b rather than silently patching it under this plan's Contracts, which do not cover it.

### Decisions (second pass — Phase 2, the real fix)
- **Fix at the exact source: `syncedHeartbeats` must never assign an explicit `undefined` for the local seat's key.** Guard the assignment on whether `local` actually has the key (`localSeatId in local`); if it doesn't, `delete merged[localSeatId]` instead of assigning `undefined` to it, so the result has a genuinely absent key (matching every other "no heartbeat yet" case already handled elsewhere in this same codebase, e.g. `findStalePeerIds`'s `lastSeenAt !== undefined` check and the doc comment on `GameState.heartbeats` itself — "a missing key means no heartbeat yet"). This is the smallest change that fixes the actual defect: one `if` added around one line, no behavior change for the common case (local already has the key).
- Rejected: a blanket "strip `undefined` recursively before every `setDoc`" guard in `saveGameState`. That would mask this (and any future) bug at the write boundary instead of fixing the one place that creates the invalid value, violates "fix the root cause, not the symptom" (skill `testing`'s Bugs rule), and would silently swallow a real future bug of the same shape anywhere else in the state tree without ever surfacing it in a test. The source fix is one line; there's no KISS case for the broader net here.
- Rejected: seeding `useHeartbeat`'s first write synchronously into the local buffer itself, or delaying the turn-buffer clone until the seat's own heartbeat is confirmed present server-side. Both are real alternative fixes to the *race* (why `local` lacks the key at all on turn 1), but `syncedHeartbeats` has a second, independent duty regardless of why the key is missing: it must never emit an explicit `undefined` for *any* key, including a peer's (e.g. a peer who has genuinely never heartbeated yet, or whose entry a concurrent `convertSeatToBot` deletes mid-sync). Fixing only the turn-1 race would leave the `syncedHeartbeats` function itself still capable of producing the same invalid shape from a different trigger; fixing the function closes the whole class of bug at once.
- Keep Phase 1's 120s `STALE_THRESHOLD_MS` and the widened e2e issue-buffer draining — see their own Decision bullets above. They are not redundant with this fix: the threshold raise is independently justified by the triage's human-alt-tab concern, and the issue-buffer widening is exactly what surfaced this bug and should stay to catch the next one.
