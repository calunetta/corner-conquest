## Revise-mode update (fourth pass — the acting seat's own heartbeat, not just peers')
Phase 3's write-boundary fix (`syncedHeartbeats` reused inside `setGameState`) is real and correctly closes the lost-update race for every PEER seat's heartbeat, confirmed by a real `test:e2e` run after implementation. That same run still timed out. architect-b's Phase 3 review Finding 2 had already flagged, and accepted as safe, that the merge preserves the ACTING seat's own key from the turn buffer rather than from `gameStateRef.current` — reasoning that `useHeartbeat`'s 15s cadence "self-heals" it before `STALE_THRESHOLD_MS` (120s). A fresh live trace (coordinator, direct log of `callerHeartbeats`/`gameStateRefHeartbeats`/`mergedHeartbeats` inside `setGameState`) shows that judgment was wrong: the acting seat's own heartbeat gets rolled back to its turn-start value and **written to Firestore** on every single `EndTurn` — not a rare race, a guaranteed occurrence every turn, for the whole match — because the turn buffer never refreshes its own seat's heartbeat key after seeding at turn start, even though that seat's own `useHeartbeat` keeps writing fresh values the whole time. The corrupted value is visible to every other client's staleness check in the window before the next heal tick, every turn; over a long match this reliably trips the threshold. See `progress.md`'s Phase 4 section for the exact captured log.
This pass's fix: stop special-casing the local seat at all in `syncedHeartbeats`. Heartbeats are not part of any seat's own in-turn gameplay mutations (unlike army positions, resources, etc., which the turn buffer legitimately owns mid-turn) — they are an independent, continuously-updated side channel written only by `useHeartbeat`, on its own schedule, regardless of whose turn it is. There is no scenario where the server's value for a seat's own heartbeat is less trustworthy than the buffer's. `syncedHeartbeats` now always takes every seat's heartbeat (including the local seat's own) from `server`; this also fully subsumes Phase 2's explicit-`undefined` guard — the function no longer ever reads an individual value out of `local`, so it cannot produce an own-enumerable-`undefined` property. See the new Verified-context rows, Root cause and Decisions sections below.

## Revise-mode update (second pass — the real root cause)
Phase 1 below (120s threshold, e2e un-skip, widened issue-buffer draining) was implemented, checked clean, and re-run for real. The suite still stalled at ~10 minutes, but this time the widened issue-buffer draining (exactly the diagnostic Phase 1 added for this reason) caught the actual mechanism directly: turn 1, seat 0's console errors contain `Error handling game action: FirebaseError: Function setDoc() called with invalid data. Unsupported field value: undefined (found in field heartbeats.\`0\` in document games/1Hj86ZqodE2BZXAcFmlv)`, and that same turn's `landingIssues` show `never landed: army 0 position on food at (0,0)` — the turn's Firestore write (End Turn, `saveGameState`'s `setDoc`) threw synchronously and never landed, because `state.heartbeats[0]` was an explicit `undefined` in the object passed to `setDoc`. Firestore's client SDK rejects an explicit `undefined` anywhere in the write (an absent key is fine; `undefined` is not).
This is the real, confirmed root cause of the whole stall. The staleness/45s-threshold mechanism investigated in Phase 1 was very likely a downstream symptom, not the cause: once a game-state write like this one silently (from the player's point of view) throws and never reaches Firestore, the match genuinely stops advancing server-side, which is consistent with the "document deleted mid-match" failures the two earlier live runs also hit (a match stuck mid-write for long enough starts looking "stale" to peers for real reasons, not a timing fluke). Phase 2 below is the real fix. ## Root cause (bugs only)
- **Confirmed mechanism, not yet confirmed trigger.** The match document (`games/{gameId}`) is deleted mid-match. The only in-progress delete path in the repo is `player-exit.service.ts:57-60` (`remainingRealPlayers.length === 0`), reached only via `useStalenessCheck`'s `convertStalePeer` (no "Leave Game" button is ever clicked by the spec). For a 2-seat match this requires *both* seats to have been wrongly converted to a bot at some point (the branch only fires once excluding the seat being processed leaves zero humans) — i.e. each seat's own `heartbeats[seat.id]` entry must have gone unwritten in Firestore for more than `STALE_THRESHOLD_MS` (45s) at least once during the match, while that seat was not actually disconnected (both browser contexts stay open for the test's whole 10-minute run).
- **Ruled out, with evidence (this pass), as the mechanism:**
  - *Chrome background-tab timer throttling.* Disproven twice over: (1) the three flags the original hypothesis proposed adding (`--disable-background-timer-throttling`, `--disable-backgrounding-occluded-windows`, `--disable-renderer-backgrounding`) are already unconditionally present in Playwright's own default Chromium launch switches (`node_modules/playwright-core/lib/coreBundle.js`'s `chromiumSwitches`), independent of `playwright.config.ts` (which only sets `executablePath`). (2) An isolated experiment this session — two `chromium.launch()` contexts, a page in each with a bare 15000ms `setInterval`, one page CPU-busy-looping for 70s while the other sits fully idle, using this repo's exact default launch options — showed `document.visibilityState: "visible"` on *both* pages throughout and the idle page's interval firing at ~15000ms, zero drift, the whole 70s. Separate `browser.newContext()` pages are not treated as backgrounded tabs here, with or without the proposed flags.
  - *Turn-buffer clobbering the peer's heartbeat.* `withSyncedSeatManagement`/`syncedHeartbeats` (`game-board.state.map.ts:15-66`) re-syncs every *other* seat's latest `heartbeats` entry into the turn-holder's local buffer on every `serverGameState` change, before any `setGameState`/`setDoc`. A full-document overwrite from that buffer cannot carry an older `heartbeats` value for a peer than the last snapshot the turn-holder's client has seen — ruled out.
  - *Write contention on the heartbeat write itself.* `writeHeartbeat` (`game-board.engine.service.ts:44-50`) is a single-field-path `updateDoc`, not a transaction — it cannot be blocked or retried-into-failure by a concurrent whole-document `setDoc` the way the separately-tracked write-contention bug (`docs/ai/tasks/2026-10-15-heartbeat-contention-fix`) described; that bug's Phase 1 already landed this exact change.
  - *The spec's own per-turn wait budget (up to ~60s: 3 `BOT_STEPS` + End Turn, each bounded at `SYNC_TIMEOUT_MS = 15000`) directly causing a gap.* The Node-side Playwright driver waiting on `waitForStepEffects`/`waitForGameState` does not block the browser page's own JS event loop — confirmed by the same experiment above (the busy page's *own* interval also landed on schedule). A slow turn, by itself, does not stall that page's heartbeat.
- **Most likely remaining, unconfirmed lead:** the e2e spec itself has a real, independently-confirmable gap that would hide exactly this failure mode. `attachIssueListeners`/`drainIssueBuffer` (`e2e/bot-vs-bot-ui.spec.ts:264,290,312`) only ever drains and checks `issueBuffers[actingSeat]` — the *idle* seat's console errors, page errors and failed requests accumulate but are explicitly discarded, unread, the moment that seat becomes active again (the `drainIssueBuffer(issueBuffers[actingSeat])` call at the top of the loop, commented "discard noise from the previous seat's turn", is discarding exactly the window the idle seat was NOT acting — the one window we need visibility into). A JS error, an unhandled rejection, or a React crash on the idle page — which would plausibly stop its `setInterval`-driven heartbeat outright, unlike any of the ruled-out mechanisms above — would currently produce **zero** signal anywhere in this spec's output.
- This has not been confirmed with a live run (per the coordinator's own instruction, that specific sub-question needs one, not a guess). Phase 1 below closes the known, real gap (idle-seat issues going unobserved) and applies a defensive threshold increase justified independently by the triage's own production concern (a human alt-tabbing under a minute should not get bot-converted), rather than landing a fix keyed to an unconfirmed mechanism.

### Root cause, confirmed (second pass — Phase 2)
- **The actual bug: `syncedHeartbeats` (`src/modules/game-board/game-board.state.map.ts:55-66`) can write an explicit JS `undefined` into `GameState.heartbeats`, which Firestore's client SDK refuses to persist.** Line 61 is `if (localSeatId !== undefined) merged[localSeatId] = local[localSeatId];` — unconditional. On (at least) the match's first turn, the turn-holder's local buffer (`localGameState`, seeded by `cloneDeep(serverGameState)` in `game-board.state.hook.ts:31-32` the instant `isMyTurn` first becomes true) can be cloned from a `serverGameState` snapshot taken *before* this seat's own first `writeHeartbeat` call has round-tripped back through `onSnapshot` — a real race, since `useHeartbeat`'s "send immediately" write is an async network round trip, not synchronous with the clone. When that happens, `local.heartbeats` has no key at all for the local seat; `local[localSeatId]` reads as `undefined`; and the line above **assigns** that `undefined` onto `merged[localSeatId]` — unlike an absent key, a JS `obj[key] = undefined` assignment creates a real, enumerable own-property with value `undefined` (confirmed: `Object.keys`/`in`/`hasOwnProperty` all see it). Once any *other* seat's heartbeat differs between `local` and `server` (which happens on its own 15s cadence, continuously), `isSame` (line 64) is `false` for an unrelated key, so the whole `merged` object — including the poisoned `heartbeats.<localSeatId>: undefined` — is returned and becomes the new `localGameState`. It then rides along through every reducer call for the rest of that turn (most reducers shallow-copy `GameState`, preserving the `heartbeats` reference/value) until `EndTurn`'s `setGameState`/`saveGameState` calls `setDoc` with it, which throws synchronously (`game-board.engine.hook.ts:23-29`'s try/catch logs it as `console.error('Error handling game action:', error)` — the exact text captured). The write never lands, so nothing from that turn (including the position action) reaches Firestore — exactly the captured `landingIssues` entry.
- **Why this explains the earlier "document deleted mid-match" failures too, not just this run's symptom:** once a turn's write silently fails this way, the match stops advancing in Firestore even though both players are still actively playing through the UI — the document looks abandoned from the staleness check's point of view for a real, if indirect, reason. Phase 1's threshold raise and observability widening were reasonable, independently-justified defensive moves (kept, see Decisions), but they were not the primary fix — they could not have been, since nothing in Phase 1 touches `syncedHeartbeats`.
- Confirmed NOT present on every turn, only when the race lands against the local seat's own still-unsynced heartbeat — consistent with this being turn 1, seat 0 specifically (the host's very first turn, heartbeats barely a few hundred ms old anywhere in the system) rather than every turn.

### Root cause, confirmed (third pass — Phase 3): a lost-update race at the write boundary, not a timing issue
- **The actual bug: `setGameState` (`game-board.engine.hook.ts:20-33`) persists whatever `heartbeats` its caller's state object happens to carry, with no check against the engine's own always-current `gameState`.** For every non-realtime action during a turn (most army moves/positions/attacks — confirmed in Phase 1's Verified context, `game-board.actions.hook.ts:60-65`), the acting client calls `setLocalGameState(result.state)` — a plain value assignment, not a functional update. Separately, `game-board.state.hook.ts`'s seat-sync effect (`lines 26-43`) also calls `setLocalGameState(synced)` whenever a fresher `serverGameState` arrives (e.g. the peer's own `writeHeartbeat` landing, confirmed firing every ~15s in the trace). Both are independent producers of the SAME piece of React state, and neither merges with the other — whichever commits last for a given render fully replaces the local buffer. Because bot-driven UI actions fire in a rapid, synchronous burst (several moves/positions per turn, only the e2e driver's own `waitForStepEffects` polling in between, not a wait for this specific sync), the game-action writes consistently outrun the Firestore-round-trip-dependent sync effect for the whole turn: the peer's heartbeat sync never gets a chance to "stick" in the buffer before being overwritten by the next action's own `setLocalGameState`, which is still built from the pre-sync, turn-start snapshot. The result: `localGameState.heartbeats[otherSeat]` stays frozen at whatever it was when the buffer was first seeded (`cloneDeep(serverGameState)` at turn start), for the whole turn, no matter how many real heartbeats the peer sends in the meantime. When `EndTurn` finally calls `setGameState(localGameState, ...)`, that frozen, stale peer heartbeat is what gets written — overwriting the peer's real, fresh value that is *already* sitting correctly in the live Firestore document at that moment. This is a genuine lost update, not a race against time: the correct data exists, in Firestore, right up until this write clobbers it.
- **Why Phase 1/2 didn't catch this:** Phase 2 fixed a *different* defect in the same function (`syncedHeartbeats` creating an explicit `undefined`) — real, confirmed, and still correct to keep fixed — but `syncedHeartbeats` only runs inside the turn-buffer sync effect, one of the two racing producers; it was never the thing deciding what actually gets persisted. Phase 1's threshold/observability changes don't touch this path at all.
- This explains both of the two earlier "document deleted mid-match" live-run failures as well: whenever a turn's `EndTurn` write clobbers a peer's heartbeat back to an old value, every client's next staleness check (correctly, given the now-corrupted document) sees that peer as stale and converts it — the staleness mechanism was working exactly as designed throughout; the data it was reading was simply wrong.

### Root cause, confirmed (fourth pass — Phase 4): the write-boundary merge still rolls back the ACTING seat's own heartbeat, every single turn
- **The actual bug: `syncedHeartbeats` preserves the acting seat's own key from `local` (its first argument) at both call sites, and the turn buffer never refreshes that key after seeding it at turn start.** `withSyncedSeatManagement`'s own per-seat sync (`game-board.state.map.ts:22-23`) explicitly skips the local seat for `isBot`/`isVacant`/`reclaimRequested` — a deliberate, correct choice, because the turn-holder genuinely can have in-flight optimistic mutations to those fields during the turn. `syncedHeartbeats` was written by analogy to that same "never clobber the turn-holder's own in-flight state" rule, but heartbeats do not fit it: nothing in the turn buffer ever legitimately mutates a seat's own `heartbeats` entry — it is seeded once, by `cloneDeep(serverGameState)`, at turn start (`game-board.state.hook.ts:31-32`), and then never touched again by any gameplay reducer for the rest of the turn (confirmed: grepped every reducer under `src/modules/game-rules/` for `heartbeats`, zero hits outside `game-setup.reducer.ts`'s initial seed and `player-exit.service.ts`'s delete, neither of which runs mid-turn for the acting seat). Meanwhile `useHeartbeat` keeps writing that same seat's own heartbeat every 15s throughout the turn, completely independent of the buffer, and those writes round-trip back into `gameStateRef.current` within milliseconds (confirmed in the capture: seat 1's own `writeHeartbeat`s landed at 576970→591972→606971→...→696971, all visible). So at `EndTurn`'s `setGameState` call, `result.state.heartbeats[localSeatId]` (from `syncedHeartbeats`'s first argument, the buffer-derived `result.state`) is the stale turn-start value, while `gameStateRef.current.heartbeats[localSeatId]` (the second argument, never read for this key) is the genuinely fresh one — and the function returns the stale one, every time, for every turn, not a rare race.
- **Why architect-b's Phase 3 Finding 2 accepted this as safe, and why that was wrong.** The accepted reasoning was that `useHeartbeat`'s next tick (≤15s later) "self-heals" the rollback before `STALE_THRESHOLD_MS` (120s) notices. That reasoning only considered the value as something a LATER write would eventually correct — it did not account for the fact that the ROLLED-BACK value itself gets **written to Firestore and is live** for every other client's staleness check in the window between this `EndTurn` and the next `writeHeartbeat` tick. That window recurs on every single turn, for the whole match, not once. Over a 25-round match (the e2e spec's actual length) this reliably trips 120s somewhere, exactly matching the observed stall.
- **Why Phase 2 and Phase 3 didn't catch this:** Phase 2 fixed a different defect in the same function (an explicit `undefined` assignment) and did not touch the own-key-preservation branch at all. Phase 3 added the `setGameState`-boundary call to `syncedHeartbeats` specifically to fix PEER heartbeats — correct and still necessary — but reused the function's existing own-key contract unchanged, carrying the bug forward into the new call site. Both passes' regression tests exercised only a peer seat's heartbeat (confirmed: `game-board.state.map.test.ts:216-232`'s own-key cases test the behavior as a documented feature, not a bug, and `game-board.engine.hook.test.ts:727-759`'s Phase 3 test never varies seat 0's — the acting seat's — heartbeat between `liveState` and `staleCallerState`).

### Root cause (fifth pass — Phase 5): a different bug — the e2e harness can hang indefinitely when a turn's own `isMyTurn` auto-expires mid-step, confirmed mechanism, exact turn-5 trigger not pinned
- **Confirmed mechanism.** `turn-timer.hook.ts`'s `useTurnTimer` runs an independent, client-side 120-second timer for whichever seat's turn it currently is, gated only on `isMyTurn && gameStatus === 'playing'` — with no awareness of, or coordination with, the e2e harness's own per-turn work (the `BOT_STEPS` loop's three steps plus the final explicit End Turn click). If that harness-side work for a given turn takes 120 seconds or more of real wall-clock time, this timer fires its own, genuine `GameAction.EndTurn` dispatch (through the same `onAction`/`setGameState` pipeline every UI click uses, confirmed via `game-board.hook.ts:29,109-113`) *out from under* the harness, while it is still mid-turn.
- The moment that happens, `isMyTurn` flips to `false` for the acting seat's own page. Every action button the harness might still be about to click is affected, in one of two ways, both confirmed by reading the real component code: the **End Turn** button is conditionally *rendered* (`ActionsPanel.tsx:69`, `{isMyTurn && (<Button data-testid="actions-panel-end-turn">...)}`), so it vanishes from the DOM entirely; every *other* action button (Position, Attack, Deploy, Upgrade, BuyCard, Abilities — `ActionsPanel.map.ts:60,69,81-86,98-103,112-118,136`) stays in the DOM but has `!isMyTurn` folded into its `disabled` expression, so it becomes permanently unclickable for the rest of that (now-over) turn.
- Nearly every Playwright action call the harness issues against these targets — `clickTile`/`clickActionButton` (`e2e/bot-ui-actions.ts:129-135`, used throughout `performUiAction`/`performEvent`), two of `resolveCombat`'s four clicks (`:161,171`), every click in `clickUseCard`/`clickUseWealthyCard`/`buyAbility` (`:178-205`), and the spec's own final End Turn click (`e2e/bot-vs-bot-ui.spec.ts:321`) — has **no explicit `{timeout}` option**. Playwright's own documentation for these methods (confirmed by reading the installed `1.62.1` `.d.ts`, `node_modules/playwright-core/types/types.d.ts:2093-2099`) states the default is `0` — no timeout — changeable only via an `actionTimeout` config option or `page.setDefaultTimeout`, neither of which this repo sets anywhere (`playwright.config.ts` re-read in full this pass; grepped `actionTimeout` repo-wide, zero hits). So once a target the harness is waiting on will never become actionable again this turn, the call doesn't fail fast or time out at `SYNC_TIMEOUT_MS` (15s, the bound every *Node-side* poll in this spec uses) — it hangs silently for whatever remains of the test's own `test.setTimeout(10 * 60 * 1000)` (`:256`). This produces exactly the observed symptom: no console error, no page error, no failed request (a Playwright actionability wait is not a JS exception — nothing on the page itself is wrong), nothing captured again, and a teardown error naming whichever unbounded locator call happened to be in flight when the 10-minute budget ran out.
- **This is not a hypothetical mechanism — it is already visible, non-fatally, in the real capture from the run that confirmed Phase 4.** `e2e/.bot-self-play-captures/1792146328698/report.json`'s turn-1 "end"-phase entry (seat 0) shows a ~120,024ms gap, matching `TURN_DURATION` almost exactly, between the harness's own successful End Turn write landing (`now=1792146334882`) and the live document's `turn` field actually advancing (`now=1792146454906`) — meaning this exact race already cost turn 1 about two minutes of real time, self-recovering (something the harness was waiting on eventually became actionable again, or the already-in-flight call happened to resolve once the state caught up) before the 10-minute ceiling. By turn 5, whatever the harness is waiting on evidently does not recover in time.
- **Why turn 5 specifically, not confirmed.** The exact step/action scheduled for turn 5 (one of `cardStrategy`/`purchases`/`armyActions`, and which specific sub-action within it — a move, a position, an attack requiring `resolveCombat`, or a Deploy/Upgrade/BuyCard event) is not pinned down this pass; doing so needs either a fresh live trace scoped to that turn, or (more directly) converting every currently-unbounded call above to a bounded one so the *next* real run throws a concrete, attributable Playwright timeout error (naming its own locator) instead of hanging silently — turning an unattributed 10-minute stall into a diagnosable, ≤15s failure. The second option is this plan's proposed first step (see Decisions) precisely because it is the same "widen observability first" move that found the real bug at every prior phase of this task (Phase 1 → Phase 2; Phase 3 → Phase 4), rather than guessing at which exact action turn 5 happens to exercise.
- **Ruled out:** a game-state/game-rule bug specific to turn 5's content (e.g. a disabled-button mismatch between the bot's oracle and the real UI, the class of bug this task originally opened with for the Position button). Nothing above depends on what turn 5 specifically does — the `isMyTurn`-driven unmount/disable and the unbounded click are both unconditional, generic properties of every turn once the 120s auto-`EndTurn` race is lost. A fix targeting one specific action (e.g. "fix Attack's disabled condition") would not address the underlying class of bug and could still fail on a different step at a later turn.

### Root cause (sixth pass — Phase 6): confirmed — the harness's explicit End Turn click races the app's own, correct, 700ms "no actions remain" auto-end-turn
- **Fifth pass's "turn 5, not confirmed" question is answered, but the answer is a different mechanism than the one guessed at.** Bounding every click (Phase 5) did exactly what it was meant to: the next real run failed fast (22.5s) with an attributable `TimeoutError` on `actions-panel-end-turn`. But the failure is on **turn 1**, and 22.5s total (of which the failing click itself accounts for the full bounded 15s) is nowhere near the 120s `turn-timer.hook.ts` race Phase 5's root cause described — that race may still exist as a real, separate, rarer risk (see Risks below), but it is not what is failing here, and three fresh, instrumented, real `test:e2e` runs this pass never observed it once.
- **The actual, fully confirmed mechanism: a second, independent, much faster auto-`EndTurn` source — `game-board.hook.ts`'s "Automatically end turn when player has no valid moves or affordable strategic actions left" effect (lines 63-84, Verified context above) — races the harness's own explicit End Turn click, and routinely wins.** This effect is **not a bug**: it is existing, intentional, already-documented production behavior (confirmed in `docs/architecture/game-mechanics.md` and `docs/architecture/systems-and-visuals.md`) that ends a human or bot player's turn 700ms after `hasPlayerRemainingActions` goes `false`, exactly the correct thing to do when a player genuinely has nothing left to do. On turn 1 specifically, after the bot's lone starting army positions (its only legal action; every purchase/card/ability branch in `hasPlayerRemainingActions` is unaffordable or empty this early), `hasPlayerRemainingActions` correctly returns `false`, and this effect's 700ms timer reliably fires *during* the harness's own `waitForStepEffects` poll for that same action (which routinely takes at least one 300ms tick beyond the write's own round trip) — i.e. before the harness's loop ever reaches its explicit `page.getByTestId('actions-panel-end-turn').click(...)` call. By the time that click runs, the real `EndTurn` has already landed (confirmed directly: the live document's `log` already contains the normal "It's now BotGuest_...'s turn." entry, `currentPlayerIndex` is already `1`, both seats' `isBot` is still `false` and both heartbeats are fresh — ruling out every staleness/heartbeat mechanism from Phases 2-4), `isMyTurn` has already flipped to `false` for the acting seat's page, and the End Turn button has already unmounted (same `ActionsPanel.tsx:69` mechanism Phase 5 documented for the 120s case). The harness's click then has nothing to find and waits the full `SYNC_TIMEOUT_MS` before throwing — exactly the observed, 100%-reproducible (3/3 fresh runs) `TimeoutError`.
- **Why this is a harness bug, not a game bug, and not the same bug as Phase 5's.** The game is doing exactly what it should: a player (bot or human) with zero remaining legal actions should not be stuck waiting for someone to click End Turn. The harness's bug is in assuming it must *always* perform an explicit End Turn click — it has no way to know the app may have already done this for it. This is a distinct root cause from Phase 5's `turn-timer.hook.ts`/120s race: different trigger (`hasPlayerRemainingActions` going false vs. a fixed 120s wall-clock timeout), different timescale (700ms vs. 120s), different turn (reliably turn 1, not "eventually, around turn 5"). Phase 5's fix (bounding every click) was still the right, necessary step — it is what turned this from a silent 10-minute/until-teardown hang into a concrete, attributable, fast failure this pass could actually root-cause.
- **Why Phases 1-5 never hit this before:** every earlier real `test:e2e` run that got far enough to exercise turn 1's End Turn click either (a) was still blocked by one of the four already-fixed heartbeat/write bugs before reaching this point, or (b) in the one post-Phase-4 run that got past all of them, happened to have the heartbeat-rollback bug (Phase 4's own target) *also* in play, which this pass's fix-free re-runs no longer have — once every earlier mechanism was closed, this one, previously masked, became the very next thing in the critical path, consistent with this task's own established pattern (each fix exposes the next bug underneath).

### Root cause (seventh pass — Phase 7): confirmed — a harness verification-timing bug, not a game bug or a flaky race

- **This is option (b) from the task prompt: a harness bug in how it verifies Deploy/Upgrade landed — checking a live document before the turn-buffer flush that would ever write it there.** `waitForStepEffects` is called separately for each of the 3 `BOT_STEPS`, immediately after that step's own `performUiAction`, each with its own fresh `SYNC_TIMEOUT_MS` (15s) window, checked against the live Firestore document. But Deploy, Upgrade, Position (`SelectResourcePosition`) and Move are not in `useGameBoardActions`'s `realTimeActions` allowlist (`game-board.actions.hook.ts:42-52`) — clicking any of their action buttons only calls `setLocalGameState`, an in-memory update with **no Firestore write**. The only things that ever flush that buffer to Firestore mid-turn are a realtime action (combat) or the app's own "no actions remain" 700ms auto-end-turn effect (`game-board.hook.ts:63-84`, the mechanism Phase 6 root-caused and made the harness tolerant of); the only thing that flushes it unconditionally is the turn's own explicit End Turn click, which this spec performs only **after** all 3 `BOT_STEPS` have run and been checked (lines 320-338).
- **For `purchases` specifically (where Deploy/Upgrade happen), the write genuinely cannot land within that step's own check window in the common case.** `purchases` runs before `armyActions`; while the acting seat still has an unacted army going into `armyActions` — true on essentially every turn where the bot has any army at all — `hasPlayerRemainingActions` is still `true` right after `purchases` finishes, so the 700ms auto-end-turn effect does not fire during `purchases`'s own wait. The deploy/upgrade genuinely does land, just later — once `armyActions` finishes and the bot's whole planned turn is done (auto-end-turn fires), or at the harness's own explicit End Turn click, both of which happen after `purchases`'s own check has already given up and recorded the false "never landed."
- **Confirmed directly against the real capture, not just the code trace.** `e2e/.bot-self-play-captures/1792155502116/`'s own screenshots for the two flagged turns examined this pass (turn 13 "deployed", turn 27 "upgraded") show the supposedly-missing log line already present in the live Event Log by the end of that same turn — the action unambiguously landed; the check was wrong, not the game.
- **Why `armyActions`'s own checks (moves/positions/attacks) never show this symptom.** `armyActions` is the *last* `BOT_STEP`; by the time its own `waitForStepEffects` call runs, the bot's entire turn is already decided, so `hasPlayerRemainingActions` is normally `false` by then and the 700ms auto-end-turn effect reliably fires within that step's own 15s window — the structural gap this bug depends on (an intermediate step whose effect won't flush before a later step in the same turn needs to run) doesn't exist for the last step.
- **Why this looks "intermittent" across the 50-turn run but is actually deterministic.** Deploy and Upgrade both become rare as a match progresses (`nextArmyCost` grows every deploy; `attackPower` caps at 4 — `player-actions.reducer.ts:17,72,87`), so the 10 flagged turns are plausibly every single occurrence of a Deploy or Upgrade in this entire 50-turn match, not a flaky subset of a larger population that mostly "landed." Nothing in the mechanism above depends on chance — any `purchases`-step Deploy/Upgrade on a turn where the acting seat still has an unacted army afterward will reproduce this 100% of the time.
- **Ruled out:** (a) a real Deploy/Upgrade application bug — the action always applies correctly, confirmed by the screenshots; (c) a rare timing race in the spirit of Phase 5/6 — this is not a race that sometimes loses; it is a structural ordering mismatch between when the check runs and when the write can first possibly exist, and it reproduces on every qualifying turn, not probabilistically.

### Root cause (eighth pass — Phase 8): could not reproduce; a turn-1 "attack" is structurally unreachable under current default-settings code, not confirmed as either a real app bug or a harness logic bug
- **Not reproduced.** Two full, clean real `test:e2e` runs this pass (instrumented to print every `BOT_STEP`'s planned `moves`/`positions`/`attacks`/`events`, plus the acting army's own array and tile right before `armyActions` runs) both completed all 25 rounds and passed; `attacks` was `[]` on every single logged turn in both runs, and no army ever moved off its own base tile for the entire span of either run. This directly contradicts the premise handed to this pass (that a real run showed the oracle planning `attack` on turn 1).
- **Traced why, by construction, not just by absence of evidence: an `attack` entry on turn 1 requires an army to already be co-located with an enemy or a monster *before any action has been taken this turn* — and that is structurally impossible under the current map-generation and game-setup code for a 2-player match with default settings.** `applyBotArmyActions` only scores `attack-player-<id>`/`attack-monster-<id>` for an army's **current** tile (Verified context above); an army can only ever reach a different tile by first spending its one action on a `Move` (which immediately sets `hasActed = true`, per `movement.reducer.ts:105,114`, excluding it from further scoring in the same call) — so within a single `applyBotArmyActions` invocation, an army that has not yet acted this turn can only attack something already on the tile it started the turn on. On turn 1, that tile is always the player's own, freshly-initialized Base tile, which `map-generation.ts:11`'s `continue` guard unconditionally excludes from ever receiving a monster, and which `game-setup.reducer.ts` seeds with only that same player's own army as an occupant. Both players' Base tiles are also always far enough apart (Manhattan distance 9 on the current `5×6` grid) to never collide. No randomness in map generation (`Math.random()` in `generateIslandTerrain`) can change this, because the Base-tile exclusion runs unconditionally, before any random roll. Separately, `defaultGameSettings.baseResourceAmount = 1` guarantees a Position action (priority 6, inserted into `possibleActions` before the move loop, so it wins every tie under JS's spec-stable sort) is always available and always outranks every possible `Move` on turn 1 too — so under the *current* balance, an army essentially never leaves its base at all in two-bot self-play (confirmed empirically: zero moves in either 50-turn run this pass), making even an *indirect*, later route to "army happens to already be on a monster tile at the start of some future turn" implausible to reach quickly, though not proven impossible over a very long match (the standalone balance simulator's non-empty `attackerWinPct`, Verified context above, shows combat does eventually happen in longer/non-UI-constrained simulated play).
- **Most likely explanation for the originally-reported failure: an environmental/shared-working-tree anomaly, not a reproducible defect in the code as it stands.** This pass directly observed the same class of problem twice in this exact session — two `test:e2e` attempts failed before the app server even started, due to a different, concurrent, uncommitted task's in-progress files breaking the production build's ESLint pass at that moment (Verified context above) — which is the exact "shared working tree, non-deterministic environment" failure mode this task's own `progress.md` already logged three separate times on 2026-10-15 (a stashed WIP collision, an active peer session's broken typecheck, and a different committed task's broken build) and that `lessons-learned.md`'s "Concurrent sessions & git" section exists to warn about. A transient, different build/runtime state at the moment of the originally-reported run (e.g. a concurrently-edited reducer or component file mid-save) is a more defensible explanation than a code-level bug this pass's structural analysis shows to be impossible under the code actually in the working tree now.
- **Neither hypothesis (a) nor (b) from the task prompt is confirmed.** (a) A real app bug in Attack's enablement logic is not supported: `canAttack` (`ActionsPanel.map.ts:37-41`) reads the same, unfiltered `GameState.map` data the oracle's reducers read (no fog-based data redaction exists in this codebase, Verified context above), so there is no mechanism by which the live UI's `canAttack` could evaluate `false` while the oracle's identical reducer logic, run against the same data, evaluates "attack is legal" `true`. (b) A harness logic bug in `planNextStep`/`applyBotArmyActions` choosing "attack" when nothing is attackable is also not supported: the same reducer that would have to produce this bug is the one the live app runs too (`bot-army-actions.reducer.ts` has no separate "harness" and "app" copies — both call the same `applyBotArmyActions` export, confirmed via `STEP_RUNNERS` in `bot-ui-actions.ts:70-74` and the reducer's own module), so a bug in its `attack` scoring would be a production bug reachable by a real (non-bot) player's attack button too, not a harness-only defect; and this pass's own live runs never got the oracle to plan one at all.

### Root cause (ninth pass — Phase 9): confirmed — `addPlayerToGame` never clears a tile's pre-existing `.monsters` array when converting it to a newly-joined player's Base
- **The defect, precisely.** `generateIslandTerrain` (`game-setup.reducer.ts:96`) runs once, over the entire map, immediately after `initializeGame` seeds only the already-present seats' (creator's, and in the solo-plus-bots path, each bot's) Base tiles. A guest who joins a real multi-human match later, through `addPlayerToGame`, has no seat and therefore no pre-marked tile at that point — `generateIslandTerrain`'s only protection (`map-generation.ts:11`'s `type === Base && owner !== undefined` guard) cannot apply to a tile nobody has claimed yet. That tile is terrain-generated like any other unclaimed tile; at the guest's fixed corner position (Manhattan distance 4 from center under the default `5×6` grid), it has a 35% chance of being rolled `IslandType.Monster` with a non-empty `monsters` array (always ≥1 entry, confirmed above). When the guest later joins, `addPlayerToGame` (`player-join.reducer.ts:60-68`) overwrites every field needed to make the tile look like a normal Base (`type`, `owner`, `occupants`, `resources`) but omits `.monsters` — the one field `generateIslandTerrain` could have populated that this conversion doesn't already touch.
- **Confirmed impact, both on the bot harness and on a real human player.** On an affected guest's turn 1: the bot oracle's `attack-monster` scoring (`bot-army-actions.reducer.ts:48`, priority 7) checks only `monsters.length > 0` and outranks `position` (priority 6), so it plans and clicks Attack; the live UI's `canAttack` requires `type === 'monster'` (already clobbered to `'base'`), so the button never enables — the harness's exact reported "Attack button disabled 15s" symptom. Independently, `canPosition` also fails for the same leftover `monsters` array (`ActionsPanel.map.ts:29-35`'s `!currentTile.monsters || ...length === 0` guard) even though `type` alone would otherwise qualify the tile — so a real human player hitting this would find their only starting army's Position *and* Attack buttons both disabled on their very first turn, a genuine dead-turn game-design bug, not merely a harness artifact.
- **Scope of the fix: exactly one write site.** The repo-wide grep (Verified context above) confirms `player-join.reducer.ts:61` is the only `.type = IslandType.Base` assignment that runs after `generateIslandTerrain`; the other two (`game-setup.reducer.ts:57,83`) are both pre-terrain-generation and already protected by `map-generation.ts:11`'s guard, confirmed unaffected. No other Base-tile-conversion path exists anywhere in `src/`.

## Decisions
- **Widen the e2e harness to observe the idle seat, not just the acting one.** Instead of discarding `issueBuffers[actingSeat]`'s stale content when a seat's turn starts, drain it and flag it (attributed to "idle before this turn") before clearing it. This is a real, confirmed gap independent of which exact mechanism turns out to be at fault — a crash or hang on the page that isn't currently acting should never be invisible to this suite. Rejected: leaving it as-is and relying solely on the threshold increase below — that would mask a real crash instead of surfacing it, and "fix the test's blind spot" is itself in scope per the triage ("fix the root cause... whichever is actually wrong").
- **Raise `STALE_THRESHOLD_MS` from 45s to 120s** (`game-board.staleness.hook.ts:6`). Both browser contexts in this spec stay open and connected for the test's whole duration — there is no legitimate disconnect to detect here, so any value comfortably above real-world transient gaps (CI CPU contention, a brief Firestore SDK reconnect/backoff, or whatever the widened issue-buffer draining surfaces) closes the observed failure without depending on pinning the exact mechanism. 120s is also a direct answer to the triage's second, independent question: a real human alt-tabbing during an opponent's turn for under a minute should not be silently converted to a bot; 45s already fails that bar, 120s comfortably clears it. Rejected: leaving `STALE_THRESHOLD_MS` unchanged and fixing only the observability gap — if the real cause turns out to be generic transient CI/SDK flakiness rather than a reproducible crash, a 45s threshold would still misfire occasionally with no code bug to fix. Rejected: a much larger value (e.g. 5+ minutes) — this is a production disconnect-detection feature, not just a test knob; 120s is the smallest increase that is comfortably safe against both the test's own worst-case per-turn wait budget (~60s) and casual real-world alt-tabbing, without materially degrading how quickly a genuinely dropped player's seat gets handed to a bot.
- `WARNING_THRESHOLD_MS` (`ConnectionWarningDialog.hook.ts:12`, 25,000) is unchanged — it still opens the "Connection lost" warning at the same absolute delay; only the countdown to takeover gets longer (now ~95s instead of ~20s), which is the intended effect of the increase. Its stale comment ("leaves a 20s countdown window") needs updating to match.
- Not fixing a specific code bug yet, because none is confirmed. If the widened issue-buffer draining (once it runs for real, Phase 1 step 5) shows a genuine idle-page crash or error, that is a new, separate root cause requiring its own fix — report it to architect-b rather than silently patching it under this plan's Contracts, which do not cover it.

### Decisions (second pass — Phase 2, the real fix)
- **Fix at the exact source: `syncedHeartbeats` must never assign an explicit `undefined` for the local seat's key.** Guard the assignment on whether `local` actually has the key (`localSeatId in local`); if it doesn't, `delete merged[localSeatId]` instead of assigning `undefined` to it, so the result has a genuinely absent key (matching every other "no heartbeat yet" case already handled elsewhere in this same codebase, e.g. `findStalePeerIds`'s `lastSeenAt !== undefined` check and the doc comment on `GameState.heartbeats` itself — "a missing key means no heartbeat yet"). This is the smallest change that fixes the actual defect: one `if` added around one line, no behavior change for the common case (local already has the key).
- Rejected: a blanket "strip `undefined` recursively before every `setDoc`" guard in `saveGameState`. That would mask this (and any future) bug at the write boundary instead of fixing the one place that creates the invalid value, violates "fix the root cause, not the symptom" (skill `testing`'s Bugs rule), and would silently swallow a real future bug of the same shape anywhere else in the state tree without ever surfacing it in a test. The source fix is one line; there's no KISS case for the broader net here.
- Rejected: seeding `useHeartbeat`'s first write synchronously into the local buffer itself, or delaying the turn-buffer clone until the seat's own heartbeat is confirmed present server-side. Both are real alternative fixes to the *race* (why `local` lacks the key at all on turn 1), but `syncedHeartbeats` has a second, independent duty regardless of why the key is missing: it must never emit an explicit `undefined` for *any* key, including a peer's (e.g. a peer who has genuinely never heartbeated yet, or whose entry a concurrent `convertSeatToBot` deletes mid-sync). Fixing only the turn-1 race would leave the `syncedHeartbeats` function itself still capable of producing the same invalid shape from a different trigger; fixing the function closes the whole class of bug at once.
- Keep Phase 1's 120s `STALE_THRESHOLD_MS` and the widened e2e issue-buffer draining — see their own Decision bullets above. They are not redundant with this fix: the threshold raise is independently justified by the triage's human-alt-tab concern, and the issue-buffer widening is exactly what surfaced this bug and should stay to catch the next one.

### Decisions (third pass — Phase 3, the write-path fix)
- **Fix at the single actual point of persistence, not the racing in-memory buffer.** `setGameState` (`game-board.engine.hook.ts`) already has (via `gameStateRef`, established in the same file for the same "avoid stale closures without widening a `useCallback`'s deps" reason) a handle on the engine's own always-current `gameState`. Before calling `saveGameState`, re-merge `result.state.heartbeats` against `gameStateRef.current.heartbeats` using the existing `syncedHeartbeats` (export it from `game-board.state.map.ts`; reuse, don't duplicate — it already has the correct "keep the acting seat's own in-flight value, take every other seat's latest known value" semantics, and already carries Phase 2's undefined-guard). This closes the race regardless of how many lost updates happened to the in-memory turn buffer along the way — the only thing that matters is that the single write to Firestore is always correct. **This closes the race for every *peer* seat's heartbeat, but `syncedHeartbeats` still preserves the acting (local) seat's own key from `result.state` (its first argument) — so the exact same lost-update shape can still roll the acting player's own `heartbeats` entry back to a turn-start value when it writes.** This is not a gap left to chance: `useHeartbeat` (`game-board.heartbeat.hook.ts`) keeps writing the acting player's own seat every 15s *regardless of whose turn it is*, independent of the turn buffer entirely, so any such self-rollback is overwritten by that seat's own next heartbeat well inside the 120s `STALE_THRESHOLD_MS` — self-healing by a hook this fix does not touch, not a property `syncedHeartbeats`'s own contract guarantees. A reader modifying `syncedHeartbeats` or the merge call later should not assume the own-key preservation is unconditionally safe outside of that reliance. Rejected: trying to fix the race in the turn buffer itself (e.g. making every `setLocalGameState` call a functional updater that merges heartbeats) — this would require touching every call site that writes to `localGameState` (`game-board.actions.hook.ts`, `game-board.card-actions.hook.ts`, `game-board.local-actions.hook.ts`, `game-board.tile-click.hook.ts`, each already doing a plain value `setLocalGameState` for its own, unrelated reasons) instead of the one place that actually persists data; bigger surface, same result, and still wouldn't protect a future caller of `setGameState` that bypasses the buffer. Rejected: a transaction around every game-state write — this project already deliberately avoided a whole-document transaction for the heartbeat write itself (the separately-tracked write-contention bug); adding one here for every ordinary game action would reintroduce exactly that performance/contention concern for a problem a plain merge-before-write already solves.
- Keep `game-board.state.hook.ts`'s seat-sync effect as-is. It is no longer the thing responsible for write *correctness* (Phase 3 moves that guarantee to `setGameState`), but it is still the thing responsible for what the UI *displays* mid-turn (e.g. `ConnectionWarningDialog` reads the live, unbuffered `serverGameState` directly per `docs/architecture/systems-and-visuals.md`, but other consumers may read the buffered value) — removing it would be an unrelated regression, not a simplification.
- The temporary `[DEBUG heartbeat-trace]` logging the coordinator added (uncommitted) should be removed once Phase 3's fix is confirmed by a real passing e2e run — it was a one-time diagnostic aid, not permanent instrumentation; keeping ad-hoc `console.error` calls in production hot paths (`onSnapshot`, every `saveGameState`, every `writeHeartbeat`) that are not genuinely intended for production logging is itself a code-quality regression `npm run lint`/`code-standards` would flag as noise. Rejected: keeping it permanently — this codebase has no precedent for always-on verbose per-write console logging in the engine hooks, and this specific bug's regression test (Phase 3's Contracts) is the right permanent safeguard, not console spam.

### Decisions (fourth pass — Phase 4, the acting seat's own heartbeat)
- **Stop special-casing the local seat at all in `syncedHeartbeats`; always take every seat's heartbeat, including the acting seat's own, from `server`.** This is judged against both existing call sites, not just the one that surfaced the bug (per this phase's brief): at `withSyncedSeatManagement` (the mid-turn display-buffer sync), the local seat's own heartbeat was never legitimately "in-flight gameplay state" to protect either — it is the same side channel, same `useHeartbeat` writer, same reasoning — so dropping the special case there too is correct, not merely harmless, and keeps both call sites consistent with one shared contract instead of two different ones. This also fully subsumes Phase 2's explicit-`undefined` guard: the new implementation never reads an individual key out of `local` to build the result (`{ ...server }` is the whole merged value), so it structurally cannot produce an own-enumerable-`undefined` property for any key, including the local seat's — the `in`/`delete` guard becomes dead code and is removed, not kept alongside the new behavior. Narrows the function's signature from 3 params (`local`, `server`, `localSeatId`) to 2 (`local`, `server`); `localSeatId` is no longer needed by the function body, only by callers that still compute it for other, unrelated reasons (`withSyncedSeatManagement` still needs `localPlayerId`, the string, for its own per-seat-field guard — unaffected).
- **Rejected: keep the own-key preservation but refresh it from `gameStateRef.current` instead of `result.state` only at the `setGameState` call site, leaving `withSyncedSeatManagement`'s call untouched.** This would fix the confirmed bug (the write boundary) but leave the *display*-buffer sync still carrying the same incorrect "preserve my own stale value" behavior — not a path that writes to Firestore today, but the same unsound reasoning the Phase 3 review already found wrong once; fixing the write boundary while leaving the read-side function's documented contract saying the opposite would mislead the next reader and risk the same bug resurfacing if a future caller (or a refactor) starts trusting that documented preservation. One shared, correct contract for the whole function is simpler and removes the risk at its root (skill `kiss-dry-solid`: fix the one function's contract, not every caller around it).
- **Rejected: add a `syncedHeartbeats` variant (e.g. a second exported function, or a boolean flag) that drops the own-key preservation only for the `setGameState` call site.** No caller of `syncedHeartbeats` has a situation where preserving the local seat's own stale heartbeat is actually correct (see root-cause trace: it is never part of a legitimate in-turn gameplay mutation at either call site) — a flag or second function would be two ways to do the same thing with no caller needing the old behavior, which is exactly the "boolean flags inside a component/function instead of a real behavior change" anti-pattern the `kiss-dry-solid` skill warns against (Open/closed: extend with the right behavior, not a flag nobody opts out of).
- Keep Phase 3's `setGameState`-boundary merge itself (re-syncing from `gameStateRef.current` right before `saveGameState`) — still the correct place to guarantee the final persisted value is correct, regardless of what the buffer carries; this phase only changes what `syncedHeartbeats` returns, not where or when it's called.
- The now-stale inline comment in `game-board.engine.hook.ts`'s `setGameState` (the "NOTE: syncedHeartbeats preserves the ACTING seat's own key..." block added for Phase 3 Finding 2) is removed and replaced — it described a caveat that no longer applies once the function no longer has that behavior; leaving it in place would actively mislead a future reader into thinking a protection exists that doesn't.

Not proposed as "the fix" — a question for whoever reviews the bounded run's actual failure, not a pre-emptive workaround.

### Decisions (sixth pass — Phase 6)
- **Fix in the e2e harness only: before the explicit End Turn click, check whether the turn has already ended; if the click itself still throws a `TimeoutError`, re-check once before deciding it's a real failure, rather than treating every timeout as a bug.** The 700ms auto-end-turn effect is correct, documented, shipped behavior — there is no game-rule or production-code change to make here, unlike every prior phase of this task. Concretely: read the live game state once before attempting the click; if `currentPlayerIndex` has already moved past `actingSeat` (or `status` is no longer `Playing`), skip the click entirely — the turn is already over, nothing to click. This handles the common, now-confirmed case (turn 1, and any other turn where the acting seat's last action leaves it with nothing else to do) without ever attempting a click that was always going to fail. For the narrower timing window where the auto-end-turn fires *during* the click attempt itself (the cheap pre-check passed, but the 700ms timer or the button's unmount lands between the check and the click), catch the resulting `TimeoutError` and re-check live state once more before deciding: if the turn has since advanced past `actingSeat`, swallow the race (it is not a bug) and proceed exactly as if the click had succeeded; if the turn genuinely has not advanced, rethrow the original `TimeoutError` so a real stuck-End-Turn bug (the kind this task has repeatedly found and fixed) still surfaces exactly as before. This reuses `readGameState`, already defined and used throughout this file — no new helper, no new dependency.
- **Rejected: just increase `SYNC_TIMEOUT_MS` or retry the click.** Neither addresses the actual cause (the button is never coming back this turn, regardless of how long or how many times the click is retried) — it would only make the already-slow failure case slower, or in the retry case, could in principle re-click a *future* turn's End Turn button if the loop iteration advanced in between, which would be a worse bug than the one being fixed.
- **Rejected: disable or delay the app's own 700ms auto-end-turn effect for e2e runs (e.g. an env-gated flag).** This is the "change production code to make a test pass" anti-pattern this task has specifically avoided at every other phase (Phase 5's own Decisions explicitly rejected the equivalent move for `turn-timer.hook.ts`). The auto-end-turn effect is correct and desirable for real players; a flag that disables it only for e2e would mean the suite no longer exercises this real, common code path at all.
- **Rejected: make the harness compute, from its own oracle (`planNextStep`'s returned `state`), whether the acting seat will have any remaining actions after this turn's `BOT_STEPS`, and skip the End Turn click proactively if not.** This would require re-implementing `hasPlayerRemainingActions`'s exact semantics a second time in the e2e harness (or importing it, which is possible since it's already a named export of `@/modules/game-rules` per its `index.ts`, confirmed by grep) — but even then, it only predicts the *common* case; the live-state check above is strictly more correct (it reacts to what actually happened, not a second, parallel prediction of it) and is no more code. Not adopted.
- **Scope note, not acted on: the same race could in principle hit a click *inside* `performUiAction`'s own per-action loops** (e.g. a multi-army turn where `applyBotArmyActions` returns several `positions`/`moves`/`attacks` entries for different armies in one `armyActions` step, and the *first* of them already leaves the player with nothing else to do, while the harness is still mid-loop clicking the *second*). This has not been observed in any of this pass's three runs (every reproduction was a single-army, single-action turn 1) and is not fixed here — flagged in Risks below for whoever hits it next, per this task's own "don't guess, re-root-cause against real evidence" rule.

### Decisions (seventh pass — Phase 7)
- **Stop checking per-`BOT_STEP`; accumulate every step's `EffectCheck`s and verify them once, after the turn is confirmed over (after the End Turn skip/click/race-catch logic and the `nextState` wait).** This fixes the actual mismatch directly: effects from non-realtime actions (Deploy, Upgrade, Position, Move) are only guaranteed to exist in Firestore once the turn's buffer has been flushed — by auto-end-turn or the explicit End Turn click — so the check should run after that point, not before it. `GameState.log` and the other fields these checks read only grow within a turn (confirmed in Verified context), so a check built from an earlier step and verified later cannot produce a false negative for a genuinely-landed effect; it still correctly flags a genuinely-never-landed one (the scenario this whole diagnostic exists to catch). Reuses the existing `waitForStepEffects`/`buildEffectChecks`/`EffectCheck` functions and types unchanged — only where and how often `waitForStepEffects` is called changes, plus `landingIssues`/`checks` becoming `turnChecks`, accumulated across the loop instead of consumed per iteration.
- **Rejected: special-case only the `purchases` step (or only Deploy/Upgrade events) to defer its check, leaving `cardStrategy`/`armyActions` checked per-step as today.** This would couple the fix to today's specific `BOT_STEPS` ordering and today's specific non-realtime action list — fragile, and it only patches the one combination this capture happened to exercise. The real mismatch (checking a live document before anything could have written to it) applies to any non-realtime action in any step that isn't last; fixing the general mechanism once, for the whole turn, is simpler and closes the whole class, not just this instance of it (`kiss-dry-solid`: fix the one actual cause, not each symptom).
- **Rejected: verify against the browser's own rendered state (e.g. scrape the Event Log DOM, or read React state) immediately after each step's click, instead of Firestore.** This would genuinely let the harness detect a step's action failing to apply at all (a true app bug) sooner, without waiting for the turn's end — a real advantage in principle — but it requires a second, different verification mechanism from the one every other check in this spec already uses (Firestore, the same ground truth the match itself converges on), adds a new kind of assertion with its own flake surface (scraping rendered text), and this spec has no existing precedent for it. Not adopted; flagged in case a future pass wants faster-than-end-of-turn failure detection for a specific action.
- **Rejected: add Deploy/Upgrade/Position/Move to `useGameBoardActions`'s `realTimeActions` allowlist so they persist immediately, matching what the per-step check already assumes.** This is a production-code behavior change made solely to satisfy a test's assumption — the same "change production code to make a test pass" anti-pattern Phase 5 and Phase 6 both already explicitly rejected for the unrelated turn-timer/auto-end-turn mechanisms. It would also substantially increase Firestore write frequency during ordinary gameplay (every Position/Move/Deploy/Upgrade click becoming its own round trip instead of batching into one End-Turn write) — a real performance/cost change nobody has asked for, to fix a test's wrong assumption about the app's own, intentional turn-buffering design (`docs/architecture/systems-and-visuals.md`'s "In-Memory Turn Buffering" section, already updated by this task's own Phase 2/4 docs-sync steps, documents this buffering as deliberate).
- **No production code, game rule, or `docs/architecture/*.md` change needed.** The turn-buffering/realtime-action design this bug depends on is correct, intentional, and already documented; only the test harness's assumption that every step's UI action is immediately visible in Firestore was wrong.

import { syncedHeartbeats } from './game-board.state.map';
// ...existing imports...

export function useGameEngine(gameId: string, playerId: string | null): UseGameEngineResult {
  const [gameState, setInternalGameState] = useState<GameState | null>(null);
  const [isLoading, setIsLoading] = useState(true);
  const { toast } = useToast();
  const router = useRouter();

  // Moved up from its old position (was after setGameState, now before it): the engine's own
  // always-current GameState, independent of any local turn-buffer race.
  const gameStateRef = useRef<GameState | null>(gameState);
  useEffect(() => {
    gameStateRef.current = gameState;
  }, [gameState]);

  const setGameState = useCallback(
    async (currentState: GameState, action: GameAction, payload?: unknown): Promise<void> => {
      try {
        const result = handleGameAction({ action, gameState: currentState, payload });
        if (result.state) {
          // A turn's own local buffer can lag the live server state for other seats' heartbeats
          // (game-board.state.hook.ts's sync effect races non-functional setLocalGameState calls
          // from in-turn actions and can lose). Re-sync from the engine's always-current
          // gameStateRef right before the one place that actually persists to Firestore, so a
          // stale buffered heartbeat for another seat can never overwrite that seat's real,
          // fresher value already sitting in the live document.
          // NOTE: syncedHeartbeats preserves the ACTING seat's own key from `result.state` (its
          // first argument), not from `latestServerState` — the same lost-update shape could still
          // roll this seat's own heartbeat back to a turn-start value. That is safe only because
          // useHeartbeat (game-board.heartbeat.hook.ts) writes this seat's own heartbeat every 15s
          // regardless of whose turn it is, self-healing well inside STALE_THRESHOLD_MS (120s) —

          // guarantees. Don't assume own-key preservation is safe if that hook's behavior changes.

            ? syncedHeartbeats(result.state.heartbeats, latestServerState.heartbeats, localSeatId)
            : result.state.heartbeats;
          await saveGameState(gameId, { ...result.state, heartbeats });
        }
      } catch (error) {
        console.error('Error handling game action:', error);
        toast({ title: 'Action Error', description: 'Could not process game action.', variant: 'destructive' });
      }
    },

  server: GameState['heartbeats'],
