**The exact remaining bug (historical — the finding that led to the plan above)**: Phase 3's fix in `game-board.engine.hook.ts`'s `setGameState` calls `syncedHeartbeats(result.state.heartbeats, gameStateRef.current.heartbeats, localSeatId)`. This correctly refreshes every PEER seat's heartbeat from `gameStateRef.current` (the engine's always-current live state) — that part works. But `syncedHeartbeats`'s contract (by design, inherited from its original use in `withSyncedSeatManagement`, where it made sense to avoid clobbering the turn-holder's own in-flight optimistic gameplay changes) explicitly PRESERVES the ACTING seat's own key from `result.state` (the first argument — the turn-buffer-derived caller state), not from `gameStateRef.current`. The turn buffer (`localGameState`) never refreshes its OWN seat's heartbeat entry once seeded at turn start — by design, nothing re-syncs a seat's own key into its own buffer — even though that same seat keeps writing fresh heartbeats via the independent `useHeartbeat` hook (a single-field `updateDoc`, bypassing the buffer entirely) throughout its own ~15s-interval, multi-minute turn. So on every single `EndTurn`, the acting seat's OWN heartbeat gets rolled back to whatever it was at turn start — not a rare race, a guaranteed occurrence every turn. architect-b's Phase 3 review flagged this exact risk (Finding 2) and judged it safe because `useHeartbeat`'s next tick (≤15s later) "self-heals" it — that reasoning is WRONG: the corrupted value still gets WRITTEN to Firestore and is visible to every OTHER client's staleness check in the window before the next heal tick, repeatedly, every turn, for the whole match. Over a 25-round match this reliably trips the 120s staleness threshold somewhere.

**Confirmed via direct log trace** (temporary instrumentation, now removed; re-add the same pattern — `console.error` in `subscribeToGameState`/`saveGameState`/`writeHeartbeat` in `game-board.engine.service.ts`, and inside `setGameState` itself logging `callerHeartbeats`/`gameStateRefHeartbeats`/`mergedHeartbeats` — to reproduce):
```
setGameState action=end-turn now=1792073700073
  callerHeartbeats={"0":1792073696946,"1":1792073576970}       <- seat 1 (acting, ending its own turn) frozen at its turn-1-era value
  gameStateRefHeartbeats={"0":1792073696946,"1":1792073696971}  <- both genuinely fresh at this instant
  mergedHeartbeats={"0":1792073696946,"1":1792073576970}        <- seat 1 ROLLED BACK by the merge, seat 0 (peer) correctly fresh
```
Seat 1 had been writing fresh heartbeats throughout its own turn (576970 → 591972 → 606971 → ... → 696971, all landing successfully) — none of that mattered because the buffer's own-key value was frozen the entire time and won the merge at EndTurn.

**Proposed fix** (not yet reviewed by an architect — judge this, don't just implement it): at this specific persistence boundary, there's no reason to prefer the buffer's own-seat heartbeat value over `gameStateRef.current`'s — unlike other turn-buffer fields (army positions, resources, etc.), heartbeats are never part of this seat's own in-turn gameplay mutations; they're an independent, continuously-updated side channel. The `syncedHeartbeats(a, b, id)` call in `setGameState` should either (a) not special-case `localSeatId` at all here — just use `gameStateRef.current.heartbeats` directly for every seat when available (`latestServerState ? latestServerState.heartbeats : result.state.heartbeats`), since gameStateRef is always the more current source for ALL heartbeats including this seat's own; or (b) add a variant/parameter to `syncedHeartbeats` for this call site that drops the own-key preservation. Whichever an architect picks, update `docs/architecture/systems-and-visuals.md`'s bullet about this merge (already touched in the Phase 1+2 commit) to describe the corrected behavior, and re-verify with a real `test:e2e` run before considering this task done — this exact "write once, verify with a real run" cycle has produced three wrong-but-plausible-looking fixes in a row (possibleMoves race, the setDoc-undefined bug, this peer-merge fix) before the suite actually passed, so don't skip the real run again.
