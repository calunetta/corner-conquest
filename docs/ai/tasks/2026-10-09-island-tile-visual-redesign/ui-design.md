# UI design: Island tile visual redesign (resources, base layout, cloud density)

## Spec (ui-designer-a)

### Purpose and user story
As a player scanning the board, I want the ocean margin, resource islands, and my Base tile to read as an intentional, legible composition — not a scattered or overlapping jumble of sprites — so that I can tell what a tile offers and who's farming it at a glance, at any zoom level or device size.

This is a presentation-only fix (audit points 109, 110, 117, 118); no `GameState` shape or gameplay rule changes.

### Placement and layout
No new placement: all three components already render where they do today. This spec changes their *internal* composition only.
- **`MapDecorations`** (`src/modules/map/components/MapDecorations/`): absolutely-positioned cloud/rock sprites in the ocean margin around the grid, behind `MapGrid`. Desktop and mobile both show the full perimeter; only the `desktopOnly`-flagged subset differs.
- **`TileResources`** (`src/modules/map/components/TileResources/`): absolutely positioned inside each `IslandTile`'s `centerContent` (`IslandTile.tsx:58,66`), `z-[28]` container, collector badge `z-[35]`.
- **`IslandTile`** Base composition: castle crest + `TileResources isBase` render inside the Base case of `getTileCenterContent` (`IslandTile.tsx:42-60`; crest is `baseImageWrapper`, centered, `h-12 w-12 sm:h-14 sm:w-14` ≈ 48–56px). `TileForest`, `TileBoats`, and `TileOccupants` are siblings rendered around that center content in `IslandTileView` (`IslandTile.tsx:100,102,106`), not inside lines 42-60 — all five still land in the same tile `<button>` box, which is what matters for overlap.
- Desktop reference tile side `T`: `clamp(94px, 12.5vh, 136px)` (`MapGrid.tsx:50`). Mobile `T`: `clamp(46px, 13.5vw, 68px)` (same line). All new position/size values below are expressed as a percentage of `T` (or a fixed px floor for a visible minimum), matching the convention already documented in `TileBoats.styles.ts:1-2` and `TileBoats.types.ts:19-27` (boat box 42% of `T`, rider box 29% of `T`, both corner-anchored via `CORNER_TRANSFORMS`). The whole 5×6 map grid stays visible on mobile; nothing here changes grid visibility.

### States

| State | What the player sees | Trigger |
|---|---|---|
| Ocean margin, default | Clouds (and rocks, unchanged) cover the full outer margin with no gap wider than ~8% of the board's side between two cloud silhouettes, corners included | Always, both breakpoints |
| Resource tile, 1 resource | One resource sprite centered in the upper-middle band of the tile | `island.resources.length === 1`, `amount` expands to 1 node |
| Resource tile, 2–3 resources | Resource sprites distributed through top/middle/bottom bands (not clustered in the top 40%), each legible on its own | `expandedNodes.length` 2 or 3 |
| Resource node, farmed | A small collector badge sits at the side of that node's visible sprite, not centered/overlapping it, sized to look proportionate next to the resource it's farming | `positionedBy` has an entry for that resource type |
| Resource node, not farmed | No collector badge | default |
| Base tile | Castle crest centered; forest (if any); base resource nodes at non-corner positions; idle collector(s) at the boat's existing corner anchors; anchored boat; nothing overlaps at 94–136px (desktop) or 46–68px (mobile) tile sizes | `island.type === Base` |
| Monster tile | Unchanged — resources suppressed while monsters are alive (`TileResources.map.ts:81-83`) | `island.type === Monster` with living monsters |
| Fogged tile | Unchanged — `HelpCircle` placeholder, no resources rendered | `!isTileVisible` |

### A. Cloud density (`MapDecorations.map.ts`) — Phase 1 scope

**Verified current state**: `FIXED_CLOUD_LAYOUT` (`MapDecorations.map.ts:32-96`) has **48 entries** (4 corner clusters × 5 = 20, plus 4 edges × 7 edge clouds = 28). Screenshot `test-results/ui-verify/testbed-map-decorations-state-Desktop--desktop.png` (captured this session) confirms a visible gap between each corner cluster and the first edge cloud on every side — e.g. top edge: corner cluster's rightmost cloud sits around left 4%, but `cloud-t1` (the first edge cloud) is at left 16%, leaving roughly a 12%-wide stretch of bare ocean margin at the corner-to-edge transition.

**Revision (this pass) — correcting a factual error from the prior revision pass of this document.** An earlier edit to this section (still visible in `## Final spec`'s "Round 2 re-verification" below, which I'm not deleting so the error trail stays visible) claimed the root cause was "any negative/`>100%` offset is unconditionally clipped" and that "no edge cloud is `desktopOnly`." Both are wrong, and I re-verified against the actual file and a live browser in this pass, not just the prior report:

- **The "unconditional clipping" claim is false.** I measured `cloud-t0`/`t8`/`b0`/`b8` (the top/bottom gap-fillers, at the original spec's `top: '-5%'`/`'105%'`) in the browser (`getBoundingClientRect` intersection against the clipping box, plus a zoomed screenshot crop) on the literal acceptance page, `/testbed/map-decorations`: they render **30–32% of their sprite area visible**, not 0%. Only the **left/right** gap-fillers (`cloud-l0`/`l8`/`r0`/`r8`, at `left: '-5%'`/`'105%'`) measured **0% visible** — confirmed empty by a 4×-scale screenshot crop (`/tmp/l0-zoom4x-old.png`, this session) showing nothing painted at that position, vs. the corrected version showing a clear cloud sliver (`/tmp/l0-zoom4x.png`). The real mechanism: `CloudDef.left`/`.right` are a percentage of the decoration box's **width**; `.top`/`.bottom` are a percentage of its **height**. That box (`MapDecorations.root`, `absolute inset-0` to `oceanFrame` in-game or the bare preview `canvas` at `/testbed/map-decorations`) is much wider than tall in both places I measured (`/testbed/map-decorations`: 920×192 desktop, 342×192 mobile; the real `oceanFrame` at default zoom, measured via `/testbed/map-grid`'s "Populated board" state: ~316×134 desktop, ~315×110 mobile). A `±5%` offset on the ~130–192px-tall axis is only ~7–10px, small enough that most of a 48px-tall sprite still lands inside; the *same* `±5%` on the ~315–920px-**wide** axis is 16–46px — more than a 74px-wide sprite's own half-width (37px) — so it lands entirely outside `[0%, 100%]` and renders nothing. This is a width-vs-height asymmetry specific to the left/right fillers, not a blanket "negative is always clipped" rule.
- **"No edge cloud is `desktopOnly`" is also false** — see the Mobile coverage subsection below; 8 edge clouds carry `desktopOnly: true` today, verified directly from `MapDecorations.map.ts:63,67,72,76,81,85,90,94`.

(The original 48 clouds' corner-cluster entries also use negative/`>100%` offsets, e.g. `cloud-tl-1` at `left: -8%, top: -8%`; those predate this task and are out of scope — don't re-litigate them here. But the gap-filler and mid-edge fixes below do touch other existing entries' `desktopOnly` flag and two of their numeric fields, because that's what actually closes the mobile gap — see below.)

**Fix, verified**: reposition the 8 gap-filler clouds fully inside the visible `0%`–`100%` box, following the convention `FIXED_ROCK_LAYOUT`'s corner rocks already use successfully for the same problem — `rock-tl`/`rock-tr`/`rock-bl`/`rock-br` sit at `3%`/`97%` (`MapDecorations.map.ts:6-9`), inside the box, and render correctly today. Each gap-filler keeps its existing midpoint position along the edge it fills, but the coordinate on the perpendicular axis moves from the off-box `-5%`/`105%` to an in-box `2%`/`98%`. This is deliberately **inside** the box rather than a smaller negative overshoot (e.g. `-2%`/`102%`, which I also tried and confirmed partially works but only for a specific box aspect ratio — it still leaves a magnitude judgement call that depends on the exact width of whatever box the component ends up in): a value strictly between `0%` and `100%` can never be clipped by that box's own `overflow`, regardless of its aspect ratio or how zoomed the board is, which is a strictly safer guarantee than tuning an overshoot magnitude per context.

I checked the one real risk this approach raises — landing a decoration *inside* `[0%, 100%]` could in principle place it under the opaque grid tiles (`MapDecorations` is `z-[5]`, the grid is `z-10`, `MapGrid.styles.ts:5`) instead of in the open water margin. Measured `oceanFrame`'s own padding at default zoom (`p-3 sm:p-5 md:p-8` on `MapGrid.styles.ts:4`, e.g. `md:p-8` = 32px) against its ~316px (desktop) / ~315px (mobile) measured width: `2%` of that box is ~6.3px, well inside the padding band before the grid starts, so the gap-fillers stay in open water, not under a tile. Confirmed visually: `/testbed/map-grid`'s "Populated board" state renders the repositioned clouds fully in the open margin around the teal `oceanFrame`, not clipped by any tile (screenshot this session, both desktop and mobile viewports).

**Mobile coverage (defect 2) — correcting a second factual error from the prior revision pass.** That pass claimed only 8 of the original 48 clouds are `desktopOnly` ("2 per corner cluster only... no edge cloud is `desktopOnly`") and treated the resulting mobile density gap as pre-existing and intentional, requiring no fix. I re-verified directly against `MapDecorations.map.ts` and this is wrong: **16** entries carry `desktopOnly: true`, not 8 — 8 corner-cluster "wisps" (`cloud-tl-2`/`-3`, `cloud-tr-2`/`-3`, `cloud-bl-2`/`-3`, `cloud-br-2`/`-3`, lines 35-36/42-43/49-50/56-57) **and 8 mid-edge clouds, one pair per edge** (`cloud-t2`/`t6` line 63/67, `cloud-b2`/`b6` line 72/76, `cloud-l2`/`l6` line 81/85, `cloud-r2`/`r6` line 90/94). Confirmed by direct count (`grep -n "desktopOnly: true" MapDecorations.map.ts`, this session): exactly 16 `cloud-*` entries carry `desktopOnly: true` (the 8 wisps plus the 8 mid-edge pairs listed above; 8 more hits in the same grep are `rock-*` entries, irrelevant here). So of the 48 original cloud entries, 48 − 16 = 32 render on mobile today; plus the 8 gap-fillers (never `desktopOnly`) = 40 — which matches a live DOM count of rendered `[data-testid="decorative-cloud"]` elements at `/testbed/map-decorations?state=Mobile` (pre-fix, this session): exactly 40.

Losing the 8 mid-edge clouds on mobile isn't a harmless density reduction — it opens a **real, uncovered 22-percentage-point gap on every one of the 4 edges**, verified by reading the rendered DOM's `top` values on, e.g., the left edge: `cloud-l1` at `top:16%` to `cloud-l3` at `top:38%`, with `cloud-l2` (`top:27%`) removed on mobile — nearly 3× this task's own ~8% target gap, and identical on all 4 edges (same `t2/t6`, `b2/b6`, `l2/l6`, `r2/r6` structure — this is not a left/right-specific issue, contrary to how the original defect report framed it).

**Decision**: make the 8 mid-edge `desktopOnly` clouds visible on mobile too (closing the gap), rather than declaring the lower mobile density an acceptable, separate target. Corner-cluster wisps (`*-2`/`*-3`) stay `desktopOnly: true` — they're a corner-only decorative bonus, not gap-closing; each corner already keeps 3 non-`desktopOnly` clouds, so removing the wisps creates no edge gap. This is an explicit, honest asymmetry, not a silent shortfall: desktop keeps 56 clouds (48 + 8 gap-fillers), mobile reaches 48 (32 always-visible originals + 8 newly-unflagged mid-edge + 8 gap-fillers) — the 8-cloud gap between them is confined to corner wisps that don't affect edge coverage.

Un-flagging alone isn't enough for the 4 **left/right** mid-edge entries (`cloud-l2`, `cloud-l6`, `cloud-r2`, `cloud-r6`): they use the same width-axis offset problem as the broken gap-fillers above (`left: '-4%'`/`'104%'`), which a 6×-scale screenshot crop (`/tmp/l2-tight.png`, `/tmp/l2-precise.png`, this session) shows renders only a ~1–2px sliver of a semi-transparent sprite edge — indistinguishable from "no cloud" at normal viewing size even though technically non-zero. Fix, verified: move them inside the box the same way as the gap-fillers (`left: '-4%'`/`'104%'` → `'2%'`/`'98%'`). No opacity change is needed once they're fully inside the box — I tried a smaller-overshoot variant first (`-1%`/`101%` plus opacity `0.78`→`0.9`, screenshotted at `/tmp/l2-precise2.png`, this session) that also worked, but it's an extra lever to tune for no benefit once the simpler inside-the-box fix is available; the table below uses the inside-the-box values. Both variants, and the final one, are confirmed via the full-board screenshots `test-results/ui-verify/testbed-map-decorations-state-Mobile--mobile.png` (this session), which show a continuous ring of clouds on all 4 mobile edges with no large gap. The 4 **top/bottom** mid-edge entries (`cloud-t2`, `cloud-t6`, `cloud-b2`, `cloud-b6`) only need the `desktopOnly` flag removed — their offset is on the (small, in-pixels) height axis and was already comfortably visible (29–34% of sprite area) even before this revision; moving them to `2%`/`98%` for consistency with the rest of this fix is optional polish, not required, but is what the table below specifies to keep the pattern uniform across all 8.

### B. `TileResources` sprite layout + collector-beside-node — Phase 2 scope (first pass)

**Verified current state**:
- Collector badge: `absolute -top-3.5 -right-2 ... w-7 h-7 sm:w-8 sm:h-8` (`TileResources.styles.ts:6`), positioned relative to the node's **slot box** (`nodeSlot`, sized `node.nodeSize`px), not relative to the resource sprite's visible pixels. For Food, `nodeSize` is inflated ×1.45 to compensate for `sheep.gif`'s transparent padding (`TileResources.map.ts:117-119`), so the collector badge — anchored to the inflated box's corner — ends up visually detached from the sheep sprite. Confirmed in this session's screenshot (`testbed-tile-resources-state-Resource-20with-20collector--desktop.png`): the collector icon floats well above-right of the sheep, not touching it.
- Scatter slots (`TileResources.map.ts:36-58`): `SINGLE`/`DUAL`/`TRIPLE_RESOURCE_SLOTS` all sit in the tile's top 10–38% band (verified: `SINGLE_RESOURCE_SLOT`/`DUAL_RESOURCE_SLOTS` top 20%, `TRIPLE_RESOURCE_SLOTS` top 10%/10%/38%, `TileResources.map.ts:36-52`); nothing occupies the lower ~60%, so multi-resource islands read as top-heavy rather than "organically scattered."
- Base slots (`BASE_RESOURCE_SLOTS`, `TileResources.map.ts:54-58`): fixed-pixel `{top: '6px', left: '6px', size: 28}` etc. — these don't scale with tile size and sit at the same four corners `TileBoats`' 42%-of-`T` boat box and `TileOccupants`' 29%-of-`T` rider box are corner-anchored to (`BOAT_CORNER_POSITIONS`/`CORNER_TRANSFORMS`, `TileBoats.types.ts:19-27`). At a 94–136px desktop tile that boat box alone is ~40–57px, so a 28px resource icon 6px from the same corner sits inside or behind it — this is the Base-tile overlap in audit point 118.
- Also found, out of my scope to fix but worth flagging to the owning file's next editor: `TileResources.preview.tsx:14,22` references `/sprites/gold.gif` and `/sprites/wood.gif` — corrected from ui-design.md's first pass, which said both files don't exist. Verified against `public/sprites/`: `gold.gif` does exist as a file but is not the game's real Gold sprite (`/sprites/mine.png` idle / `/sprites/mine_active.png` farmed, per `TileResources.map.ts:17-24`); `/sprites/wood.gif` does not exist at all — the real Wood sprite is `/sprites/tree.gif`. The 404 in this session's console (`Failed to load resource: ... /sprites/wood.gif`) comes only from the missing `wood.gif`; the Gold preview node silently renders the wrong (unused) sprite instead of 404ing. Both paths are still wrong and should be fixed. Route this fix to whoever owns `TileResources.preview.tsx` in Phase 2 (not a design decision, a path bug).

**Fix direction** (first pass; architect-a locks exact values against the file plan):
1. **Collector badge, beside the node**: anchor the badge to the resource *sprite's* own box (not the inflated Food bounding box), on its right side by default (left if the node's own slot is already right-anchored, to avoid pushing the badge off-tile), vertically centered on the sprite. Size the badge relative to the node's un-inflated size, e.g. ~55% of `slot.size` (the pre-Food-scale value) with a floor around 22px, so it reads proportionate to what it's farming rather than a fixed 28–32px regardless of resource size.
2. **Scatter slots**: redistribute `SINGLE`/`DUAL`/`TRIPLE_RESOURCE_SLOTS` through three vertical bands — top (~18–22%), middle (~45–50%), bottom (~68–72%) of `T` — keeping the existing left/right horizontal stagger per slot so multiple same-row resources don't collide. One resource uses the middle band (centered); two resources use top+bottom (or top+middle) with left/right offsets; three use top/middle/bottom, alternating side.
3. **Base resource slots**: replace the fixed-pixel corner slots with percentage-of-`T` positions placed at tile **edge midpoints**, not corners — e.g. top-center and bottom-left-of-center / bottom-right-of-center — sized ~20–22% of `T` (matching the existing occupant-box convention, `TileOccupants.styles.ts:8`), so they can't collide with the boat/occupant corner boxes. Confirm against real `IslandTile` renders with 2–3 base resources — corrected from ui-design.md's first pass, which said today's fixtures have a single-resource Base island: verified both `baseIslandOwnedByLocalPlayer` and `baseIslandOwnedByOpponent` in `IslandTile.fixtures.ts:36-42` have `resources: []` (zero resources, not one). Phase 2 testing needs a 2–3-resource Base fixture built from scratch, not adapted from an existing one.

**Round 2 revise pass (this session) — two locked decisions, both verified live at the real tile clamp sizes (not the testbed's inflated default container).**

Method: since no testbed control forces a tile to its real clamp width, I drove the actual rendered values at `/testbed/island-tile?state=Base%20island%20with%20resources` with a standalone Playwright script (`chromium.launch()`, no project config) that overrides the tile `<button>`'s inline `width`/`height` to each clamp value in turn (`46px`, `68px`, `94px`, `136px`, `!important` to beat the `w-full`/`aspect-square` Tailwind classes), then reads `getBoundingClientRect()` on the crest `<img>`'s wrapper and each resource `<img>` to detect real 2D box overlap, plus screenshots for a visual legibility check. All temporary overrides were applied in the browser only and reverted; no source file was edited for this check (confirmed: `git status --short` shows no tracked file changed by this verification).

**Decision 1 — base resource node size: 22% of `T`, not 18% and not a 20–22% range.**
Current code (`TileResources.map.ts:60-62`, `BASE_RESOURCE_SLOTS`) sets `width`/`height` to `18%`. At the mobile-minimum tile (`T=46`), 18% renders at ~8.3px — the triage's measured 7.5px is close enough (rounding through the `size: 26`px reference field vs. the percent override; the percent field is what actually governs the rendered box per `TileResources.map.ts:34-35`'s own comment, "Base slots only, overrides the node box's px size"). Either way it's barely-legible. Lock it at a single number, **22%**, the top of the originally-proposed 20–22% range: measured in the browser at `T=46/68/94/136`, 22% resource nodes (~9–25px per node, scaling with `T`) are legible sprites against the grass terrain at every clamp width, screenshotted and visually confirmed.

**Decision 2 — castle crest becomes percent-of-`T`, not a fixed px box, at 44% of `T` with a 20px floor; base resource node positions are unchanged.**
Root cause, verified: `IslandTile.styles.ts:53`'s `baseImageWrapper` is `h-12 w-12 sm:h-14 sm:w-14` — a **fixed** 48px (or 56px past the `sm:` viewport breakpoint) box, not a percentage of the tile. It doesn't scale down as `T` shrinks toward the 46–68px mobile range, so at those sizes the crest's fixed footprint is close to or larger than the tile itself and overlaps the Base resource nodes. Measured in the browser with the *current, unfixed* code (both percentages and positions untouched): at `T=46` the 56px crest (`sm:` applies because the test viewport is 1280px wide, same as a real desktop testbed view; a real narrow-viewport mobile device gets the 48px `h-12` variant instead, which is barely smaller and still collides) fully overlapped all three resource nodes; same at `T=68` and `T=94`; only at `T=136` (the desktop clamp max) did the fixed 56px box happen to clear by coincidence, confirmed by `getBoundingClientRect` intersection returning zero overlapping resource sprites only at that one size.

I decided **against** moving the resource-node positions further away: the current `BASE_RESOURCE_SLOTS` positions (`top: 4%` centered; `bottom: 4%` at `left: 35%`/`left: 65%`, both centered via `translateX(-50%)`) already keep a 30-point horizontal gap between the two bottom nodes and stay clear of the boat/occupant corner-anchor boxes (per the existing "Edge-midpoint slots keep clear of the boat and occupant corner anchors" comment, `TileResources.map.ts:58`) — moving them again risks re-opening that corner collision this task already solved. The crest is the one oversized, non-scaling element; fixing its sizing alone is sufficient and is the smaller, more targeted change.

Locked values, checked via the geometry that must hold for zero overlap given the unchanged node positions/22% size above: a centered square crest clears the top node (bottom edge at `top: 4% + 22% height = 26%` of the container) whenever the crest's own top edge (`50% - crest%/2`) is `≥ 26%`, i.e. crest size `≤ 48%` of `T`; the same bound applies symmetrically against the bottom nodes' top edge (`74%`). **44% of `T`, floored at 20px**, gives a 2-percentage-point clearance on both sides (crest spans `28%`–`72%` vs. nodes at `4%–26%` and `74%–96%`) — verified via `getBoundingClientRect` intersection in the browser: **zero** crest/resource-sprite overlap at all four clamp sizes (`T=46/68/94/136`) with this value, versus full overlap at all but the largest size under the current fixed-px code.

The 20px floor matters only as insurance below the supported clamp range: `44% × 46px = 20.2px`, so the floor never actually engages within `T ∈ [46,136]` — it exists only to stop the crest from disappearing if a future change ever drops `T` below 46px. ## Review (ui-designer-b), round 2
VERDICT: CHANGES REQUESTED

Independent re-verification of §B's Round 2 geometry claims, per instruction, done live against `/testbed/island-tile?state=Base%20island%20with%20resources` with a standalone Playwright script (`chromium.launch()`, fresh `page` per `T`, tile `<button>` width/height forced to `46/68/94/136px` via `!important` inline style, node slots forced to `width/height: 22%` via `!important`, `baseImageWrapper` converted to `width/height: max(20px, 44%)` via `!important` with the `h-12/w-12/sm:h-14/sm:w-14` classes removed — same method ui-designer-a describes, independently re-implemented, not reused). `getBoundingClientRect()` read on the crest wrapper and all three `resource-node-*` elements at each size. All temporary overrides were browser-only; `git status --short` after cleanup shows no tracked file changed.

**Zero-intersection conclusion holds at all 4 sizes** — confirmed: `overlap: false` for all three resource nodes against the crest at `T = 46, 68, 94, 136`. That part of the Round 2 decision is correct and reproducible independently.

**But one of the two stated justifications is factually wrong, and it matters: the 20px floor does engage at `T=46`, contrary to ui-design.md:124's claim it "never actually engages within `T ∈ [46,136]`".**

- ui-design.md:124 computes `44% × 46px = 20.2px` and concludes the floor "never actually engages." That arithmetic uses the tile's full `T` as the container, but it isn't: `baseContent` (`IslandTile.styles.ts:52`, `absolute inset-0`) resolves against the tile `<button>`'s *padding box*, which excludes the button's own `border-2` (`IslandTile.styles.ts:6`, 2px each side = 4px total). So the real container at `T=46` is **42px**, not 46px: `44% × 42 = 18.48px`, which **is** below the 20px floor. Measured directly: the crest wrapper's `getBoundingClientRect().height` at `T=46` is exactly **20px**, not 18.48px or ~20.2px — the floor is what's rendering, not the percentage.
- This isn't just a documentation nit. The floor forcing the crest to 20px instead of the percent-driven 18.48px makes the crest **1.5px taller** than the clearance math in ui-design.md:122 assumed (which derives the "2 percentage-point" / `~0.84px`-at-T=46 margin from the 44% figure alone, without the floor). Measured real clearance between the crest and the nearest resource-node edge at `T=46`: **0.09px** (crest top `330.00` vs food-node bottom `329.90625`; symmetric on the bottom pair, crest bottom `350.00` vs wood/gold-node top `350.09375`) — not the ~0.84px (2% of the 42px container) the spec's own math implies, and nowhere near the "2 percentage-point" clearance language in ui-design.md:122. At `T=68/94/136` the floor doesn't engage (container 64/90/132px, `44%` of each exceeds 20px) and the measured clearance is the expected ~1.3px / ~2% of container — only `T=46`, the mobile-minimum clamp and the one size most likely to appear on real small phones, has this near-zero margin.
- `0.09px` is not a meaningful safety margin. It is "no overlap today, in this browser, at this sub-pixel rounding" — not a structural 2-point clearance that survives a different browser's text/flex sub-pixel rounding, a font metrics difference affecting `items-center` centering, or a future border-width tweak. The acceptance criterion (ui-design.md:145, "`getBoundingClientRect` ... showing zero intersection ... at all four sizes") is still technically met by my measurement, but the design's own stated justification for *why* it's safe is wrong, and the actual margin at the worst-case size is fragile enough that I'm not approving it as "verified safe" without a fix.

**Fix, verified**: lower the floor from `20px` to `18px`. At `T=46` this makes `max(18px, 44%×42) = max(18, 18.48) = 18.48px` — the floor no longer engages, the percentage governs exactly as the spec intended, and the full ~2%-of-container clearance is restored. Confirmed by the same method: crest height measured `18.46875px` (≈18.48, matching the unfloored percentage), clearance above `0.859375px` and below `0.859375px` — roughly 10× the floored version's margin, consistent with the "2 percentage-point" language the spec already uses to describe the *intended* margin. This still satisfies the floor's own stated purpose ("insurance... if a future change ever drops `T` below 46px", ui-design.md:124) — an 18px crest is still clearly visible as a small castle silhouette, not materially different from the 20px alternative at normal viewing distance — while actually delivering the margin the rest of the doc claims.

**What this means for plan.md**: change the locked Contracts value in ui-design.md:130 from `width: 'max(20px, 44%)'`/`height: 'max(20px, 44%)'` to `width: 'max(18px, 44%)'`/`height: 'max(18px, 44%)'` (or the CSS-variable/clamp equivalent implementer-b uses — same mechanism, floor number only). No other Round 2 value needs to change: the 22% base-resource-node size, the 44% crest percentage, and the unchanged `BASE_RESOURCE_SLOTS` positions are all independently confirmed correct and are not implicated in this finding.

Everything else in Round 2 and the rest of the document — cloud density fix (§A, Phase 1, already shipped and reviewed separately), collector-beside-node direction, scatter-band redistribution, Base-slot edge-midpoint placement, states table, accessibility, mobile fit, buildability — stands from the round-1 review below, unchanged.
