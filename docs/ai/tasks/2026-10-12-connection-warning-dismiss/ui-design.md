# UI design: Manual dismiss + mobile wrap fix for the connection warning dialog

## Spec (ui-designer-a)

### Purpose and user story
As a player whose own connection warning dialog is showing (`src/modules/game-board/components/ConnectionWarningDialog/ConnectionWarningDialog.tsx`), I want a button to tell the game "I'm back" that actually proves it by writing a fresh heartbeat, so that I can close the warning myself instead of waiting for the next automatic heartbeat tick or the takeover countdown, without being able to fake my way past a real disconnect.

This revises one piece of the prior spec (`docs/ai/tasks/2026-10-11-connection-warning-dialog/ui-design.md`): the "no buttons, non-dismissable" decision becomes "one button, and it can fail." Everything else in that spec (placement, non-dismiss via Escape/overlay, countdown behavior, sound, color escalation) is unchanged and is restated only where this button touches it.

### Placement and layout
- Desktop (1280×720): unchanged `AlertDialogContent` (`src/components/ui/alert-dialog.tsx:31`, centered, `max-w-lg`). Add a footer row below the countdown line using `AlertDialogFooter` (`alert-dialog.tsx:66-76`, `flex flex-col-reverse sm:flex-row sm:justify-end`), verified present and already imported by sibling dialogs (e.g. `CombatDialog`). It holds exactly one control — the dismiss button — right-aligned on desktop.
- Mobile (390×844): same footer, stacked (the primitive's own `flex-col-reverse` at the `sm:` breakpoint already does this — no override needed). The button is full-width at this breakpoint only because `AlertDialogFooter`'s own children default to natural width; make the button `w-full` on mobile only (`w-full sm:w-auto`, mirroring the existing `AlertDialogCancel`'s `mt-2 sm:mt-0` breakpoint-only tweak) so it's an easy, full-bleed tap target rather than a narrow inline one. No map-grid rule applies here — this is a modal takeover like the rest of the dialog, per the prior spec's "Placement and layout" (unchanged).
- Countdown text (`ConnectionWarningDialog.styles.ts:13`, currently `text-4xl font-bold font-mono`, fixed size on all breakpoints) gets a responsive size step-down: `text-2xl sm:text-4xl` (the `sm:` breakpoint-only pattern already used for text sizing elsewhere, e.g. `src/modules/hud/components/GameBoardHeader/GameBoardHeader.styles.ts`, `src/modules/session/components/Login/Login.styles.ts`). `text-2xl` (24px) keeps "Taking over in 0:18" (20 characters) on one line at 390px width inside the dialog's `p-6` padding (342px usable); `text-4xl` (36px) is restored at `sm:` (≥640px) and up, unchanged from before. No other property of the countdown changes — same `font-bold font-mono`, same `isExpiring` color/pulse variant.

### States
Carries forward every row of the prior "States" table (Hidden, Warning/open, Recovering/auto-dismiss, Takeover reached, Match ends) unchanged. This table adds the button's own states, which live *inside* the existing "Warning (open)" state — the button is present and interactive throughout it:

| State | What the player sees | Trigger |
|---|---|---|
| Button: idle | `RefreshCw` icon + label "I'm back", default button styling, enabled | Dialog is open (any point before a click) |
| Button: pending | Button disabled, icon swapped for a spinning `Loader2` (`animate-spin`, the app's existing in-flight pattern — e.g. `src/modules/lobby/components/CreateGameDialog/CreateGameDialog.tsx:106`), label changes to "Checking…"; countdown keeps ticking underneath, unpaused | Player clicks "I'm back"; the forced heartbeat write is in flight |
| Button: success | Not user-visible as a distinct state — the dialog closes immediately once the write resolves, same as the existing "Recovering / auto-dismiss" row | Forced heartbeat write resolves without error |
| Button: failed | Dialog stays open; button returns to idle ("I'm back", enabled, `RefreshCw` icon); a destructive-variant toast appears: title "Still can't reach you", description "Check your connection and try again." (reusing the app's existing toast system, `useToast` from `@/modules/shared`, already used for action failures elsewhere, e.g. `src/modules/game-board/game-board.engine.hook.ts:28`) | Forced heartbeat write throws/rejects |

No hover/focus/selected row beyond the button's own default shadcn `Button` states (`src/components/ui/button.tsx`) — not overridden.

### Components and tokens
- Add `AlertDialogFooter` (verified, `alert-dialog.tsx:66-76`) and shadcn `Button` (`src/components/ui/button.tsx`, default variant) — both existing primitives, zero new patterns. This reverses, rather than adds to, the one new pattern the prior spec introduced ("AlertDialog with zero action buttons"); after this change the dialog is a standard one-button `AlertDialog`, which is the common case elsewhere in the app (e.g. simple confirms) — nothing novel.
- Do **not** use `AlertDialogAction` (`alert-dialog.tsx:103-113`) for this button. That primitive is meant for an uncontrolled dialog where clicking it drives the dialog's own open/close state; this dialog's `open` prop is controlled entirely by the view model (`isOpen`, `ConnectionWarningDialog.tsx:31`, no `onOpenChange`), and the close must be gated on the async write succeeding, not on the click itself. A plain `Button` with its own `onClick` keeps that gate explicit and avoids relying on Radix's close-on-Action semantics in a case they don't fit. This is the one new piece of behavior this feature introduces — not a new visual pattern (same `Button` styling as every other primary action in the app).
- Icons: `RefreshCw` (idle/failed) and `Loader2` (pending) from `lucide-react`, both verified present (`node_modules/lucide-react/dist/lucide-react.d.ts:14840` `RefreshCw`; `Loader2` already imported app-wide, e.g. `src/modules/session/components/Login/Login.tsx:3`).
- Tokens: button uses the default `Button` variant (no destructive/outline override — this is a normal, encouraged action, not a dangerous one). Toast uses the existing `variant: 'destructive'` already used by `game-board.engine.hook.ts:28`. No new color tokens.
- Countdown size step: `text-2xl sm:text-4xl` replacing the fixed `text-4xl` in `ConnectionWarningDialog.styles.ts:13` — same cva, same `isExpiring` variant branch, only the base size classes change.

### Copy
- Button label, idle/failed: "I'm back"
- Button label, pending: "Checking…"
- Toast on failure — title: "Still can't reach you"; description: "Check your connection and try again."
- No other copy changes; title ("Connection lost"), body ("We haven't heard from you in a while. Reconnect now or a bot will take over your seat.") and countdown line format ("Taking over in {mm:ss}") are unchanged from the approved prior spec.

### Interactions and motion
- Escape and overlay-click remain suppressed exactly as before (`keepOpen` on `onEscapeKeyDown`, `ConnectionWarningDialog.tsx:20-22`, unchanged) — the only way to close the dialog is this button succeeding, or the existing automatic-recovery/takeover paths. This preserves the prior spec's acceptance criterion "clicking the dimmed overlay, or pressing Escape, does not close it" — only the new explicit button closes it, per `triage.md`.
- Click → pending: button disables and swaps to `Loader2`/`animate-spin` the instant the click handler fires, so a double-click can't fire two writes. Wrap the spin in `motion-reduce:animate-none` per the app's existing convention (`CreateGameDialog.styles.ts:15`), consistent with the dialog's own existing `motion-reduce:` handling of the countdown pulse.
- Success → the dialog's own close transition is the unchanged primitive default (`fade-out-0`/`zoom-out-95`, `alert-dialog.tsx:31`) — no new motion.
- Failure → button springs back to idle, toast slides in using the app's existing `Toaster` (`src/components/ui/toaster.tsx`) — no custom timing, the toast's own default duration applies.
- The countdown continues ticking during the pending state — a slow network response must not freeze the player's sense of the remaining time.

### Accessibility
- Button is a standard shadcn `Button`, so it is reachable by Tab, activates on Enter/Space, and shows the default `focus-visible:ring-2 focus-visible:ring-ring` — nothing to add.
- While pending, the button is `disabled` (not merely visually dimmed) so assistive tech announces it as unavailable and a screen-reader user isn't told to activate it twice.
- Label changes ("I'm back" → "Checking…") are plain text content, not icon-only, so no `aria-label` is needed; the icon is decorative (`aria-hidden`, matching the existing `WifiOff` icon's treatment at `ConnectionWarningDialog.tsx:35`, which has no separate text alternative because the adjacent title already names the condition).
- Failure feedback is a toast (visible text, not color alone) plus the button simply being available again — a screen reader hears the toast via the `Toaster`'s existing live-region behavior (unchanged primitive, not new work here).
- Text contrast: button uses the default `Button` variant's existing contrast-checked tokens; toast uses the existing `destructive` variant's tokens — both already relied on elsewhere, no new contrast risk.
- Countdown text contrast and color-escalation accessibility are unchanged from the approved prior spec (color never the sole signal — the number itself still updates).

### Acceptance criteria
<!-- Checked in the browser by the ui-verify skill. Make each one observable. -->
- [ ] With the dialog open, a button labeled "I'm back" with a `RefreshCw` icon is visible in a footer row below the countdown, enabled.
- [ ] Clicking "I'm back" immediately disables the button, swaps its icon to a spinning `Loader2`, and changes its label to "Checking…"; the countdown text keeps updating while this is shown.
- [ ] Forcing the write to succeed (fresh `lastSeenAt`) closes the dialog with no further interaction, the same way the existing automatic-recovery path does.
- [ ] Forcing the write to fail re-enables the button back to "I'm back" with the `RefreshCw` icon, and a destructive-variant toast titled "Still can't reach you" appears; the dialog itself stays open and the countdown keeps running from where it left off.
- [ ] Pressing Escape, or clicking the dimmed overlay, still does not close the dialog (this still only re-verifies the unchanged prior behavior, not a new one).
- [ ] On a 390×844 viewport, the button is full-width in the footer and the countdown line ("Taking over in 0:18" or any other `m:ss` value) renders on a single line with no horizontal scrolling or wrapping.
- [ ] On a 1280×720 viewport, the button is right-aligned in the footer (not full-width) and the countdown remains at its prior, larger size.

Findings:
- **Fix (folded in):** the `motion-reduce:animate-none` precedent citation pointed at the wrong file/line (`CreateGameDialog.styles.ts:15`, which is a `transition`/`scale` reduction, not `animate-none`). Corrected citation in Final spec to `ConnectionWarningDialog.styles.ts:8,16` — the component's own existing `icon`/`countdown` cva already do exactly this pairing, which is a better consistency argument than reaching into an unrelated dialog.
- **Fix (folded in):** the Accessibility section's wording claims the new button's icon is "decorative (`aria-hidden`, matching the existing `WifiOff` icon's treatment...)" but `WifiOff` at `ConnectionWarningDialog.tsx:35` has no `aria-hidden` attribute at all — lucide icons render as bare `<svg>` with no `role`, so they're already un-announced by default without needing the attribute. The spec's intent (new icon needs no separate text alternative) is correct, but as written it implies an attribute exists on `WifiOff` that doesn't. Reworded in Final spec to stop asserting a non-existent attribute.
- **Gap, folded in as a note rather than a blocking rewrite:** `toConnectionWarningViewModel` (`ConnectionWarningDialog.map.ts:27-28`) closes the dialog the moment `isBot` flips true (takeover) or `lastSeenAt` recovers, independent of whatever the button is doing. If the forced write is still pending (or its promise settles) after the dialog has already closed through one of those other paths, a stray failure toast ("Still can't reach you") could appear after the seat has already been taken over or the warning has already cleared — confusing in context, even though it's not wrong information. The spec doesn't mention this race. Added one line to States/Interactions in the Final spec: the toast must not fire for a click whose dialog has already closed by the time the write settles. This is implementation guidance (a stale-closure/mount guard), not a new visible state, so it doesn't need its own acceptance criterion row — existing criteria still cover the common path.
- Minor, not fixed: the countdown fit arithmetic says "20 characters" for `"Taking over in 0:18"`, which is actually 19 characters. Doesn't change the conclusion (not safety-margin-critical) and the acceptance criteria already require a real screenshot, not the arithmetic, to confirm the fit — left as-is.
- Confirmed: all seven acceptance criteria are independently observable in a browser or a test (button present/labeled, pending visuals, success closes dialog, failure shows toast + re-enables + dialog stays open, Escape/overlay no-op retained, two explicit viewport checks). None requires reading internal state.
- Confirmed: using a plain `Button` over `AlertDialogAction` is correct given the controlled `open={isOpen}` with no `onOpenChange` — Radix's `Action` only auto-closes through the Root's own uncontrolled state, which this dialog doesn't use, so gating the close on the async result requires a plain `Button` regardless.
- Confirmed: mobile layout fix (`text-2xl sm:text-4xl`) and footer button placement reuse only existing primitives (`AlertDialogFooter`, `Button`, Tailwind breakpoints) — no new visual pattern, consistent with "at most one new visual pattern per feature" (this feature's one new thing is the button's own async-gated behavior, not a new look).

## Final spec
The Spec section above stands, with these corrections:

1. **Interactions and motion**, spinner line: replace "Wrap the spin in `motion-reduce:animate-none` per the app's existing convention (`CreateGameDialog.styles.ts:15`)" with: Wrap the spin in `motion-reduce:animate-none`, per this same component's existing convention (`ConnectionWarningDialog.styles.ts:8` and `:16`, where the `icon` and `countdown` cva already pair `animate-pulse`/`motion-reduce:animate-none` for `isExpiring`) — the new spinner follows the identical pattern already in this file, not a borrowed one.
2. **Accessibility**, icon line: replace "the icon is decorative (`aria-hidden`, matching the existing `WifiOff` icon's treatment at `ConnectionWarningDialog.tsx:35`, which has no separate text alternative...)" with: the icon is decorative — lucide icons render as a bare `<svg>` with no `role`, so like the existing `WifiOff` icon at `ConnectionWarningDialog.tsx:35` (which also carries no `aria-hidden`), it is already un-announced by assistive tech without needing the attribute; add `aria-hidden="true"` anyway for explicitness since this icon (unlike `WifiOff`) changes between two glyphs and should never be read as its own content.
3. **States / Interactions**, add one line: if the dialog closes through another path (automatic recovery or takeover) while the forced heartbeat write is still in flight, its eventual failure must not surface the "Still can't reach you" toast — guard the resolution against a click whose dialog has already closed. This is a hook-level guard (e.g. checking the dialog is still open, or an unmount/stale-closure check), not a new visible state, and needs no new acceptance-criterion row.

Everything else in the Spec section (placement, layout, states table, components/tokens, copy, remaining interactions/motion, remaining accessibility, all seven acceptance criteria) stands unchanged.
