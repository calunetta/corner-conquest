# Triage: Default-elements editing mode for the tile-decoration editor

Request: add a second mode to `TileDecorationEditor` for editing the fixed/default tile elements (knight occupant, base crest, boat, special-island art, resource nodes) using the same drag/nudge/resize canvas pattern as the forest-decoration mode, and guarantee these elements always paint above the decoration layer.

## Why this tier
- Writes land in `src/modules/map/island-tile-slots.types.ts`, the file `feedback_island_tile_slots_locked.md` (user memory) marks hand-tuned/locked: `OCCUPANT_CORNER_SLOTS`, `BOAT_CORNER_POSITIONS`, `CORNER_TRANSFORMS`, `SINGLE/DUAL/TRIPLE/QUAD_RESOURCE_SLOTS`, `BASE_RESOURCE_SLOTS`, `OCCUPANT_SIZE`, `BOAT_SIZE`, `SPECIAL_ISLAND_SIZE/TOP/LEFT`, `BASE_CREST_SIZE/MIN_PX` (verified by reading the file this session, `island-tile-slots.types.ts:1-123`). The user's request is the explicit ask the memory requires before touching these — but the save path must be built carefully (whole-file read/preserve, not regenerate) so it doesn't clobber anything the task doesn't touch.
- Visible UI: yes, both in the editor and on the live game board (`IslandTile.tsx`, `TileOccupants`, `TileBoats`, `TileResources` all render from these slot tables already).
- Data model mismatch with the existing decoration-editor pattern: `DecorationLayout`/`DecorationInstance` is a free-form array (N instances, each with `top/left/size/z`, `TileDecorationEditor.map.ts`, `TileDecorationEditor.types.ts`). The default elements are **fixed single/4-corner slots**, not arrays — occupant and boat are 4 `CornerPosition` entries (`{top|bottom}+{left|right}` pairs, not top/left-as-center), special-island art is one center point, base resources are 3 fixed center points, and single/dual/triple/quad resource slots are 4 separate small tables selected by node count. "Same criteria/logic" means reusing the editor's interaction model (drag on a live tile canvas, arrow-key nudge, numeric inspector fields, Save-writes-the-whole-file), not reusing `DecorationInstance`'s shape verbatim.
- Z-index finding (verified this session): the invariant the user wants is **already true by construction**. Container classes are `TileDecorations` `z-[12]` (`TileDecorations.styles.ts:2`) < `IslandTile` `centerContent` `z-20` (`IslandTile.styles.ts`, wraps base crest/special art/resources on non-Base/Resource islands) < `TileBoats` `z-25` (`TileBoats.styles.ts:4`) < `TileOccupants` `z-30` (`TileOccupants.styles.ts:4`); `TileResources`' own container is `z-28`/`z-32`/`z-35` but only inside `centerContent`'s *own* stacking context on Base/Resource tiles. A per-instance decoration `z` (10-20) only reorders within `TileDecorations`' own stacking context (`TileDecorations.map.ts`'s contract comment, confirmed in the existing plan.md Contracts block) and can never cross above `z-[12]`. Scope therefore includes a locked-in regression test/doc note for this invariant, not new z-index data — unless the user wants per-element z made visible/editable in the inspector too (see Open questions).
- Cross-module, cross-layer: new types/map functions for 5 different fixed-slot shapes, hook/view-model changes for a mode switch, canvas/inspector UI changes per element kind, the existing save API route (`src/app/api/tile-decoration-editor/layouts/route.ts`) needs a sibling or extension to also persist `island-tile-slots.types.ts`-shaped data, plus docs-sync (`docs/architecture/systems-and-visuals.md` documents these slot tables) and a mandatory test update since `island-tile-slots.test.ts` pins today's locked literals (`feedback_island_tile_slots_locked.md`'s own "How to apply" note: pinned-literal tests are expected to fail while values are being tuned, and get a full update pass only when the user asks for one).

## Scope
- In: a new "Default elements" mode/tab in `TileDecorationEditor`, switchable alongside the existing "Decorations" mode; drag/nudge/resize editing of knight (4 corner slots + size), boat (4 corner slots + size), special-island art (1 center point + size), base resource slots (3 center points), and the 4 per-node-count resource slot tables (1/2/3/4 nodes); a save path that writes the edited values back into `island-tile-slots.types.ts` (as source, since it's a typed `.ts` file consumers import directly — not the JSON config); a regression test asserting the documented z-index ordering (`TileDecorations` < `centerContent` < `TileBoats` < `TileOccupants`) holds; docs-sync on `systems-and-visuals.md` if any described default-element behavior changes.
- Out: the forest/tree decoration mode itself (unchanged); `BOAT_SIZE`'s or any other value's *default numbers* (only the editing tool is built — no table is pre-emptively retuned); converting `island-tile-slots.types.ts` to JSON (stays a typed `.ts` module, since game code imports its exports directly, not through `resolveJsonModule`); exposing per-element z-index as new editable data (pending the open question below) unless the user confirms they want that.

## Open questions

- Save target: regenerate `island-tile-slots.types.ts` as TS source from a template that preserves every existing comment verbatim, substituting only the edited numeric values. Do not move these tables to JSON.
- Z-index: leave the current fixed per-layer order alone (no new editable z field). Add a regression test locking in today's order (`TileDecorations` z-[12] < `IslandTile` centerContent z-20 < `TileBoats` z-25 < `TileOccupants` z-30).
