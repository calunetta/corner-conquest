## A. Player session & state model

1. `usePlayer` generates a unique `playerId` on first visit and stores it in `localStorage`, persisting across reloads.
2. Choosing a username creates a Firestore doc at `usernames/<username>` whose content is the player's `playerId`, acting as a claim lock.
3. On reload, the session is re-validated against Firestore: the `usernames/<name>` doc must exist and its stored `playerId` must match localStorage, or the session is cleared and the user returns to login.
4. Logout or tab close deletes the `usernames/<name>` doc and clears `username` from localStorage, freeing the name.
5. `GameState` (players, map, currentPlayerIndex, turn, log, combatState, monsterCombatState) is the single Firestore-synced source of truth, only written when an action irrevocably changes the game for all players.
6. Local UI state (`GameBoardUIState`: selectedArmyId, possibleMoves, pendingAction, dialog open/closed flags) lives in a client-only reducer (`gameBoardReducer`) and never touches Firestore by itself.
7. Action flow is: local select → local validate → dispatch shared action → reducer computes new `GameState` → single `setGameState` write → Firestore pushes to all clients.

## B. Map, resources, win condition

8. Win condition: first player to reach `victoryPointGoal` (default 30 VP) wins; game `status` becomes `'finished'` and a `winner` snapshot (deep copy) is stored.
9. VP sources: +5 for winning a battle against another player.
10. VP sources: variable VP for defeating a monster, scaled by monster level (2 for Lvl 1, 5 for Lvl 2, increasing with level).
11. VP sources: +`vpPerIslandDiscovery` for being the *first* player in the game to reveal a given island, awarded only for army movement (not the Scout card).
12. VP sources: the `Explorer` passive ability grants VP each turn for non-base islands the player currently occupies.
13. Map is a grid sized by `settings.gridSize.cols` × `.rows`; each player starts at a corner Base.
14. Fog of war hides tiles until a player's army moves adjacent to them, at which point they're revealed (default mode — see section E for fog-disabled/debug variants).
15. Map generation is procedural, driven by `game-setup.reducer.ts` + `map-generation.ts`, tunable via lobby "Customize Match" settings.
16. Base tiles generate all three resource types, and their sprite is a castle specific to the owning player's color (`player-data.ts`).
17. Resource islands hold Food, Wood, or Gold; whether an island has one or two resource types is determined by its distance from the map center.
18. A single-resource-type island always has exactly two collection spots for that resource.
19. A two-resource-type island gives each type a random number of collection spots (one or two).
20. Monster islands are inhabited by hostile creatures that must be defeated to pass/claim the island.
21. Monsters render with a dynamic idle animation (random left/right shifts, occasional attack-pose plays) inside `IslandTile`; all monster sprites are animated GIFs.
22. When the last monster on an island dies, the island's type flips to `Resource` and it immediately generates new resources using the same rules as other resource islands.
23. Special islands grant a random Special Card on first discovery.
24. Landing again on an already-discovered Special Island opens a roll-die prompt; rolling 3 or 6 grants another card.
25. Island-type distribution (Resource vs Monster vs Special) is controlled by `resourceDensity` (default 60% = resource island probability); the remainder splits between Monster and Special, Special being rarer, and the split shifts with distance from center (more valuable/dangerous islands cluster toward the middle).
26. Food is used to Deploy new armies; its cost increases with each additional army owned.
27. Wood is used to permanently increase a player's global Attack Power via Upgrade.
28. Gold is used to buy Special Cards or purchase permanent Passive Abilities.

## C. Turn structure, army actions, combat

29. Each army may perform exactly one major action (Attack, Position, or Move) per turn, tracked by a per-army `hasActed` flag.
30. At turn start (`handleEndTurn`), `hasActed` resets to `false` for all of the *new* current player's armies only, `actionsThisTurn` clears, and resource yields + passive abilities (Collector, Explorer) are calculated.
31. `hasActed` flags are NOT reset when a player ends their own turn — they persist until that player's next turn starts.
32. `getPossibleMoves` returns `[]` for any army with `hasActed === true`.
33. Clicking a selected army tile again toggles deselection.
34. Clicking a tile with multiple friendly armies opens `ArmySelectionDialog`, marking the active selection with a badge/ring and allowing re-toggling.
35. Deselection also triggers on: clicking any unoccupied/invalid tile, clicking "Deselect Army" in `ActionsPanel`, or pressing Escape (which also cancels pending card actions).
36. Position action: available on a resource island with no monsters, for a valid un-acted army; opens `PositionDialog` listing unoccupied resource spots; selecting one dispatches `SelectResourcePosition`, sets `hasActed: true`, and the army collects that resource starting next turn.
37. Attack vs. one enemy army: sets shared `combatState`, opens `CombatDialog` for both sides.
38. Attack vs. multiple enemy armies on the tile: opens local `AttackSelectionDialog` for the attacker first, then proceeds as above.
39. Attack vs. one monster: sets shared `monsterCombatState`, opens `MonsterCombatDialog`.
40. Attack vs. multiple monsters: opens local `MonsterSelectionDialog` first, then proceeds as above.
41. Rolling dice in either combat dialog dispatches `handleCombatRoll`/`handleMonsterCombatRoll`, immediately sets the attacker's `hasActed: true`, and resolves the battle.
42. Move: dispatches `GameAction.Move` with the new position, sets `hasActed: true` (unless Extra Move is active on a fresh army), and triggers `revealIsland` if the tile was previously unrevealed to this player.
43. Deploy, Upgrade, Buy Card, and Use Card are "strategic actions" — once per turn each, independent of any army's `hasActed` state.
44. Deploy: requires enough Food (or active `Reinforce`), fewer than 5 armies, and the action unused this turn; subtracts/reduces Food cost, adds a new army at the Base with `hasActed: true` (can't act same turn), marks `deploy` used, consumes `Reinforce`/`Efficient` if active.
45. Upgrade: requires enough Wood (or active `MasterBuilder`), attack power below max, action unused this turn; subtracts Wood, raises global attack power, marks `upgrade` used, consumes `Master Builder` if active.
46. Buy Card: requires ≥10 Gold, hand not full (<7), deck or discard non-empty, action unused this turn; subtracts Gold, draws a random card (reshuffling discard into deck if needed), marks `buy-card` used.
47. Use Card: opens `CardsDialog`; "Use" is enabled only if no card has been used yet this turn; resolution varies per card (section D).
48. Combat dice count = player's Attack Power + 1, uncapped.
49. Monster dice by level: Lvl 1 (Lancer) 1 die, Lvl 2 (Bear) 2 dice, Lvl 3 (Ogre) 3 dice, Lvl 4 (Minotaur) 4 dice.
50. Combat-card selection (None/Overcome/War Chief/Decide Dice Roll) in the prep dialogs is a mutually-exclusive radio group; chosen card is consumed, discarded, and logged to `actionsThisTurn` at roll time.
51. PvP combat: higher total wins; ties favor the **defender**.
52. PvP vs. Monster: higher total wins; ties favor the **monster**.
53. Defeated armies are never destroyed — they return to the owner's Base and their `hasActed` resets to `false`, ready to act again on the owner's next turn.
54. Death animation: placed with a `createdAt` timestamp; host prunes it from Firestore after 1.5s via persistent timer tracking; tiles locally prune expired ones after 2s; `handleEndTurn` also prunes stale ones on turn change.
55. Combat dialog animation: both combatants show `attack` pose during rolling; on results, winner stays in `attack` pose, loser switches to `death`; the right-side combatant's sprite is horizontally flipped so they visually face each other.

## D. Special card interactions

56. PvP matches start all players with zero Special Cards. PvB matches with Debug Mode start the human with one of every card.
57. Hand limit is 7 cards; a full hand discards a would-be new card from Special Island discovery or Buy Card (no new card granted).
58. Deck exhaustion reshuffles the discard pile into a new deck.
59. Using a card removes it from hand to `discardPile` and consumes the turn's one `UseCard` action; combat-context cards appear as mutually exclusive options inside the relevant combat dialog instead.
60. Cancelling an in-progress card (Extra Move, Teleport, Reinforce, Efficient, Master Builder) before completing its effect restores the card to hand, clears its modifier flag, and refunds the turn's Use Card action.
61. Extra Move: consumes the card, sets `hasExtraMove: true`, and reactivates *all* friendly armies (`hasActed: false`); UI shows a glowing banner prompting a soldier selection; cancellable before moving.
62. Teleport: sets local `pendingAction: {type:'teleport'}`; deselects any selected army; player picks an army then any non-enemy-base tile; dispatches `Move` with `isTeleport:true`, consumes the card, sets `hasActed:true`, and does **not** award discovery VP.
63. Scout: sets local `pendingAction: {type:'scout', count:3}`; player clicks 3 hidden tiles, each individually revealed via local `Scout` dispatch; after the third, `UseCard` with `isScout:true` consumes the card from hand; does **not** award discovery VP.
64. Sabotage: opens `SabotageDialog` listing opponents; selecting one dispatches `SabotagePlayer`, consumes the card, sets the target's `isSabotaged: true`.
65. Reinforce: sets `reinforceActive:true`; the next Deploy this turn costs 0 Food; card is consumed only on successful deployment, else returned on cancel.
66. Efficient: sets `efficientActive:true`; next Deploy this turn costs 50% less Food; consumed only on successful deployment, else returned on cancel.
67. Master Builder: sets `masterBuilderActive:true`; next Upgrade this turn costs 50% less Wood; consumed only on successful upgrade, else returned on cancel.
68. Steal Resource: opens `StealResourceDialog` (pick opponent, then resource type); dispatches `StealResource`, consumes the card, transfers resources between players with NaN-guarding.
69. Wealthy: opens `WealthyDialog` (pick resource type); dispatches `GainWealth`, consumes the card, grants +5 of the selected resource.
70. Overcome: a checkbox in combat dialogs; when checked, the combat auto-resolves as a win for the player; card consumed on roll.
71. War Chief: a checkbox in combat dialogs; grants +2 attack power for that single combat; card consumed on roll.
72. Decide Dice Roll: a checkbox + 1–6 slider in the *monster* combat dialog only; forces one of the player's dice to the chosen value; card consumed on roll.
73. Productive: passive-triggered; at turn start, if the player has positioned collectors, opens `ProductiveCardDialog` restricted to resources the player is actually positioned on (prevents doubling un-positioned resources); selecting one and confirming dispatches `UseProductiveCard`, consumes the card, and doubles that resource's yield.

## E. UI dialogs, selection, fog of war, debug mode

74. Most action dialogs (Sabotage, Wealthy, Position, My Cards, Abilities Shop, ProductiveCardDialog, SpecialIslandRollDialog) render only for the current player and live in local component state, not `GameState`.
75. `CombatDialog` and `MonsterCombatDialog` are the exceptions — their state lives in shared `GameState` so all players can observe outcomes/involvement.
76. Multi-army tile clicks open `ArmySelectionDialog` for disambiguation; single-army clicks select directly.
77. "Deselect Army" is a hard reset clearing both the selected army and any pending card action.
78. Fog of War enabled (default): each player tracks independent visibility in `player.revealedTiles`; tiles (and armies on them) reveal only via adjacent army movement; opponent armies are visible only at their Base or on tiles this player has personally explored.
79. Fog of War disabled: visibility is shared globally — once any player reveals a tile, it's visible to all players for the rest of the match.
80. Debug Mode auto-enables for Player-vs-Bot lobby games and overrides Fog of War settings: full map and all armies visible from turn 1.
81. Debug Mode also grants the human player one of every Special Card and 20 Food / 20 Wood / 20 Gold at match start.

## F. Bot logic, mobile UI, Firestore economics

82. Bot turns run as one atomic loop (`bot-turn.reducer.ts` + `bot-turn.service.ts`) to avoid timeout debouncing, state deadlocks, or dangling combat.
83. Bot pre-computation: activates strategic cards (Reinforce, Efficient, MasterBuilder) when relevant, uses Wealthy/Sabotage opportunistically, buys affordable passive abilities, attack upgrades (cap 4), new armies (cap 5), or special cards.
84. Bot army evaluation priority: Positioning on a resource = priority 9 (primary economy driver); Attacking = priority 7–8 (auto-rolls and closes combat within the turn); Movement = scored by preference for unexplored fog-of-war islands and unoccupied resource/special islands.
85. Bot guarantees turn transition: after all valid army actions, calls `handleEndTurn` and writes the result in one atomic Firestore update.
86. A standalone balance simulator (`scripts/balance-simulator/`) runs bot-vs-bot matches through real game logic with Firestore stubbed (zero writes) to report win rates, match length, economy, combat accuracy, and bot-health signals.
87. Desktop map starts at 85% zoom; zoom control steps in 15% increments; a reset button returns to 85%.
88. Mobile map auto-fits the full grid to viewport width via clamped tile size/gaps, ensuring all 4 corner bases are visible without panning on load.
89. Mobile supports single-finger pan and two-finger pinch-to-zoom up to 2.0x.
90. Mobile `ActionsPanel` renders a fixed bottom bar (context row + primary actions row, 44px+ touch targets) instead of the desktop Card; secondary actions (Upgrade/Buy Card/Cards/Abilities) live in a bottom sheet; disabled-reason text is a static caption on mobile instead of a hover tooltip.
91. `PlayerInfo` shows `armies.length` and base `attackPower` with a tooltip explaining the dice formula (`Attack Power + 1`).
92. Combat/monster dialogs sync real-time actions to both local state and Firestore for instant transitions between prep/rolling/results.
93. `MonsterCombatDialog` has a spectator view during the `rolling` phase with no interactive buttons, preventing interference.
94. `handleEndTurn` uses bounded iterative advancement to safely process multiple simultaneously sabotaged players without recursion risk, and validates tile data before running passive abilities.
95. Turn auto-completes once the active player has exhausted all army moves/attacks/positions and can't afford any remaining strategic action (Deploy/Upgrade/BuyCard/UseCard/BuyAbility).
96. All human in-turn actions (Move, Deploy, Upgrade, BuyCard, UseCard, SelectResourcePosition, CancelAction) execute purely in local client memory — zero Firestore writes until turn end.
97. A single `setDoc` fires at `handleEndTurn`, so a human player generates ~1 write per round.
98. Bot turns likewise commit via a single atomic `setDoc` per round.
99. Host cleanup routines (animation/event pruning) use in-memory state references instead of extra `getDoc` reads.
100. Claimed sustainability: a standard 20-turn match needs ~20–30 total writes and ~40–60 reads across all clients, fitting Firebase's free tier for hundreds of matches/day.

## G. Tutorial, E2E lifecycle, tile visuals/sprites

104. Every Playwright suite must register `safeCleanupGame` in `test.afterEach`, guaranteed to run even on assertion failure, dismissing modals and exiting the match.

106. `handlePlayerExit`: last human player leaving (bots-only remaining) deletes the room immediately.
107. `handlePlayerExit`: if remaining players drop to ≤1 when the host leaves, the room doc is dismantled.
108. `TileForest`: 2–3 trees of one deterministically-hashed type (from island x/y + base flag) render on Base/empty islands; Resource islands suppress decorative trees entirely to avoid confusing them with wood nodes.
109. `TileResources`: resources render as animated sprites (sheep=Food, trees=Wood, mine=Gold) at z-35, scattered organically (non-linear 2D), with multiple same-type resources shown as distinct side-by-side sprites rather than count badges.

113. Turn auto-completion is cross-documented under `hasPlayerRemainingActions` + `GameBoardContext.tsx` (duplicate of point 95 — same mechanic, different doc location).
114. Dialogs with rich sprite previews: `ProductiveCardDialog`, `WealthyDialog`, `StealResourceDialog`, `PositionDialog`, `AbilitiesDialog` all show animated resource sprites and custom icons (`FightIcon`, `ResourceIcon`).
115. `TileBoats`: each island has 4 fixed shore-corner anchor slots (0=BR, 1=TR, 2=TL, 3=BL); every player's boat starts anchored at their home Base; landing on an island docks the boat at the first free corner, avoiding visual collision between multiple players/armies on the same tile.

117. `MapDecorations`: fixed cloud sprites (small/medium/big) decorate the outer ocean margins/corners around the playable grid.
118. `IslandTile` Base layout: castle sprite sized ~48–56px, laid out to fit castle + tree forest + base resource nodes + idle collectors + anchored boat without overlap.

## H. Part 8 — undocumented logic found in code (first pass, 2026-10-09)

Not yet reviewed by the user — these are new findings, not yet tagged. Pulled from `src/modules/game-rules/` directly since `docs/README.md` doesn't mention them (or mentions them without the real numbers/edge cases).

119. **Passive ability exact mechanics** (`player-turn.reducer.ts:76-116`, run at the start of each of *that ability-holder's* turns, not continuously): Explorer grants +1 VP per distinct non-Base island one of the player's armies currently occupies (deduped by tile, so multiple armies on the same island don't double-count). Collector grants +1 of *every* resource type present on each distinct Resource-type island one of the player's armies occupies (also deduped per tile) — this stacks with, and is separate from, the normal positioned-army auto-collection.
120. **Ability purchase rules** (`card-acquisition.reducer.ts:68-85`): flat cost from `settings.abilityCost` (default 15 gold); throws if the player already owns that ability (one-time, non-stacking) or if the ability isn't in `settings.availableAbilities` for this match. Only two abilities exist at all: `Explorer`, `Collector` (`src/lib/types/cards.ts:18-21`) — there is no larger "Abilities Shop" catalog beyond these two.
121. **Lobby-customizable content pools**: `settings.availableCards` and `settings.availableAbilities` (`game-settings.ts:14-15`) let a match restrict which special cards and passive abilities are in play at all — defaults are all `BASE_CARDS` (13 unique cards) and both abilities, but the lobby's "Customize Match" settings can narrow either list. Not mentioned anywhere in `docs/README.md`.
122. **Special-card deck weighting** (`card-data.ts:7-21`): the actual 19-card weighted deck (`SPECIAL_CARDS`, what `BuyCard`/island discovery/special-island rolls draw from) has non-uniform copy counts — Extra Move ×3; Steal Resource, Reinforce, Wealthy, Productive ×2 each; Efficient, Master Builder, War Chief, Decide Dice Roll, Scout, Overcome, Sabotage, Teleport ×1 each (Teleport explicitly commented "only one copy"). `BASE_CARDS` (13 unique, one each) is the separate list used for Debug Mode's "one of every card" starting hand, not the draw deck.
123. **Sabotage resolution is a skip-loop, not a single skip** (`player-turn.reducer.ts:45-61`): `handleEndTurn` advances through *consecutive* sabotaged players in one call (bounded by `attempts < players.length` to prevent an infinite loop if everyone is sabotaged), clearing each one's `isSabotaged` flag as it's skipped and logging each skip, before finally landing on and fully processing a non-sabotaged player's turn start.
124. **Turn-counter increment has two separate trigger paths** (`player-turn.reducer.ts:58-60` inside the skip-loop, and `:68-69` after it): `state.turn` increments either mid-skip-loop (if the rotation wraps to seat 0 while skipping a sabotaged player) or once after the loop exits (if the final landing seat is 0 and no skips happened) — never both for the same wrap. Not documented at all; relevant to anyone debugging turn-count display or balance-simulator turn limits.
125. **Productive-card turn-start branching** (`player-turn.reducer.ts:118-124`): if the player has active resource positions AND still holds the `Productive` card, automatic collection is *skipped entirely* in favor of opening `productiveDialogState` (the player must resolve the dialog, per §6.5, to collect anything that turn from positioned armies). If they have positions but no longer hold the card, normal automatic collection runs immediately. `docs/README.md` §6.5 describes the dialog but not this "collection is blocked until you resolve it" exclusivity.
126. **Combat/monster-combat state is force-cleared every turn transition** (`player-turn.reducer.ts:144-145`): `handleEndTurn` unconditionally nulls `combatState`/`monsterCombatState`, independent of the death-animation pruning described in §6.4 — a stray un-resolved combat dialog state can never survive into the next player's turn.
127. **Win condition is checked at four independent sites**, each immediately after a VP grant, all guarded by `!state.winner` to prevent double-declaring: `combat-player-resolve.reducer.ts:111`, `combat-monster-resolve.reducer.ts:106`, `island-discovery.reducer.ts:26`, and `player-turn.reducer.ts:132` (the passive-ability/turn-start case). `docs/README.md` §5.1 lists the VP *sources* but never states that the win check itself is duplicated across four call sites rather than one central check — worth knowing before adding a fifth VP source.
128. **Default economy numbers** (`game-settings.ts:5-17`, all lobby-overridable): `victoryPointGoal: 30`, `vpPerIslandDiscovery: 1`, `initialDeployCost: 6` food (so army costs 6/8/10/12/14 as `deployCostIncrement: 2` applies after each deploy), `upgradeCost: 6` wood flat per level, `abilityCost: 15` gold flat, `baseResourceAmount: 1` per collection spot per turn, `resourceDensity: 0.6`. `docs/README.md` never states any of these numbers (it says "default 30 VP," "default 60% density," but not the deploy/upgrade/ability costs at all).
129. **Extra Move's own card text confirms the fix direction for point 61**: `SPECIAL_CARD_DESCRIPTIONS['Extra Move']` (`card-data.ts:35`) literally reads *"If used on an army that has not yet acted, it does not exhaust them"* — i.e. the in-game copy already states the rule the user corrected in the audit review, independent confirmation that `combat-player-roll.reducer.ts`, `combat-monster-roll.reducer.ts`, and `resource-position.reducer.ts` setting `hasActed = true` unconditionally is a bug against the game's own documented card text, not just the user's preference.

130. **Island reveal has no radius/neighbor effect** (`island-discovery.reducer.ts:6-16`, confirmed by its only two call sites in `movement.reducer.ts`): `revealIsland` only ever reveals the single tile an army actually lands on — there is no "reveal adjacent tiles" or fog-of-war radius anywhere in the codebase. This *confirms* `docs/README.md` §5.2's wording is accurate as written, just worth stating explicitly since it was a candidate for hidden extra behavior and there isn't any.
131. **`revealIsland`'s third parameter is reused for both Scout and Teleport** (`island-discovery.reducer.ts:6`, named `isScout` in the signature; called from `movement.reducer.ts` as `revealIsland(state, x, y, isTeleport)`): it's really a generic "suppress discovery VP" flag, not Scout-specific — naming is misleading but behavior is correct and consistent with §6.5's "Teleport does not award discovery VP" / "Scout does not award discovery VP" rules.
132. **Special-island card draw has its own full fallback chain** (`island-discovery.reducer.ts:36-73`, separate from the near-identical logic in `card-acquisition.reducer.ts` for Buy Card): hand full → log only, no card; deck and discard both empty → log only; deck empty but discard has cards → reshuffle discard into a fresh deck (Fisher-Yates shuffle) before drawing. Same three-way fallback exists twice in the codebase (special-island discovery and Buy Card) as separate implementations rather than a shared helper — not a bug, but a DRY note worth flagging to `kiss-dry-solid` review if either path is touched again.
133. **Map generation's full distance-based formula** (`map-generation.ts:1-69`, Manhattan distance from map center, i.e. `|x-centerX| + |y-centerY|`):
    - The exact center tile is **always** a solo Minotaur (level 4) boss monster island — not randomized, not subject to `resourceDensity` at all (`map-generation.ts:15-25`, the one `continue`-short-circuited special case).
    - Distance ≤ 1 from center (the ring immediately around the boss, excluding the boss tile itself): resource roll uses `resourceDensity - 0.1` (10 points lower than normal, i.e. fewer resource islands close to the boss), then 70% of the *remainder* is Special, 30% is Monster (so Special islands are deliberately front-loaded near the center, opposite of what §5.2's "more valuable/dangerous islands appear closer to the middle" implies for Special specifically — monsters get harder near the center, but Special-island odds are actually higher near center, not lower).
    - Distance > 1: normal `resourceDensity` for Resource, then 95% of the remainder is Monster, 5% is Special (Special islands are rare farther out, as §5.2 states).
    - A Resource island has a 40% chance of being dual-resource only when `distance <= 3` (never farther out) — the "distance affects one-vs-two resource types" rule from §5.2 is real but only applies within a 3-tile radius of center; beyond that every resource island is single-type. Single-type islands get a flat 2 collection spots (`2 * baseResourceAmount`); dual-type islands get 1 or 2 spots per type at 50/50 odds each (matches §5.2's "random number... one or two").
134. **Monster island generation's full table** (`monster-catalog.ts:11-68`, same Manhattan-distance-from-center metric as map generation, evaluated independently per monster-island tile — not reused from `map-generation.ts`'s own distance calc):
    - Distance ≤ 1 (ring around the boss): possible levels {3, 4} only. Distance ≤ 3: {1, 2, 3}. Distance > 3 (outer ring): {1, 2} only.
    - If the tile's possible-levels set includes a "big" monster (3 or 4): 30% chance it actually gets one. If it does, there's a further 25% chance (only reachable where level 4 is possible, i.e. distance ≤ 1) it's a level-4 Minotaur instead of a level-3 Ogre, and it's *always* paired with one little monster (60% Lancer/level 1, 40% Bear/level 2) — confirms §5.2's "'big' monsters always accompanied by 'little' monsters."
    - If no big monster rolled: 70% chance of exactly 1 little monster, 30% chance of 2, each independently rolled from the tile's little-monster-eligible levels (1-2).
    - A final dedupe step removes a second monster of the *same name* if one was accidentally rolled twice (e.g. two Lancers) — so an island can have at most one of each monster type, not necessarily "at most 2 monsters total" as a hard rule, though the roll logic above never generates more than 2 before dedupe.
    - Monster-kill VP table (`combat-monster-resolve.reducer.ts:6`): Level 1 = 2 VP, Level 2 = 5 VP, Level 3 = 7 VP, Level 4 = 10 VP. `docs/README.md` §5.1 only states the first two values and "increasing" — the 7/10 numbers for Ogre/Minotaur were undocumented.
135. **Bot attack priority is relative, not fixed** (`bot-army-actions.reducer.ts:35`): attacking an enemy player scores `8 + (own attackPower - enemy attackPower)` — a bot can and will pick a fight it's likely to lose if nothing else scores higher that loop, since the formula has no floor. Attacking a monster is a flat priority 7 regardless of monster level (`:48`), and moving onto an unrevealed fog-of-war tile (priority 6) or an unoccupied resource/base tile (priority 4) or a Special island (priority 3) or any other move (priority 2) — Positioning on a resource is the single highest priority at 9 (`:60`), confirming §6.8's ordering with exact numbers.
136. **Bot purchase order is fixed and sequential** (`bot-purchases.reducer.ts:7-50`): Ability → Upgrade → Deploy → Buy Card, each gated by its own affordability/cap check, re-reading `activeBot` fresh from state after each purchase (so an early purchase's resource spend can block a later one in the same turn). Buy Card's gold-cost check uses a hardcoded `10` rather than reading any settings field (there is no `settings.buyCardCost` — 10 is a literal in both the bot code and, per earlier verification, `player-actions.reducer.ts`'s equivalent human-facing check).
137. **Bot Sabotage always targets a human, never another bot** (`bot-card-strategy.reducer.ts:51`: `currentState.players.find((p) => !p.isBot && p.id !== activeBot.id)`) — in any match with multiple bots, bots never sabotage each other, only human opponents. Not documented anywhere, and relevant to balance/fairness discussions about bot-vs-human matches.
138. **Bot Wealthy card targets whichever resource it's currently short of**, checked in a fixed priority order (`bot-card-strategy.reducer.ts:37-40`): Food (if can't afford its next deploy and has room for more armies) → else Wood (if can't afford upgrade and isn't at attack cap) → else Gold (default/fallback). Not "random" or "whatever's lowest," a specific deterministic order.
139. **Bot pre-turn card activation has no conditional logic at all for Reinforce/Efficient/MasterBuilder** (`bot-card-strategy.reducer.ts:15-26`): the bot activates all three unconditionally whenever it holds them and hasn't used a card yet that turn, regardless of whether it's actually about to deploy/upgrade — if the bot never ends up affording a deploy/upgrade that turn, the activated flag is simply cleared at the next turn-start reset (per finding in section H point 123's sibling logic in `player-turn.reducer.ts`) and the card stays in hand unused (per the `IMMEDIATE_EFFECT_CARDS` deferred-consumption design in `card-effects.reducer.ts`) — functionally harmless but means the bot can "waste" its one use-card action on a flag that never pays off that turn, blocking itself from using a different card instead.

### Firestore security rules — RESOLVED (was a significant finding, not just documentation drift)
140. ~~**`firestore.rules` has no server-side enforcement of per-player action legality or identity at all**~~ — **Fixed in `docs/ai/tasks/2026-10-09-games-identity-rules/` (commit `4dd74ae`, "feat(firestore): require games/{gameId} writers to be a seated participant [phase 2/2]").** Current `firestore.rules` requires every Firebase Auth uid (guest or signed-in, via Anonymous Auth) to appear in the match's `players[].playerId` before it can `create`/`update`/`delete` a `games/{gameId}` doc (`isGameParticipant()`); `usernames/{username}` creates/updates/deletes are gated by `authUid`/`request.auth.uid`, with account-owned reservations permanent; `accounts/{authUid}` is create-once and otherwise immutable. The app's game logic in `src/lib/actions` still separately validates per-move legality — this rules change only closes the "who may write at all" gap, which is what this finding was about. Verified by reading `firestore.rules` 2026-10-10; rules unit tests live in `firestore.rules.test.ts`, run via `npm test`. One gap remains: the e2e spec covering this (`e2e/auth-and-lobby.spec.ts`) was not run in the games-identity-rules task's environment (no Java runtime for the Firestore emulator) — run it before deploy. **`2026-10-09-reconnect-bot-takeover`'s "only this player can reclaim this seat" guarantee can now rely on this server-side enforcement** rather than needing to build it.

141. **Bot turn orchestration, confirmed exact** (`bot-turn.reducer.ts:14-25`): `decideBotTurn` deep-clones the incoming state (lodash `cloneDeep`, pure — never mutates the caller's object), then runs `applyBotCardStrategy` → `applyBotPurchases` → `applyBotArmyActions` → `handleGameAction(EndTurn)` in that fixed order, matching `docs/README.md`'s high-level description exactly. `bot-turn.service.ts:1-16` is the only place that checks `botPlayer.isBot && status === 'playing'` before calling it — the reducer itself has no guard (its own doc comment says so), so any other caller must replicate that check.
142. **The "atomic" bot write is a plain `setDoc`, not a transaction** (`bot-turn.service.ts:15`): unlike `player-exit.service.ts` (which uses `runTransaction`), `takeBotTurn` reads `initialState`, computes entirely in memory, then does one unconditional `setDoc`. If a human action and a bot turn race against the same document, there's no optimistic-concurrency check (no version/etag compare) — the later write simply wins and silently discards the earlier one. `docs/README.md`'s "atomic" claim is true in the sense of "one write, not several," but not in the stronger sense of "safe against concurrent writers." Relevant risk to flag for `2026-10-09-reconnect-bot-takeover`, which will have a bot and a just-reconnected human both potentially racing to act on the same seat around the handoff moment.
143. **Bots are only ever created at match setup, and only for solo-vs-bot games** (`game-setup.reducer.ts:70-93`: the bot-adding loop is gated by `if (maxPlayers === 1 && numBots > 0)`). A multiplayer lobby game (`maxPlayers` 2-4, created via the normal "Create Game" flow) can **never** contain a bot seat today — bots and multi-human matches are currently mutually exclusive at the data-model level, even though nothing in `Player`/`GameState`'s types would prevent it. This is the single most load-bearing fact for `2026-10-09-reconnect-bot-takeover`: converting a human seat to a bot mid-match is genuinely unprecedented behavior, not an extension of an existing mixed-mode.
144. **Base-position assignment is strictly seat-index order, duplicated in two places** (`game-setup.reducer.ts:42-47` and `player-join.reducer.ts:38-43`, the identical `[{0,0}, {cols-1,rows-1}, {0,rows-1}, {cols-1,0}]` array hand-copied into both files): seat 0 = creator/top-left, seat 1 = second joiner (or first bot)/bottom-right, seat 2 = bottom-left, seat 3 = top-right. Not randomized, not player-chosen. A DRY violation worth a follow-up cleanup, not a bug.
145. **A lobby game auto-starts the instant its last seat fills** (`player-join.reducer.ts:76-86`): `addPlayerToGame` itself flips `status` to `Playing` and sets `turn = 1` when `players.length === maxPlayers`, with no separate "host clicks start" step for a full multiplayer lobby — `startGame` (`game-setup.reducer.ts:134-146`) is a distinct, separately-invoked function, presumably for a host starting a match before it's full (e.g. solo-vs-bot, where the single human+bots already satisfy `maxPlayers` at creation so `startGame` is likely the only path for that mode — confirming the exact UI call site for each was out of scope for this pass).
146. **Debug Mode's human-only bonus is `!isBot`-gated, not "the single human seat"-gated** (`player-factory.ts:16-25`): every player created with `debugMode && !isBot` gets the starting-card set and 20/20/20 resources — in a hypothetical multi-human debug match (not possible today per point 143, but the check itself doesn't special-case "exactly one human"), every human would get the bonus, not just one.
147. **Two different deep-clone strategies coexist**: `bot-turn.reducer.ts` uses lodash `cloneDeep`; `player-join.reducer.ts:26` uses `JSON.parse(JSON.stringify(...))`. Both produce a correct deep clone for this state shape (no functions/dates/Maps in `GameState`), so not a bug — just an inconsistency worth normalizing if either file is touched again.

148. **A 120-second per-turn countdown that auto-ends the turn exists and ships live — entirely undocumented.** `useTurnTimer` (`src/modules/game-board/turn-timer.hook.ts:6-67`): resets to `TURN_DURATION = 120` seconds whenever it becomes the local player's turn (`isMyTurn && gameStatus === 'playing'`), ticks down once per second, and when it hits 0 **automatically dispatches `GameAction.EndTurn`** — the current player's turn ends for them, with no confirmation. Exposes `isExpiring` (true in the last 20 seconds of a player's own turn) and `percentage`/`formattedTime` for UI. Confirmed wired into **four** separate HUD surfaces: `GameBoardHeader.tsx:57-60` (header countdown + `Timer` icon), `GameStatusBadge.tsx:30-32` (a `data-testid="turn-countdown-timer"` badge), `ActionsPanel.tsx:76-89` (desktop End Turn button progress ring + time label), and `MobileActionsBar.tsx:122-137` (mobile equivalent) — all with an `isExpiring`-driven visual warning state and existing test coverage (`ActionsPanel.test.tsx:229`, `MobileActionsBar.test.tsx:217`). This is a core, full-shipped game mechanic (every turn has a hard 2-minute cap, enforced client-side) that `docs/README.md`/`docs/architecture/*.md` never mentions at all — the single largest gap found in this entire audit. **Needs its own documentation section**, not a footnote — recommend adding it to whichever architecture file covers turn structure (`game-mechanics.md`, per the current split) alongside `hasActed`/`handleEndTurn`.
149. **The timer is client-side only, with no server-side enforcement** — unlike the Firestore write-authorization gap (point 140, now resolved), there is no equivalent server-side fix available for this one: `onActionRef.current(GameAction.EndTurn)` just calls the normal action dispatch path through the local client; nothing stops a player from keeping a tab open past 120 seconds if, say, their network is slow and the dispatch silently fails, nor is there anything forcing a *disconnected* player's turn to end at all (the timer only runs while their own browser tab is open and running the hook) — this directly informs the "disconnect vs. intentional leave" open question in `2026-10-09-reconnect-bot-takeover`'s triage: a disconnected player's turn does **not** time out and hand off on its own today; `handlePlayerExit` only fires on an explicit exit action or `beforeunload`, and a lost connection without either firing leaves the match stuck waiting on that player indefinitely. This is a meaningful addition to that task's scope, not just a side note.
150. **`useCardActions`' `handleCancelAction` already self-infers which card to cancel** (`game-board.card-actions.hook.ts:17-40`): called with no payload at all, it checks `uiState.pendingAction?.cardName`, then `localPlayer?.reinforceActive`, then `efficientActive`, then `masterBuilderActive`, then `hasExtraMove`, in that fixed priority order, and auto-attaches `scoutedTiles` if the pending action is a Scout. **This simplifies the fix for audit point 77** (`2026-10-09-hasacted-extramove-deselect-fixes`): `local_DeselectArmy` doesn't need to derive the card name itself — it can just call `handleCancelAction()` with no arguments, identical to how the keyboard Escape handler already calls it. Worth updating that task's plan.md to point at this exact function instead of describing a to-be-built inference.
151. **A known, intentionally-accepted type-safety gap**: `game-board.card-actions.hook.ts:78-79`'s own comment states "Sabotage, Wealthy and Steal Resource are runtime pending types that the `PendingAction` union does not list (pre-existing gap, out of scope)" — a previous agent already found and consciously chose not to fix this during an earlier task. Not a correctness bug (the runtime behavior works via an `as unknown as PendingAction` cast), just a type-coverage gap — flagging so a future reviewer doesn't rediscover it as "new."
152. **Host vs. non-host exit confirmation differs by game status, not just by role** (`game-board.session.hook.ts:49-62`): clicking "Exit" as the host *always* opens the Host Leave dialog, in any game status (including the pre-game lobby). A non-host player only gets a confirmation dialog if `status === 'playing'` — leaving a lobby before the match starts exits immediately with no confirmation for them. `handleConfirmExit` and `handleConfirmHostLeave` are two separate handlers that both simply call the same `handlePlayerExit(gameId, playerId)` — today there is no behavioral difference between "the host left" and "a regular player left" at this layer; the distinction lives entirely inside `handlePlayerExit` itself (point 105-107's logic). Directly relevant groundwork for `2026-10-09-reconnect-bot-takeover`, confirming there's exactly one call site to change, not two.
