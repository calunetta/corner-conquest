# AI workflow (Claude Code)

How this repository configures Claude Code, and how to work with it day to day.
Generated by [`bootstrap-prompt.md`](bootstrap-prompt.md); rerun that prompt after a large stack change.

## What lives where

| Path | Purpose | When Claude reads it |
|---|---|---|
| `CLAUDE.md` | Facts and rules for every session: stack, commands, folders, principles, workflow | Every session and every sub-agent |
| `.claude/settings.json` | Concise output style, allowed check commands, SessionStart hook | Every session |
| `.claude/skills/` | Procedures and standards (triage, swarm, testing, …) | When relevant, or preloaded into agents |
| `.claude/agents/` | The 13 agents of the swarm | When spawned |
| `docs/ai/templates/` | Templates for the task record files | When a task starts |
| `docs/ai/tasks/` | One folder per task: triage, designs, plan, progress, review | Handoff between agents; history for you |
| `scripts/claude-swarm-runner.sh` | Runs the pipeline headlessly through the Claude CLI | When you or the coordinator call it |
| `src/testbed/`, `src/app/testbed/` | Dev-only component previews at `/testbed` | When previews are added or checked |

## Day-to-day use

1. **Describe the work** (feature, component, bug, refactor). Claude runs `/triage` and shows a triage card: tier, pipeline, models, phases. For L and XL tasks it waits for your go-ahead.
2. **Run the swarm**: Claude follows `/swarm`, spawning agent pairs in order. Each agent ends with `DONE` or `BLOCKER`; a `BLOCKER` stops the run and comes back to you.
3. **Long tasks run in phases.** After each phase Claude commits and stops; type `continue` for the next one.
4. **New session?** The SessionStart hook lists unfinished phases, so Claude picks up where it stopped.
5. **Headless alternative**: `scripts/claude-swarm-runner.sh docs/ai/tasks/<folder>` runs the same pipeline through the CLI (`--dry-run` prints the commands without running them).

## The pipeline

```
triage
  → game-designer-a ⇄ game-designer-b     gameplay, balance, cards, economy (claude-sonnet-5)
  → ui-designer-a ⇄ ui-designer-b         anything the player sees (claude-sonnet-5)
  → architect-a ⇄ architect-b             plan.md: the contract (claude-sonnet-5)
  → implementer-a ∥ implementer-b         logic files ∥ view files, then cross-review (haiku → sonnet)
  → tester-a → tester-b                   logic tests first, then view and e2e tests (haiku)
  → preview-a ⇄ preview-b                 testbed previews, checked in a browser (haiku)
  → docs-sync                              mandatory when rules/architecture changed, incl. bug fixes (haiku)
  → architect-b (final review)            diff vs plan, checks, docs
```

`⇄` means a proposer and a challenger: the `-b` agent reviews the `-a` agent's work and answers `VERDICT: APPROVED` or `VERDICT: CHANGES REQUESTED`; changes go back to `-a`, at most two rounds.
Triage decides which stages a task needs. Tiers, stages and model rules are defined in `.claude/skills/triage/SKILL.md`.

## Agents

| Agent | Role | Writes |
|---|---|---|
| `game-designer-a` / `-b` | Propose / stress-test gameplay changes that make the game more fun | `game-design.md` |
| `ui-designer-a` / `-b` | Propose / challenge the UI spec: states, layout, copy, accessibility | `ui-design.md` |
| `architect-a` / `-b` | Draft / challenge the plan; `-b` also does the final review | `plan.md`, `progress.md`, `review.md` |
| `implementer-a` / `-b` | Logic files (`.types`, `.map`, `.service`, `.hook`) / view files (`.tsx`, `.styles`) | source code |
| `tester-a` / `-b` | Logic unit tests first / view tests and e2e specs | tests |
| `preview-a` / `-b` | Write testbed previews / check them in a browser | `*.preview.tsx`, screenshots |
| `docs-sync` | Keep `docs/README.md` and `docs/architecture/*.md` matching the shipped behavior, bug fixes included | `docs/README.md`, `docs/architecture/*.md` |

Each agent's model is the `model:` line of its file in `.claude/agents/` (the runner reads it from there). Defaults: claude-sonnet-5 for planners, haiku for builders.

## Code layout for new work

New code goes in `src/modules/<domain>/components/<Name>/`, one file per responsibility (view, hook, styles, mappers, types, tests, preview). Legacy folders stay frozen. See `.claude/skills/component-architecture/SKILL.md`.

## Maintaining this setup

- **Change a rule that applies everywhere**: edit `CLAUDE.md` (keep it under 200 lines).
- **Change a procedure or standard**: edit the skill in `.claude/skills/<name>/SKILL.md`. Each rule lives in one place; link to it instead of copying it.
- **Change a model**: edit the agent's `model:` line.
- **Add an agent**: copy an existing agent file, keep the `agent-protocol` skill in its `skills:` list, and add it to the triage stage table.
